# Decisions

Assumptions and judgment calls made without a synchronous check-in, per the working-style agreement: proceed autonomously through reasonable implementation decisions, document them here, and only stop and ask when credentials, external account setup, a business/legal choice, or a fundamentally product-changing decision is genuinely required.

## Stripe webhook reconciliation: organization/customer-wide, fenced against out-of-order writers (superseded twice — see history below)

**Current design (third independent review).** Two separate, previously-unresolved problems, both closed:

1. **Canonical retrieval is authoritative only for the ONE subscription it fetches — never for the organization or Stripe Customer.** A second independent review's "retrieve the named subscription and write it" design broke the moment two subscriptions existed for the same organization: a canceled `sub_old`, superseded by a genuinely newer `sub_new`, still produces a real, signed webhook event on any retry or manual redelivery, and retrieving/writing exactly `sub_old` silently overwrote `sub_new`'s live state. Reproduced directly (`app/api/webhooks/stripe/route.test.ts`'s "Finding 3" tests). **Fixed by never trusting a single retrieved subscription as the organization's truth at all**: `syncSubscription` lists the event's Stripe Customer's FULL subscription set (`stripe.subscriptions.list`) and picks whichever one should currently govern entitlement (`pickCurrentSubscription`: prefer a live/non-terminal subscription over a canceled/never-activated one; among ties, the most recently created) — an event naming an old subscription still triggers a fresh, complete re-derivation of the organization's real current state, never a blind overwrite with what that one event happened to carry. A subscription's Stripe Customer is also now required to match the organization's own already-persisted `stripe_customer_id`; a mismatch is quarantined (logged loudly, left for Stripe to retry) rather than treated as license to rebind the organization to a different customer.
2. **The write-write race a prior round called "self-healing" instead of closing.** Two webhook deliveries for the same organization processed concurrently could each retrieve/list Stripe state, then race to write, with the OLDER request's write landing AFTER the newer one's and silently reverting it — both still returning HTTP 200, with no guarantee a later event would ever re-correct it (calling this "self-healing" was itself the mistake: nothing about the design actually guaranteed a correcting event would arrive). **Fixed with `billing_sync_seq`, a per-organization fencing token** (`claim_billing_sync`, migration `20260907200000`): claimed via a single atomic UPDATE before any Stripe network call (no database transaction ever spans a Stripe call), and the final write is conditioned on still holding the exact value claimed. A request that finishes later than a newer one has a lower seq by the time it writes; its conditional UPDATE matches zero rows once the newer request has already advanced the counter, and it correctly stands down instead of overwriting the newer result. Proven with a barrier-controlled concurrent test forcing reverse completion order (`app/api/webhooks/stripe/route.test.ts`'s "Finding 4" test).

A genuinely missed reconciliation (a crashed request that claimed a fencing token but never wrote) is not auto-corrected by anything today — Stripe's own retries are finite. **Revisit if** production billing volume makes a missed webhook a real operational concern: an authenticated manual resync endpoint and/or a monitored scheduled reconciliation job (re-running the same list-and-pick logic for every organization with a live subscription) would close this without changing the fencing mechanism itself.

**History (superseded designs, kept for context, not current behavior):** round 2 of this review compared each event's `created` timestamp against the last one applied, which broke on Stripe's own one-second timestamp resolution (two distinct same-second events, the second wrongly treated as "not newer"). Fixed by switching to per-subscription canonical retrieval, documented at the time as leaving a "self-healing" residual race under genuine concurrency — the third review found that framing wrong on two counts (the race wasn't actually self-healing, and canonical-per-subscription retrieval had its own separate organization-wide correctness gap), both closed above.

## Billing state machine: `activated_at` set only from a signed `invoice.paid` event, never from a subscription status snapshot (superseded once — see history below)

**Current design (third independent review).** A grandfathered organization can pay, transition to Stripe status `active` briefly, and be canceled again before any subscription-status webhook happens to be processed while it was still active — under the prior design (`activated_at` set inside `syncSubscription` when an observed status was `'active'`), that specific delivery timing meant `activated_at` would simply never be set, and a genuinely-once-paying organization would keep relying on grandfathering forever. **Fixed by decoupling activation from subscription state entirely**: `activated_at` is now set only by `activateOnPayment`, triggered exclusively by a signed `invoice.paid` event — Stripe's own durable, verified "a payment genuinely succeeded" signal, independent of whatever the subscription's status happens to read at any later point. Idempotent by construction (`.is("activated_at", null)` at the database level): a duplicate delivery, a second successful invoice, or events arriving in any order all converge on the same result, and a subscription canceled moments after this invoice paid does not un-set it. See `app/api/webhooks/stripe/route.ts`'s `activateOnPayment` and its "Finding 5" test suite (payment-then-rapid-cancellation, a missed `active` subscription event, duplicate invoices, reverse arrival order).
`isBillingActive` (`features/billing/status.ts`) checks the current subscription status first (a real `active`/`trialing` subscription is always authoritative, independent of `activated_at`), falls back to blocking if `activated_at` is set (real billing has genuinely started at least once — grandfathering/trial are a one-time bridge, not a permanent exemption a later cancellation regains), and otherwise falls back to whichever pre-payment grant applies. `hasLiveSubscription` is the separate, narrower question Checkout's own guard needs — trialing/active/past_due/incomplete/unpaid/paused block a second attempt (a live or recoverable subscription a duplicate Checkout would risk double-charging); `canceled`/`incomplete_expired` do not, since both are dead ends a resubscribe attempt must be allowed past.
**Why two separate functions rather than one combined check:** `isBillingActive` answers "can this organization use the dashboard right now" (checked on every request); `hasLiveSubscription` answers "would a new Checkout Session risk creating a duplicate" (checked only when starting one) — the two questions have different, only partially-overlapping answers for several statuses (e.g. `past_due` blocks dashboard access but also blocks a *new* Checkout, since the correct recovery path is the Billing Portal, not a second subscription).
**Revisit if:** the product ever needs multiple subscriptions per organization, or a genuine "downgrade to grandfathered" support flow — `activated_at` is deliberately a one-way, permanent flag today.

**History (superseded, kept for context):** the design this replaces set `activated_at` inside the subscription-sync path itself, conditioned on the currently-observed Stripe status being `'active'` — correct for the specific incident it originally fixed (grandfathering surviving an `incomplete` first attempt) but still vulnerable to the missed-delivery-timing gap described above, which a third independent review found and closed by moving to `invoice.paid`.

## Checkout concurrency: a durable, owned checkout-attempt model with compare-and-swap, not a bare lease pair (superseded once — see history below)

**Current design (third independent review).** The prior "database-backed lease" (a bare `pending_checkout_session_id`/`pending_checkout_expires_at` pair, no ownership token) had several real gaps once examined closely: its 60-second claim window was shorter than the installed Stripe SDK's own 80-second default request timeout, so a genuinely slow-but-legitimate Stripe call could have its claim expire and get raced by a retry; its final Supabase write ignored `{ error }` and affected-row count; nothing gave a caller an identity to compare-and-swap against, so a delayed caller could clear or overwrite a newer claim; lease decisions compared against the application server's own clock, not the database's; the Stripe idempotency key was time-bucketed, so a retry after the bucket rolled over reached Stripe as an apparently-fresh request; a completed session was never reconciled once the local lease itself had expired; and an open session for one plan/interval could be reused for a different one.
**Fixed with a durable, opaque checkout-attempt id and three compare-and-swap database functions** (`claim_checkout_attempt`/`record_checkout_session`/`release_checkout_attempt`, migration `20260907200000`), all conditioning their writes on that exact attempt id and all making lease decisions with `clock_timestamp()` inside the database, never the application server's clock:
- The claim window is 150 seconds (comfortably above the SDK's 80-second default, with margin).
- `record_checkout_session`/`release_checkout_attempt` both fail (return null/false, checked by the caller) if the attempt id no longer owns the row — a delayed caller holding a superseded attempt id can never modify a newer claim.
- The Stripe idempotency key (`checkout:attempt-<id>`) is derived from the durable attempt id, stable across any retry that still holds the same (unexpired) claim.
- `claim_checkout_attempt` returns a superseded attempt's own session id ALONGSIDE a freshly-minted attempt id when the previous claim has expired — the caller still reconciles that orphaned session against Stripe (including a completed one) before ever creating a new one, closing the "reconcile even after 24 hours" gap.
- Interval, Price id, and mode are stored per attempt and compared before any reuse; a mismatch (a plan switch mid-flow) releases the stale attempt and claims a genuinely fresh one rather than reusing a session for the wrong plan.
See `features/billing/actions.ts`'s `claimAndCreateCheckoutSession` and its test suite (barrier-controlled concurrency, persistence-error, zero-row/fenced-out, slow-Stripe, plan-switch, and completed-session-after-lease-expiry cases) in `features/billing/actions.test.ts`.
**Why a webhook-clearable claim, not just its own expiry:** once a subscription genuinely exists for an organization, any pending checkout attempt has been fulfilled (successfully or not) and must stop blocking a future legitimate attempt immediately, not up to 24 hours later — `syncSubscription` clears every checkout-attempt column unconditionally on every successful sync (subject to its own fencing token, see above), and the attempt's own expiry is only the fallback for a checkout that was started and simply abandoned (a closed tab, a crashed request), which has no webhook event of its own to be cleared by.

**History (superseded, kept for context):** the design this replaces (`organization_billing.pending_checkout_session_id`/`pending_checkout_expires_at`, migration `20260907190000`) was a real improvement over a bare time-bucketed idempotency key, but a third independent review found it still lacked the ownership/compare-and-swap semantics described above.

## Stripe configuration validated against what the billing page actually promises, not trusted from environment variables alone

Third independent review, Finding 6: the billing page hardcodes 5,990 Ft / 59,900 Ft display prices while the actual amount charged is whatever `STRIPE_PRICE_ID_MONTHLY`/`STRIPE_PRICE_ID_YEARLY` happen to resolve to on Stripe's side — a swapped, stale, or wrong-mode Price id would silently charge something different from what the page shows, with nothing in this app ever noticing.
**Fixed with `assertStripeConfigurationValid()`** (`features/billing/stripe-config.ts`), checked before every Checkout attempt: `STRIPE_SECRET_KEY`'s own live/test prefix must agree with `APP_ENV`; both Price ids must resolve, be `active`, agree with `APP_ENV` on livemode, charge exactly the promised amount in `huf`, recur at the promised interval, be `tax_behavior: "inclusive"` (matching the page's own "árak az ÁFát tartalmazzák" copy), and both resolve to the SAME Stripe Product. The webhook route separately checks `event.livemode` against `APP_ENV` on every delivery (`checkEventEnvironment`) — a different check (an incoming event, not an outgoing API call) needed at a different layer, not folded into the same function.
**Why memoized, not checked fresh on every request:** a live Stripe API call (`prices.retrieve`) on every single Checkout attempt would be real, unnecessary latency and API load for something that only needs to catch a genuine misconfiguration — which doesn't change between requests. A failed validation is never cached (the next call re-attempts it), so a transient Stripe outage doesn't get mistaken for a permanent misconfiguration.
**Revisit if:** this app ever sells more than one product, or Price ids become editable at runtime (e.g. an admin UI) rather than fixed environment variables — the per-process memoization assumes they don't change without a redeploy.

## Checkout success is verified server-side against Stripe, not inferred from a query parameter

Third independent review, Finding 7: `?checkout=success` alone proves nothing — a bookmarked, shared, or hand-crafted URL could carry it with no real Checkout ever having happened. **Fixed by using Stripe's own `{CHECKOUT_SESSION_ID}` placeholder** in `success_url` (substituted server-side by Stripe on redirect, not client-controllable) and retrieving that session directly from Stripe on the billing page, verifying it actually belongs to the current organization (`client_reference_id`/`metadata.organization_id`) before rendering anything. Four distinguishable outcomes, not a single boolean: paid and already locally reflected ("confirmed"); paid but the webhook hasn't landed yet ("pending" — webhooks are asynchronous, this is a normal brief window, not an error); never actually completed ("unpaid"); missing/foreign session ("invalid" — logged loudly, since a foreign session id here is worth investigating, and rendered as if no success param were present at all rather than any kind of error banner).
**Grandfathered organizations get their own explicit UI state** (a "Ingyenes hozzáférés" badge and copy explaining permanent, non-expiring access) instead of being folded into the generic "trial" badge/countdown treatment, which previously implied an expiry that doesn't exist for them and asked them to subscribe with the same urgency as an organization whose actual trial is running out. The Checkout forms remain visible below regardless — grandfathering being permanent doesn't mean subscribing should be hidden or blocked, only that it should never be presented as required or time-pressured.

## Hungarian localization: in-place translation, not an i18n framework

The full UI (public feedback flow, auth, dashboard, email alerts) is Hungarian by directly replacing English strings, not via `next-intl` or similar with language files and a switchable locale.
**Why:** the explicit request was "make the whole system Hungarian," not "support both languages" — no toggle or English fallback was asked for. Adding an i18n framework for a single fixed language would be exactly the premature abstraction the product skill warns against; it's straightforward to introduce later if English support is ever actually needed, since nothing about in-place strings blocks that migration.
**Revisit if:** the product needs to serve non-Hungarian-speaking businesses too.

## Supabase Auth's own error messages get a translation lookup, not raw passthrough

`features/auth/actions.ts`'s `translateAuthError()` maps the handful of Supabase SDK error strings the app actually surfaces (invalid credentials, already-registered, etc.) to Hungarian, falling back to a generic message for anything unmapped.
**Why:** Supabase Auth returns error messages in English with no localization option; showing that raw text on an otherwise fully-Hungarian sign-in form would be a jarring, obviously-untranslated seam. A small lookup table for the errors users actually hit is cheap and covers the real cases; the generic fallback means an unmapped Supabase error still degrades to Hungarian rather than leaking English.

## Developer-facing log messages (`console.warn`/`console.error`) stay in English

Server-side log lines like "Failed to send negative feedback alert email" were not translated, even though everything a business owner or customer actually sees was.
**Why:** these are read by whoever maintains the code (server logs, Vercel dashboard), not by end users — translating them would add no value for a Hungarian business owner (who never sees a server log) and would work against future maintainers/AI assistants who default to English technical conventions.

## Rebrand: navy/blue/cyan from the actual logo, replacing the invented wine/gold palette

The `--pf-*` CSS custom properties (shared by the public feedback page and the homepage) were repointed from an invented "wine and gold, warm hospitality" palette to navy ink + a blue-to-cyan gradient, matching the user-supplied logo and app icon exactly. Renamed `--pf-wine`/`--pf-wine-hover`/`--pf-gold` to `--pf-accent`/`--pf-accent-hover`/`--pf-accent-2` throughout, since the old names became actively misleading once they held blue/cyan values.
**Why:** the original wine/gold direction was a reasonable choice when no brand assets existed yet, but a real logo/icon was later provided — matching it exactly is strictly better than an invented palette once one exists, and using it is what was explicitly asked for.

## Single organization per signed-in user

`getCurrentOrganization()` resolves the earliest-joined membership and the dashboard has no org switcher, even though the schema (`organization_memberships`) supports a user belonging to more than one organization.
**Why:** no product requirement yet calls for one user managing multiple businesses, and building a switcher speculatively would be exactly the kind of premature abstraction the product skill warns against.
**Revisit if:** a user needs to manage more than one business — the schema already supports it, so this is additive, not a migration.

## No role-gated dashboard authorization

`organization_memberships.role` supports `owner/admin/manager/staff`, and RLS/dashboard access is uniform across all of them — no feature is currently hidden or restricted by role.
**Why:** there is no invite flow, so no membership other than `owner` (the signup-time creator) can ever actually exist yet. Gating UI or actions by a role that's unreachable would be dead code that's also untestable, and would be inconsistent with the rest of the app's current "any member can act" model.
**Revisit when:** an invite flow ships and `manager`/`staff` memberships become real — at that point, Settings (business profile edits) is the most likely first candidate for an owner/admin-only restriction.

## Organization logo as a pasted URL, not an upload

The Settings page's `logo_url` field is a plain text input validated as an `http(s)://` URL, not a Supabase Storage upload widget.
**Why:** building storage upload UI (bucket policies, signed URLs, image validation, a picker component) is a meaningfully larger scope than the rest of the Settings page for a field with no other consumer yet (nothing in the product currently renders the logo anywhere).
**Revisit when:** something actually displays the logo (e.g. branding the public `/r/{publicId}` page) and self-hosted upload becomes worth the scope.

## `notification_email` overrides member-based alert routing (not additive)

If an organization sets `notification_email`, negative-feedback alerts go there and only there — the owner/admin/manager member lookup is skipped entirely, not supplemented.
**Why:** matches the Settings page's own copy ("Where negative-feedback alerts are sent. Leave blank to notify all team members instead.") and the common real-world case: a business wants alerts routed to one shared inbox (e.g. a manager's email or a shared support address), not fanned out to every account holder.
**Revisit if:** a business wants both a shared inbox and individual member alerts — would need to become an explicit "also notify members" checkbox rather than silent dual-delivery.

## Cookie-based duplicate-submission guard, plus a database-backed rate limit (not Redis)

**Superseded in part** by the 2026-09-04 review-response pass — see `SECURITY.md` § "Rate limiting: database-backed, not Redis" for the current, accurate state. The cookie-based guard below is still exactly as originally decided; what changed is that "no rate limiting at all" turned out to be the wrong call, not "no *Redis* rate limiting."

Original reasoning, still valid for the cookie half: Vercel's serverless model makes an in-process limiter unreliable without new infrastructure, which isn't justified before an observed abuse problem; a short-lived, card-scoped, `HttpOnly` cookie solves the actual common case (accidental double-tap) with zero new infrastructure and no personal data collected. What the original reasoning got wrong: it treated "no in-process limiter" and "no rate limiting" as the same conclusion, when Postgres — already the shared state every request goes through regardless of serverless instance — could enforce a count-over-a-trailing-window check with zero new infrastructure, inside the same atomic function (`submit_feedback_atomic`) that already needed to do the insert. An independent review flagged the resulting gap (unbounded scripted flood, and a related email-amplification risk since each qualifying submission sends a real alert email) as finding #2; both are now fixed at the database layer.
**Revisit if:** the 20-per-5-minutes threshold turns out too strict for a real high-traffic location, or too loose against real observed abuse — it's a plain constant in the migration, easy to retune without an architecture change.

## Single `internal_note` column, not a `feedback_notes` table

The master build prompt's suggested schema includes a separate `feedback_notes` table (presumably for multiple, attributed, timestamped notes per feedback item). The shipped schema keeps the original single `internal_note text` column on `feedback` instead.
**Why:** the dashboard's actual manager workflow today is one person resolving one item; a single free-text note covers that completely. A separate table (with its own RLS policies, its own UI for a note thread, author attribution) is real added complexity for a capability nothing in the current product asks for — exactly the "complicated CRM workflow" the product skill says to avoid during MVP.
**Revisit when:** more than one team member is realistically working the same feedback item (which itself depends on the invite flow / role-gating above existing first) and a single overwritable note becomes a genuine collaboration gap.

## `priority` as a generated column, not application-computed

`feedback.priority` is `GENERATED ALWAYS AS (...) STORED` from `rating`, rather than computed in TypeScript at read time or written by the application on insert.
**Why:** correctness-by-construction — a generated column cannot drift from the rating that produced it, whereas an app-computed value could (a bug, a bypassed code path, a manual DB edit) silently desynchronize priority from rating. This is a stronger guarantee than the alternative for equivalent effort.

## UTC day boundaries for "today" / "this week"

Overview stats' `today`/`thisWeek` use UTC calendar-day boundaries (matching the existing `dailySeries` aggregation's own UTC-day convention), not a per-organization local timezone.
**Why:** the schema has no per-organization timezone field, and adding one purely to shift a dashboard stat by a few hours is disproportionate for MVP. A single-timezone small business won't notice the skew; this was already the established convention elsewhere in `features/analytics/aggregate.ts` before this decision, so it's consistency, not a new tradeoff.
**Revisit if:** a business spans multiple timezones or complains about the boundary being visibly wrong for their location.

## Sentry source map upload skipped for now

`withSentryConfig` in `next.config.ts` runs with only `{ silent: true }` — no `org`, `project`, or `authToken`. Error capture (client/server/edge) is fully live; stack traces in the Sentry dashboard will show minified production code instead of your original source.
**Why:** wiring up source maps needs a `SENTRY_AUTH_TOKEN`, which is a credential — per the working-style agreement, that's a "stop and ask" item, not an autonomous one, and the DSN alone (no token needed) already delivers the actual point of this round: knowing when something breaks in production.
**Revisit when:** minified stack traces become a real debugging obstacle — at that point, generate a Sentry auth token and add `org`/`project`/`authToken` to the `withSentryConfig` call.

## No Sentry Session Replay or user feedback widget

Only core error monitoring was wired up — not `Sentry.replayIntegration()` or `Sentry.feedbackIntegration()`, both mentioned in Sentry's own quickstart.
**Why:** Session Replay records DOM/screen activity, which is a materially bigger privacy surface than error capture alone (see `SECURITY.md` § Data minimization) and wasn't what was actually asked for — the task was closing the "no error monitoring" gap tracked in `STATUS.md`, not building out a full observability suite. Adding integrations nothing asked for is the kind of speculative scope the product skill warns against.
**Revisit if:** debugging a hard-to-reproduce customer-facing bug genuinely needs session context beyond what an error's stack trace and breadcrumbs already provide.

## e2e tests now run against a dedicated isolated Supabase project

**Superseded** by the 2026-09-04 review-response pass. The reasoning below explains why this was originally accepted and is kept for that context; it is no longer the current state — see `e2e/README.md` for how tests are configured today.

Original decision: `e2e/review-gating.spec.ts` hit the same Supabase project used for local dev and production — there was no `supabase start` (Docker-based local Postgres/Auth) stack for tests to run against instead.
**Why it was accepted then:** this project had never had local-Postgres infrastructure at any point (every migration was pushed directly via `supabase db push --db-url` against the linked hosted project), so a Docker-based local stack would have been genuinely new infrastructure, not a variation on an existing pattern — and it couldn't be verified in the environment this was built in (no Docker available there either). There were no real customers on the product yet, so the blast radius was accepted as low.

**What changed:** an independent review treated "tests run against production" as a real, current risk regardless of whether customers exist yet — correctly; "no customers yet" bounds the blast radius of a mistake, it doesn't make writing test data into the production database intentional or reviewed. The task required an isolated database for its own DB-touching fixes, which forced the actual resolution: a new, dedicated, free-tier Supabase project (URL/keys in `.env.test.local`, gitignored), with `e2e/support/env.ts` preferring it over `.env.local` and `playwright.config.ts` injecting its values into the spawned dev/start server's environment so the app under test talks to it too, not just the Node-side test helpers. Docker remained unavailable throughout, so this is still not a local stack — but it is now a genuinely separate project, not the production one.
**Still open:** CI's e2e job secrets need updating to the isolated project's values if they were ever set from `.env.local` — see `STATUS.md`'s "What's needed from the user."

## Analytics row-cap fix: page-by-page fetching, not SQL-side aggregation

**Superseded** by the round-2 review response — see `SECURITY.md` § "Analytics correctness" and `DATABASE_SCHEMA.md` § "Database functions callable as RPCs" for the current state (SQL-side aggregation, exactly what this entry originally declined to build). Kept below for the original reasoning and why it changed.

An independent review's finding #7 flagged that `getOverviewStats`/`getAnalyticsData` computed all-time/period stats by fetching feedback rows into Node and reducing them there — and that PostgREST's `max_rows` cap (1000, `supabase/config.toml`) silently truncated any single request past that, which was confirmed empirically (1200 seeded rows, `.limit(5000)` requested, 1000 returned). The review's suggested fix was tenant-scoped SQL aggregate functions/views, which would sidestep the cap entirely.
**What was built instead (round 1):** `features/analytics/fetch-all-rows.ts` fetched page by page (parallel requests past the first) until a `MAX_ROWS = 5000` ceiling, leaving `aggregate.ts`'s existing pure, already-unit-tested reduction functions untouched.
**Why it seemed right at the time:** fully closed the *reported* correctness bug (no more silent truncation at 1000 rows) with a much smaller, lower-risk change — no new migration, no new RPC/view surface to keep in sync with `aggregate.ts`'s several different breakdowns. Per the product skill's own "avoid unnecessary infrastructure" and "do not build a full BI platform during MVP," proportionality mattered: the *reported* bug was about correctness at the 1000-row cap specifically, not performance, and page-by-page fetching was correct up to the new 5000-row ceiling.
**What changed:** a round-2 review (R2-02) correctly pointed out that 5000 was itself still a silent correctness ceiling — the same class of bug at a higher threshold, not a different class of problem the original fix didn't need to consider. Separately (R2-03), `OFFSET`-based pagination turned out to not be consistent under concurrent writes at all — a property page-by-page fetching never actually had, previously undetected because nothing had tested it under concurrency. Both findings together meant the original "smaller, lower-risk change" framing was wrong on its own terms: a bounded-but-still-silently-truncating ceiling plus a pagination-consistency bug is not actually lower-risk than the SQL aggregation the first review already suggested. Built this round: `get_feedback_overview_snapshot`/`get_feedback_period_analytics`, computing every statistic inside one tenant-scoped SQL function call per page — no row-count ceiling, one consistent MVCC snapshot per call.
**Lesson, not just an outcome:** proportionality reasoning is only as good as its list of what the smaller fix doesn't need to consider — this is worth re-checking explicitly (not just re-asserting the original conclusion) whenever a later review specifically challenges the boundary a "smaller fix" was scoped to.

## `create_organization_atomic` as `SECURITY DEFINER`, not another admin-client insert

Finding #8 (onboarding non-atomicity/non-idempotency) could have been fixed by keeping the admin-client architecture and just wrapping the existing two inserts more carefully (e.g. a compensating-transaction pattern, or moving both inserts behind a single admin-client RPC call to a `SECURITY INVOKER` function run as `service_role`). Instead, `create_organization_atomic` is `SECURITY DEFINER`, callable directly by the authenticated user's own session — the only genuinely `SECURITY DEFINER` function in this schema.
**Why:** the actual race (finding #8's per-user serialization requirement) needs the check-existing-org-then-insert sequence to happen atomically from the *caller's own identity* (`auth.uid()`), which only makes sense evaluated as that specific user — routing it through the admin client would mean either trusting a user-supplied user ID (a spoofing risk) or adding an extra auth round trip to look up the caller's identity server-side first, for no benefit over letting Postgres read `auth.uid()` directly from the RPC caller's own JWT. `DEFINER` here is the standard, narrowly-scoped pattern for "let an authenticated user perform one specific privileged action that RLS structurally can't authorize," with the mitigations documented in `SECURITY.md`.

## R2-08: server-owned cooldown and an org-level budget; R3-03 completed recipient verification

Round 2 finding R2-08 flagged three things about the negative-feedback alert's abuse controls: the cooldown state was tenant-writable (a plain column an org member's own session could reset via a direct `UPDATE`), the per-card rate limit didn't bound total email volume across an org's cards, and `notification_email` accepts any syntactically-valid address with no verification that the org actually controls it. The first two were fixed completely in round 2: `last_negative_alert_at` can only be changed by `claim_negative_alert_send()` (a trigger rejects every other caller, including the admin client itself), and that same function enforces an organization-wide hourly budget independent of which card a submission came from.

**Round 2 explicitly deferred the third piece** (recipient verification), reasoning that the only complete fix was a real email-confirmation flow, and that the org-wide budget was a real, meaningful (though partial) mitigation in the meantime. A domain-matching heuristic was considered and rejected — actively wrong for this product's real usage pattern (small business owners routinely sign up with a personal Gmail address while wanting alerts routed to a business address on a different domain).

**Round 3 (finding R3-03) built the confirmation flow this entry originally deferred**, since a second independent review pushed back on treating the budget alone as sufficient: `request_notification_email_change()`/`confirm_notification_email_change()` (`DATABASE_SCHEMA.md`) — a candidate address is stored as PENDING alongside a hashed, expiring, single-use token; the active `notification_email` (what alerts actually go to) is untouched until the token is confirmed by visiting a link sent to the candidate address itself. Requesting a new address always overwrites any prior pending request outright — no history of abandoned requests is kept, since the only thing that matters is the current pending token's validity. Clearing the address needs no verification (removing a recipient can't be abused to send email anywhere). The same class of "RLS is row-level, not column-level" gap R2-08 already fixed for the cooldown column applies here too — a trigger (`private.prevent_direct_notification_email_change`) rejects any direct write to the four notification-email columns from any caller but the three functions above, closing the specific hole where a member could otherwise set the pending token hash to one they chose themselves and "confirm" an address without ever proving inbox possession.

**Why this wasn't built in round 2 despite being clearly the complete fix:** proportionality under the original task's own framing — treating a full confirmation flow (new columns, a new public route, new Resend copy, new pending-state UI, an enforcement trigger with its own deploy-ordering hazard) as disproportionate to fold into a pass whose stated scope was fixing a set of already-identified security findings, versus shipping the cheaper, still-meaningful budget mitigation and flagging the gap explicitly for a follow-up. That judgment call was revisited, not reversed on new information: R3-03 concluded the deferral itself was the wrong call for a public-facing spam-relay vector, not that the original reasoning about relative cost was inaccurate.
**Revisit when:** nothing further — this is now the intended long-term state, not a stepping stone.

## Billing: one flat plan, a 14-day no-card trial, dashboard-only paywall

Three related choices made together when Stripe subscriptions were built: (1) a single flat plan, unlimited locations/cards, offered at two billing cadences (5 990 Ft/hó, or 59 900 Ft/év — roughly 2 months free versus paying monthly, a standard annual-discount shape) rather than usage-based tiers; (2) every organization gets a 14-day trial with no card required at signup, rather than requiring payment details up front; (3) the paywall (`app/dashboard/layout.tsx`) blocks only the operator dashboard — never the public NFC landing page or feedback submission, regardless of an organization's billing status.
**Why (1):** per the product skill's MVP guidance against premature tiering — there's no usage data yet to size tiers against, and `organization_billing`'s schema doesn't assume a plan count of one (`stripe_subscription_id`/`status` are plan-agnostic), so adding tiers later is additive, not a rework.
**Why (2):** the product's own explicit priority right now is landing its first paying customers (see `STATUS.md`) — requiring a card before a business has seen a single real customer rating land in their dashboard is exactly the kind of friction that costs signups without buying anything in return. A no-card trial removes that friction while still bounding how long access is free.
**Why (3):** a physical NFC card, once sold and placed on a customer's counter, is a promise to that business's own customers that tapping it works — a lapsed subscription must never retroactively break that promise or silently stop collecting real feedback. This is the same shape as the product's non-negotiable Google-Review-non-gating rule (`PRODUCT_SPEC.md`): the public-facing product experience must stay neutral and reliable regardless of an unrelated account-level state. Also directly relevant to how physical cards are sold (see the next entry): a card and a subscription are two independent things a customer can buy, and gating the card on the subscription would break that independence.
**Revisit if:** real usage data shows most organizations only need one location (tiering would be pure complexity) or, conversely, shows enough variance in usage to justify a second tier; or if trial abuse (repeated signups to extend free access) becomes a real problem worth adding friction to prevent.

## Physical NFC cards and the SaaS subscription are sold, and can be used, independently

The dashboard subscription and owning a physical NFC card are deliberately decoupled: an organization can subscribe with zero cards (nothing stops it, nothing requires a card to exist), and — per the entry above — a card keeps working for an unsubscribed organization's existing customers. Physical card fulfillment (inventory, shipping, ordering) is intentionally kept **out of this app**, on a separate storefront (Shopify, on a subdomain of the product's own domain) rather than built as a custom commerce system here.
**Why:** Shopify already solves inventory/shipping/tax well; rebuilding that inside this app to unify it with Stripe subscription billing would be substantial scope for a problem already solved. Keeping the two systems separate (one for physical goods, one for the recurring SaaS charge) is simpler to build and reason about than a merged commerce system, and matches the actual sales model: a card and a subscription are two different purchases a customer can make in either order, or only one at all.
**Not yet built:** a "claim" flow (pre-provisioned card inventory + connecting a physically-bought card to a dashboard organization after the fact) — today a card only exists once created inside a signed-in dashboard. Needed once card fulfillment actually depends on it; tracked as a follow-up, not started.
**Revisit if:** Shopify's fees or limitations become a real problem, or once card fulfillment volume justifies the cost of a fully custom storefront.

## Grandfathering pre-existing organizations into billing with a non-expiring bridge, not a short trial

Found during an independent review after the billing feature (above) was already built: the provisioning trigger that grants every new organization a 14-day trial only fires on organization creation, so every organization that already existed before billing shipped had no `organization_billing` row at all — `isBillingActive(null)` is `false`, so every one of them was silently, permanently locked out of the dashboard the moment this feature deployed. The fix backfills a `grandfathered_at` timestamp for each of them (`isBillingActive` treats it as always-active, until the organization actually subscribes through Stripe — see `features/billing/status.ts`), deliberately **not** the same 14-day countdown a brand-new signup gets.
**Why not just backfill a trial_ends_at 14 days out, reusing the existing mechanism instead of adding a new column:** these are organizations that were already using the product with no advance warning that billing was coming or that a clock had started — a 14-day countdown beginning the instant this migration happens to run would be a surprise outage for whoever hadn't checked the dashboard in two weeks, not a considered billing rollout. A distinct, non-expiring signal makes the two cases (a new signup's genuinely time-boxed trial vs. an existing customer's one-time grace period) impossible to confuse later, and gives the owner a direct, greppable way to find every organization still relying on it (the migration's own comment has the query) rather than inferring it indirectly from an unusually old `trial_ends_at`.
**Why it stops applying once a real Stripe subscription exists:** originally, `isBillingActive` checked bare `stripe_subscription_id` presence before `grandfathered_at` — found during a later independent review to be wrong in its own right (a grandfathered organization whose first payment attempt merely went `incomplete` lost grandfathering immediately, before any payment had actually succeeded). Corrected to check `activated_at` instead — a one-time signal set only on a genuine transition to Stripe status `'active'`, never on a subscription merely existing — so grandfathering now survives exactly the case it was built for (a payment attempt that hasn't succeeded yet) and still stops applying once one genuinely has. See "Billing state machine: `activated_at`..." near the top of this document for the full design.
**Revisit if:** the owner decides grandfathered organizations should eventually be asked to subscribe on a deadline — nothing in the code expires `grandfathered_at` automatically, by design, so that would be a deliberate follow-up migration/communication, not a silent cutoff.

## Stripe webhook processing reordered to apply-then-record, not record-then-apply

Found during an independent review: the webhook handler used to insert the incoming event's id into `stripe_webhook_events` (its idempotency ledger) *before* updating `organization_billing` with that event's effect — two independent, unchecked Supabase requests, not one transaction. A crash, timeout, or simply an unchecked update error between those two calls permanently marked a never-applied event as done, since a retried delivery would hit the already-recorded id and stop before ever reaching the update.
**Why reordering (apply first, record only after success) rather than making the two writes a real database transaction:** `syncSubscription`'s update is naturally idempotent — it always sets fields to the exact snapshot the current event describes, never increments or appends — so simply re-running it on a genuine retry is always safe. Reordering achieves the same practical guarantee (no lost update) as wrapping both writes in one RPC-backed transaction would, without adding a new `SECURITY DEFINER` function or a second code path just for this one handler; per the product skill's preference for simple architecture, the simpler fix was preferred once it was confirmed to actually close the gap, not just paper over it.
**Also closed in the same pass, then superseded by later independent reviews:** Stripe's own documentation does not guarantee webhook delivery order. The original fix compared the incoming event's own `created` timestamp against the last one applied, inside the `UPDATE`'s own `WHERE` clause. **That approach itself had a real bug**, found later: Stripe's `created` field only has one-second resolution, so two genuinely distinct events sharing a timestamp made the second one look "not newer" under the strict `<` comparison and silently lost its state. Replaced entirely with canonical current-state retrieval, later extended to be organization/customer-wide and fenced against out-of-order writers — see "Stripe webhook reconciliation..." near the top of this document for the current design.
**Revisit if:** a future event type needs to *accumulate* state rather than replace a snapshot (e.g. a running counter) — the "always safe to reprocess" property this reordering relies on would need to be re-established for that specific field, since a naive re-application of an accumulating update would double-count on retry.

## R6-06: round 5's `/api/health` fix rested on a false premise about Vercel — corrected with `APP_ENV`

Round 5 (R5-05) fixed a real bug (deciding "is this a deployed environment" from the *runtime* `process.env.VERCEL_ENV`, which a disabled "Automatically expose System Environment Variables" toggle also suppresses) by capturing `VERCEL_ENV` at **build** time instead (`BUILD_VERCEL_ENV`), reasoning that Vercel's build step always has it available regardless of that toggle.
**That reasoning was wrong**, per Vercel's own current documentation (`https://vercel.com/docs/environment-variables/system-environment-variables`, fetched and quoted directly during round 6's investigation rather than trusted from memory): `VERCEL_ENV` is listed as a **System Environment Variable**, and the same "Enable access to System Environment Variables" toggle gates it at **both** build and runtime — there is no build-time carve-out documented anywhere. A project with the toggle disabled would have had `BUILD_VERCEL_ENV` null too, and the health check's old logic fell through to `environment: "development", ok: true` — silently hiding precisely the misconfiguration this endpoint exists to catch, the same failure mode R5-05 believed it had closed.
**Fixed by never depending on any Vercel-managed variable for this decision at all.** `APP_ENV` is an ordinary application environment variable — not a Vercel System Environment Variable — that the repository owner sets directly per Vercel environment (`production`/`preview`); ordinary project environment variables are populated the same way at build and runtime regardless of the system-variable toggle, because they aren't subject to it in the first place. "Is this local development" is decided from `NODE_ENV !== "production"` instead of any Vercel signal either — `next dev` always sets it to `"development"`, `next build`/`next start` (and every real Vercel build) always set it to `"production"`, independent of Vercel entirely.
**Consequence, stated plainly:** until `APP_ENV` is added in Vercel Project Settings (an owner action — `DEPLOYMENT.md` § 3), `/api/health` will report `ok: false`/503 in Production and Preview, not the (possibly incorrectly) healthy state R5-05's version might have reported. This is the fix working as intended — a genuinely unestablished deployment identity is exactly what this endpoint is supposed to fail loudly on — not a regression to roll back.
**Lesson:** the same discipline this project applies to Supabase ("verify against current docs, don't trust training data — it changes frequently") turned out to matter just as much for Vercel's platform behavior. R5-05's fix was never verified against Vercel's actual documentation at the time; it was reasoned from a plausible-sounding assumption about how build tooling "should" work. Round 6 caught it by fetching the docs directly instead of re-deriving the same assumption a second time.

## R6-01/R6-03: revoking the round-3 notification-email RPC's `authenticated` grant immediately, not after a compatibility window

Round-6 finding R6-01 (HIGH) found that `request_notification_email_change()` — in **both** its round-3 (already production-deployed) and round-5 forms — returned the raw confirmation token directly to its `authenticated` caller, letting any org member obtain a live token for an arbitrary address by calling the RPC directly, never proving control of that address's inbox. Round-6 finding R6-03 separately asked, as a general principle, for a versioned/separately-named replacement RPC kept callable alongside the old one during a rollout, so old application code isn't broken by a signature change landing in the same deployment that starts consuming its replacement.
**These two findings pull in different directions for the round-3 function specifically.** A strict reading of R6-03 would keep `request_notification_email_change(bigint, text, int)` fully callable by `authenticated` throughout the deploy window, for compatibility with whatever might still be calling it. But that function's `authenticated`-callable, token-returning behavior **is** the R6-01 vulnerability — there is no way to keep it "compatible" without also keeping it exploitable.
**Chose to revoke `authenticated`'s grant on the round-3 function immediately** (migration `20260906090000`), accepting a brief, deliberate compatibility gap: if old application code somehow still calls it during the short window between this migration landing and new code deploying, it gets a clean "permission denied for function" instead of either a confusing missing-function error or continuing to leak tokens. The function's body and signature are left otherwise intact (not dropped), satisfying R6-03's actual underlying concern — no client-visible signature change, no ambiguous overload resolution, and a future cleanup migration can drop it outright once nothing could still reference it.
**Why this was the right call, not a rationalization:** the two things being weighed are not equally serious. A live, HIGH-severity credential-disclosure bug being reachable for the length of a routine deploy window is worse than a same-length window where one specific, rarely-used settings action (changing the notification-email recipient) returns an error instead of silently succeeding. The new `request_notification_email_change(bigint, text)` (2-argument) function coexists as a distinct overload for new application code from the moment this migration lands — R6-03's actual mechanism (a new, separately-shaped RPC alongside the old one) is followed faithfully for the *safe* parts of this change; only the specific sub-case where "the old behavior is itself the vulnerability" gets the stricter treatment.
**Revisit when:** confident nothing could still be calling the round-3 3-argument signature (one deploy cycle after this PR merges is almost certainly sufficient, given the settings action this backs is a low-frequency, deliberate user action, not a hot path) — at that point, a cleanup migration should drop `request_notification_email_change(bigint, text, int)` outright.
**Superseded by round 7 (R7-03), sooner than expected and for a different reason than staleness.** The "revisit when confident" framing above assumed the eventual cleanup would be a routine, low-urgency chore. Instead, round 7's own drift-repair work (recreating the 3-argument function in the isolated test project to match production, done to close a different gap — R7-03's "a database missing the production object under test is not a genuine security verification") immediately broke every 2-named-argument call to `request_notification_email_change` with `PGRST203`: PostgREST's overload resolution is ambiguous between a 2-argument call and this function (whose third parameter has `default 1440`, making it satisfiable with 2 arguments) **independent of either function's grants** — revoking `authenticated`'s grant (this migration, `20260906090000`) does not resolve the ambiguity, since PostgREST rejects the call as unresolvable before any permission check runs. This means the round-3 function's mere continued *existence*, not just its reachability, was a live correctness bug the moment both overloads coexisted — the "kept defined, ungrantable, for a future cleanup" plan above was itself broken from the day migration 18 shipped, just masked by the isolated test project's own bookkeeping drift never actually exercising that coexistence until round 7. **The cleanup migration this entry deferred to "one deploy cycle later" was written immediately instead** (`20260906100000_drop_ambiguous_request_notification_email_change_overload.sql`), dropping the function outright rather than waiting — see `DATABASE_SCHEMA.md` § "Rollout ordering" for why this also means migration 19's revoke and migration 20's drop both need production's new application code deployed first, correcting an unrelated mistake in round 6's own rollout claim (below).
**Lesson**: "kept defined, ungrantable" was reasoned about purely as a grants/security question (can anything malicious reach it), not as a schema-correctness question (can PostgREST even resolve calls to the function that's supposed to remain reachable, once this one coexists with it) — the second question turned out to matter just as much, and only surfaced once the test environment actually matched production closely enough to exercise it.

## R7-03: a test-environment repair surfaced a real production-shaped bug, and corrected round 6's own rollout claim

Round-6's handoff (quoted in `REVIEW_REQUEST_ROUND8.md`, superseded by round 7's) stated migration `20260906090000` (which revokes the round-3 3-argument `request_notification_email_change`'s `authenticated` grant) "needs no expand/enforce staged mechanism... no existing trigger or column is being newly protected against currently-deployed code." **That was incorrect**, and round 7 caught it only while writing up R7-03's own fix, not because anyone had re-examined the claim directly: production's actual currently-deployed application code (this PR has never merged) still calls the 3-argument RPC to change the notification-email recipient. Revoking its grant — let alone round 7's own new migration 20, which drops the function entirely — before the new 2-argument-calling application code is live would break that live settings action outright, the exact "enforce migration applied before the code that tolerates it" hazard this document's "Rollout ordering" section (and `scripts/rollout.mjs` itself) exists to prevent for every *other* migration in this schema. Both migrations are now correctly classified as `--enforce`, not applied ad hoc "in either order... once this PR is reviewed and merged" as the round-6 handoff had claimed.
**Why this specific mistake is worth naming, not just fixing:** round 6's claim wasn't reckless — it reasoned correctly that the function's *behavior* (leaking a token) was the thing needing to stop, and concluded from that, without a second check, that making it unreachable therefore carried no deployment-ordering risk. That reasoning conflated "this should stop being reachable" (true, and urgent) with "therefore nothing currently depends on it being reachable" (false, and exactly the kind of unverified assumption `DEPLOYMENT.md`'s own opening line — about the original Vercel deployment-gap incident — already warns this project has been burned by once).
**Revisit:** nothing further needed on this specific point; the corrected classification in `DATABASE_SCHEMA.md`/`DEPLOYMENT.md` is the intended final state, not a stepping stone.

## Renamed the new notification-email RPC instead of staging its coexistence with the legacy one — a third review of the same PGRST203 saga

R7-03/R6-01/R6-03 (above) reasoned carefully about *when* the round-3 3-argument `request_notification_email_change` could safely stop being reachable, and correctly classified dropping it as `--enforce` (after new code deploys) rather than `--expand`. **A third independent review found that entire framing was solving the wrong problem**: `DEPLOYMENT.md`'s own documented rollout applied the new 2-argument function (same name) during `prepare` — before the merge — and only dropped the legacy 3-argument one during `finalize`, after deploy and drain. That's not a bounded, carefully-timed risk window; it's a **guaranteed** PGRST203 outage for every caller, old and new code alike, for the entire span between those two steps, since a call naming just `(p_organization_id, p_email)` matches both overloads simultaneously the moment they coexist under one name — independent of grants, independent of which migration ran when. No amount of retiming `--expand`/`--enforce` fixes this; the ambiguity exists the instant both definitions are live together, and `prepare`/`finalize` genuinely need to run at different times (that's the whole point of the split).
**Fixed by making the coexistence question moot: the new function is now named `reserve_notification_email_change`, not `request_notification_email_change`.** Two different names can never collide as PostgREST overloads, at any point in any rollout — this is not a narrower or better-timed staging strategy, it removes the category of bug entirely. The legacy 3-argument function is untouched (still named `request_notification_email_change`, still exactly what `20260906090000`/`20260906100000` revoke and drop as `--enforce`, unchanged from R7-03's own correct reasoning about *that* migration's timing) — only the *new* function needed a different identity, since it's the one being introduced fresh and has no compatibility obligation to any existing name.
**Why edit migrations `20260905193325`/`20260906120000` in place rather than add a corrective migration on top:** both were already established as safe to rewrite in place (`20260905193325`'s own header comment: "this file has never been applied to production... rewritten in place for round 6 rather than patched with a follow-up migration") — neither has ever reached production, so there is no production history to preserve, and a corrective migration layered on top would have left a genuine, if brief, ambiguous-overload window inside this repository's OWN migration sequence between the original (wrong) definition and its correction, exactly the property Finding 1 required eliminated for every prefix of the rollout, not just the final state.
**Verified executably, not just reasoned about**: `e2e/rollout-compatibility-notification-email-rpc.spec.ts` reproduces all three real rollout states (migrations 1–17 baseline; after `prepare`; after `finalize`) plus a negative control proving the same harness would have caught the original bug, against the real isolated project's actual PostgREST layer.
**Lesson, again:** this is the THIRD time this same underlying mechanism (two PostgREST-visible functions with an overlapping callable shape) has produced a real, previously-unnoticed bug in this exact area — R7-03 found the isolated test project's own drift had hidden the first instance; this round found that even the *corrected* rollout timing still guaranteed the outage it was trying to bound. The actual fix, in hindsight, was available from the start and is simpler than any of the staging strategies attempted: never give two coexisting functions overlapping callable shapes under the same name in the first place.

## R7-05: after finding `now()`-after-lock once, searched for the whole class rather than trusting the one fix

Round 6 (R6-04) fixed a real, reproduced concurrency bug in `request_notification_email_change`: `now()` is fixed at transaction *start*, not statement execution, so a transaction queued behind another via `pg_advisory_xact_lock` could resume with real wall-clock time well past its own frozen `now()`, causing a freshness/cooldown check to reflect a stale instant. Round 7's finding R7-05 pointed out `claim_negative_alert_send` had the identical shape (lock → check a time window → write a timestamp, using `now()` throughout) and had simply never been looked at for the same bug, despite living in the same file as several other fixes this project has made.
**Decision:** rather than fix only the one function the finding named, searched every migration/function in the schema for the same pattern (`now()`/`current_timestamp` used after acquiring a lock, or feeding a freshness/window decision) before considering this class of bug closed. Found exactly the two instances above — no others — after checking every other timestamp read in the schema (audit-column defaults, expiry checks with no preceding lock) against the same criteria.
**Why:** this task's own explicit standing instruction ("fix the whole class, not only this function") matches a broader principle this project has hit repeatedly this round — a fix scoped only to the literal finding as stated tends to leave a sibling instance of the identical bug for the next review to find one round later (R7-01 found `redactSpan` incomplete after R6-02 introduced it; R7-03 found the 3-argument function coexistence bug only after R6-01/R6-03 had already reasoned about the same function). Searching for the class immediately, once a specific instance is confirmed, is cheaper than waiting for the next round to find the next instance.
**Revisit if:** a future function is added that acquires an advisory lock and then makes a time-based decision — check it against this same pattern at the time it's written, not retroactively.
**Postscript, from this same round's independent adversarial self-review**: the class-wide search above still missed a third instance, in `request_notification_email_change` itself — the very function whose cooldown/budget *checks* this search was implicitly modeling the pattern on. Its `insert ... reserved_at` relied on the column's `now()` default sitting right next to two correctly-`clock_timestamp()`'d reads, and the search checked "does this function use `now()` after a lock" at the function level, not "does *every* timestamp-producing statement in this function use the captured value, including ones that don't superficially look like a freshness check." Fixed in migration `20260906120000`, confirmed against the isolated project both ways (fails on the pre-fix body, passes on the fix) before being considered complete. **Restated lesson, sharper this time:** a targeted search for "the same bug shape" is not equivalent to verifying every individual statement in the functions it touches — an `INSERT`/`UPDATE` writing a timestamp is exactly as much a candidate as an `IF` checking one, and doesn't announce itself as such.
