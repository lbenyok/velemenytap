Dropping the function outright removes the ambiguity entirely. See "Rollout ordering" below for why this changes the production rollout plan for both migrations 19 and 20 together.
21. `20260906110000_fix_claim_negative_alert_send_clock_timestamp.sql` (round 7, R7-05) — `claim_negative_alert_send()` now captures `clock_timestamp()` once immediately after acquiring its per-organization advisory lock, and reuses that single value for the trailing-hour budget cutoff, the per-card cooldown comparison, the `last_negative_alert_at` write, and the reservation's `reserved_at` timestamp — replacing every use of `now()` (fixed at transaction start) in the function body, the same class of bug round 6 (R6-04) already fixed in `request_notification_email_change`. Same signature (`create or replace`), so this is a safe drop-in with no rollout-compatibility concern, exactly like migration 19's TOCTOU-fix half.
22. `20260906120000_fix_request_notification_email_change_reserved_at_clock_timestamp.sql` — found by this round's own independent adversarial self-review, not one of R7-01 through R7-08 as originally listed. `request_notification_email_change()`'s cooldown/budget *checks* correctly used `clock_timestamp()` since R6-04, but the reservation row it inserts right after never set `reserved_at` explicitly and fell back to the column's `default now()` — the identical bug class as R7-05, missed by that same round's own "search the whole schema" pass (see `SECURITY.md`). Now captures one `clock_timestamp()` value after the advisory lock and reuses it for both the checks and the `insert ... reserved_at`. Same signature, safe drop-in. Verified with a genuine two-connection concurrency test that fails against the pre-fix body and passes against the fix (confirmed both ways against the isolated project before this migration was considered complete).
23. `20260906130000_add_onboarding_tour_status.sql` (**rewritten in place — never applied to production, so safe, the same reasoning as migration 18**; found during an independent review) — `organizations.onboarding_tour_status` (`not_started` | `completed` | `skipped`, CHECK-constrained): server-side persisted state for the first-time dashboard tour (`features/onboarding-tour/`). The original version added the column with `default 'not_started'` and then ran a separate `update ... set onboarding_tour_status = 'completed'` over every existing row — a real DML statement that bumped `updated_at` (via the `organizations_set_updated_at` trigger, migration 1) on every pre-existing organization for a reason unrelated to anything the organization itself changed. Fixed with the standard two-statement pattern instead: add the column with `default 'completed'` first (Postgres 11+ applies a constant `NOT NULL` default as a fast, metadata-only catalog change, not a per-row rewrite — no `UPDATE` ever runs against existing rows, so `updated_at` is never touched for them), then `alter column ... set default 'not_started'` in a second statement in the same migration — a column-default change affects only *future* inserts, never rows that already have a stored value. Net effect verified directly against the isolated project (see § "Onboarding tour state" below): every pre-existing organization reads `'completed'` with `updated_at` unchanged; every organization `create_organization_atomic()` creates after this migration gets `'not_started'` from the column's own default. **Not a safe same-signature drop-in like migrations 19/21/22** — the new dashboard code reads this column on every request, so unlike those, this one must be classified `--expand` (applied *before* the new application code deploys, not after) — see "Rollout ordering" below.
24. `20260907150000_add_organization_billing.sql` — `organization_billing` (one row per organization, Stripe customer/subscription linkage and status) and `stripe_webhook_events` (idempotency ledger for the Stripe webhook handler); `private.provision_organization_trial()` trigger, auto-creating every new organization's `organization_billing` row with a 14-day no-card trial. Originally authored (on the billing feature's own branch) as `20260905125856`, before migrations 18-23 existed — **renamed** to this later timestamp when integrating that branch on top of this PR's final state, since it lands after migrations 18-23 in the actual production rollout order. Renaming (rather than editing in place, as migrations 18/23 above were) was checked, before renaming, against the migration *bookkeeping table* specifically (`supabase migration list` showed it unrecorded there) — **not** against whether its effects had ever actually run, which a later independent review found was a different question: the isolated test project already had a real `organization_billing` table, created out-of-band by an earlier manual `db push` whose result was never recorded in the bookkeeping table at all (see migration 26 below and `STATUS.md` for the full discovery and its fix). Renaming was still safe here specifically because the migration **file's own content had never been edited** — so once the bookkeeping was repaired to match reality, the recorded "applied" migration's SQL genuinely matched what had actually run. A migration whose file content has changed since it last ran must never be renamed this way, only ever corrected in place (if never applied to production) or superseded by a new corrective migration (if it is).
25. `20260907160000_fix_organization_billing_grandfathering_and_event_ordering.sql` — found during an independent review after the billing feature (migration 24) had already been built out end to end: migration 24's provisioning trigger only fires for organizations created after it runs, so every organization that already existed had no `organization_billing` row at all — permanently locking it out of the dashboard (`isBillingActive(null)` is `false`) and, worse, making a checkout attempt create a real Stripe customer that could never be looked up again (the persisting `UPDATE` matched zero rows, unchecked, in the pre-fix `getOrCreateStripeCustomerId`). Both new columns were purely additive — safe to apply at any point, exactly like migration 18.
26. `20260907170000_rename_billing_last_synced_column.sql` — found during a second independent review, while investigating migration 25's out-of-order guard: renames `last_synced_event_created_at` to `last_synced_at`, repurposed as a plain diagnostic timestamp (see migration 27) rather than a correctness gate. Applying this migration set to the isolated test project also surfaced the bookkeeping-vs-reality discrepancy noted in migration 24's own entry above — `organization_billing` already existed there, created out-of-band, unrecorded in `supabase_migrations.schema_migrations` — reconciled with `supabase migration repair --status applied` (bookkeeping-only, never re-running the SQL) before this and the following two migrations were pushed for real. Purely additive (a column rename, no data loss) — safe at any point, exactly like migration 18.
27. `20260907180000_add_billing_activated_at.sql` — `organization_billing.activated_at`: set once, only on an organization's first-ever observed transition to Stripe subscription status `'active'`, never overwritten afterward. Found during the same second independent review: `isBillingActive()` previously switched entirely to trusting Stripe's current status the instant any `stripe_subscription_id` existed at all, so a grandfathered organization whose first Checkout attempt merely went `incomplete` (Stripe's normal pre-payment state) lost its grandfathered access immediately — worse off than before it tried to pay. `activated_at` lets `isBillingActive` (`features/billing/status.ts`) distinguish "a subscription object exists" from "a payment has genuinely ever succeeded," falling back to grandfathering/the trial only in the latter case. See `DECISIONS.md`'s "Billing state machine" entry for the full transition table. Purely additive — safe at any point, exactly like migration 18.
28. `20260907190000_add_billing_pending_checkout_intent.sql` — `organization_billing.pending_checkout_session_id`/`pending_checkout_expires_at`: a database-backed lease per organization, claimed atomically before `createCheckoutSessionAction` (`features/billing/actions.ts`) ever calls Stripe, so a double-submitted form (different intervals, or spaced more than the previous 30-second idempotency-key window apart) can't create two separate Checkout Sessions for the same organization. Found during the same second independent review: the prior 30-second, time-bucketed Stripe idempotency key alone left exactly that gap uncovered. Cleared by the webhook once a subscription genuinely exists (migration 27's `syncSubscription`); otherwise expires on its own. See `DECISIONS.md`'s "Checkout concurrency" entry for the full design. Purely additive — safe at any point, exactly like migration 18.

### Rollout ordering for migrations 12→13 and 16→17

Both pairs follow the same expand/deploy/enforce sequence (round-3 finding R3-05): applying the "enforce" migration (13 or 17) to production at the same time as its "expand" migration (12 or 16) would break the *currently deployed* application code, which still performs a direct `UPDATE` to the column(s) the trigger would then reject — creating a real outage window (every negative-feedback alert, or every settings save touching the notification email, failing) between the migration landing and the new application code deploying. Apply 12/16 first, deploy this PR's application code (which uses the RPCs instead of a direct `UPDATE`), let old instances drain, then apply 13/17. See `DEPLOYMENT.md` § 7 for the concrete, current production rollout command.

**Migration 18 follows the R6-03 principle exactly**: the new `request_notification_email_change(bigint, text)` (2-argument) coexists with the round-3 `request_notification_email_change(bigint, text, int)` as a distinct overload, and every object migration 18 introduces is purely additive (new tables, new functions) — safe to apply before this PR's application code deploys, exactly like any other expand migration.

**Migrations 19 and 20 are where round 7 corrected a real mistake in round 6's own rollout plan, not an intentional exception.** Round 6's original handoff (quoted in `REVIEW_REQUEST_ROUND8.md`, superseded) claimed migration 19 "needs no expand/enforce staged mechanism... no existing trigger or column is being newly protected against currently-deployed code," reasoning that revoking `authenticated`'s grant on the round-3 3-argument function was acceptable to apply immediately because that function's behavior was itself the vulnerability being closed. **That framing missed the actual hazard**: production's *currently-deployed application code* — this PR has not merged yet — still calls the round-3 3-argument signature to change the notification-email recipient, the same as it did the day PR #2 shipped. Revoking that function's grant (migration 19) before the new application code (which calls the 2-argument signature instead) is live would make every "change notification email" settings save on the live site fail immediately with `"permission denied for function"` — a real, self-inflicted production outage for a feature that currently works, not a bounded window where a bypass gets a clean error instead of leaking a token (that framing was correct for the vulnerability itself, but conflated "this behavior should stop being reachable" with "it is therefore safe to make unreachable before anything else changes"). Migration 20 (R7-03's drop) has the identical hazard, one step worse: a live caller of the dropped function gets `PGRST202` ("could not find the function") instead of merely a permission error.

**Corrected rollout order, following the same expand → deploy → enforce sequence as migrations 12→13 and 16→17 above:**
1. Apply migration 18 (purely additive) and migration 21 (a same-signature `create or replace` bug fix — see below) — both safe before the application code deploys.
2. Merge and deploy this PR's application code, which calls the 2-argument `request_notification_email_change` and never the 3-argument one.
3. Let old serverless instances drain (the same reasoning as every other enforce migration in this document).
4. Apply migration 19 (revoke the 3-argument function's grant + the unrelated `confirm_notification_email_change` TOCTOU fix bundled into the same file) and migration 20 (drop the 3-argument function outright) — safe now that nothing still calls it.

**Migration 21 is a safe drop-in, not part of the enforce step**, despite being new this round: `claim_negative_alert_send()`'s signature is unchanged (`create or replace function` only), so — like migration 19's TOCTOU-fix half — it can be applied at any point without a compatibility window; it is grouped with the expand step above only because doing so early is simplest, not because it must wait.

**Migrations 23 through 28 (`onboarding_tour_status`; `organization_billing`/`stripe_webhook_events` and their grandfathering/event-ordering/rename/`activated_at`/checkout-lease columns) are all `--expand`, but for the opposite reason migrations 19/20 are `--enforce`.** Migrations 19/20 protect *old* code's dependency on something being removed (apply only after new code no longer needs it). Migrations 23-28 are the mirror case: *new* code depends on something being added — the dashboard layout queries `organizations.onboarding_tour_status` on every request to decide whether to show the tour (23); `app/dashboard/layout.tsx`'s paywall queries `organization_billing`, including `grandfathered_at` (24, 25) and `activated_at` (27), on every non-billing dashboard request; the webhook handler writes `last_synced_at` (26) on every Stripe event it processes; and `createCheckoutSessionAction` reads/writes the checkout lease columns (28) on every checkout attempt. Deploying this PR's application code before any of these six applies would make the corresponding request fail with a missing-relation or missing-column error — not a graceful fallback, since the object doesn't exist for the query to even run. So all six must land in the expand phase, before the code deploy, exactly like migrations 18/21/22. See `DEPLOYMENT.md` § 7 for where this fits in the corrected `scripts/rollout.mjs` invocation.

See `DEPLOYMENT.md` § 7 for the corrected `scripts/rollout.mjs` invocation reflecting this order, and `SECURITY.md` § "The isolated test project's own migration history had drifted" (R7-03) for how recreating the 3-argument function to match production is what surfaced the `PGRST203` ambiguity that made migration 20 necessary in the first place.

Never hand-edit the production schema outside a migration file (see `supabase` skill's Database Change Workflow). To change the schema: inspect current state → write a migration → preserve existing data → define FKs/constraints/RLS/indexes → update `database.types.ts` → update application code → verify authorized, unauthorized, and cross-tenant access.

## Tables

### `organizations`

| Column | Type | Notes |
|---|---|---|
| `id` | bigint identity | PK |
| `name` | text | not blank |
| `slug` | text | unique, not blank |
| `settings` | jsonb | default `{}`, unused today |
| `notification_email` | text | nullable; overrides per-member alert routing when set (§ Notifications). **Verified only** — round-3 R3-03: only ever set by `confirm_notification_email_change()`, never written directly. |
| `notification_email_pending` | text | nullable; a candidate address awaiting confirmation (R3-03). Overwritten outright by a new request; no history kept. |

| `logo_url` | text | nullable; pasted URL, no upload UI (see `DECISIONS.md`) |
| `onboarding_tour_status` | text | `not_started` (default) \| `completed` \| `skipped`, CHECK-constrained. First-time dashboard tour state — migration 23, see below. |
| `created_at`, `updated_at` | timestamptz | |

#### Onboarding tour state (migration 23)

`onboarding_tour_status` gates whether `features/onboarding-tour/`'s welcome dialog + step-by-step tour auto-opens on dashboard load. Scoped to the **organization**, not the member who happens to trigger it — deliberately: the tour is about whether *this business* has been introduced to the product (and nudges toward "create your first location"), not about one person's individual familiarity with it. If a future invite flow ships (no membership other than `owner` can exist yet — see `DECISIONS.md`), a newly-invited teammate joining an already-configured organization must not be told to create a first location that already exists; per-user scoping would get this wrong.

No new RPC: this column isn't one of the ones `private.prevent_direct_notification_email_change` protects, so the existing `organizations_update` RLS policy (any member of the org, `private.is_org_member(id)`) already covers writing it — `features/onboarding-tour/actions.ts`'s `setOnboardingTourStatusAction` is a plain `.update()` through the ordinary RLS-bound client, the same pattern `settings-actions.ts` already uses for `name`/`logo_url`. The CHECK constraint is what actually enforces the three-value state model, not application code.

**Existing organizations are protected from seeing the tour unexpectedly, without a bulk `UPDATE`**: migration 23 adds the column with `default 'completed'` first (every row that already exists reads `'completed'` immediately, for free, as the column's own default — no separate write touches them, so `updated_at` is never bumped for a reason unrelated to anything the organization changed), then a second `alter column ... set default 'not_started'` changes only what a *future* insert receives. Every organization `create_organization_atomic()` creates after this migration applies gets `'not_started'` from the column's new default, from its plain `insert into organizations (name, slug)` (no explicit value needed). Verified directly against the isolated project after this migration was rewritten: `information_schema.columns` shows the live default is `'not_started'::text`, the CHECK constraint is unchanged, and a pre-existing sample organization already reads `'completed'`.

### `organization_memberships`

Connects `auth.users` to `organizations`. `role` ∈ `{owner, admin, manager, staff}` (only `owner` is ever assigned today — no invite flow exists). Unique on `(organization_id, user_id)`.

### `locations`

Belongs to one organization. `google_review_url` is nullable — a location can operate before its Google Review link is configured (the public page handles a missing URL gracefully, never fabricating one). `status` ∈ `{active, inactive}`.

### `nfc_cards`

Belongs to one location (and, denormalized, one organization) — **immutably**: `location_id` cannot be changed after creation (`private.prevent_nfc_card_location_change`, migration 5). A business that physically moves a card should deactivate it and issue a new one at the new location, not relocate the existing one; see that migration's comment for why (one card mapping to two locations over its lifetime breaks per-card analytics and the product's own card model). This is also enforced in the dashboard UI, not just the database (round 2, R2-09): the edit form shows an existing card's location as read-only text and `updateNfcCardAction`'s schema has no `location_id` field at all — the create form's editable dropdown remains for new cards. `public_id` is a random UUID, not the internal `id` — this is what appears in the public URL (`/r/{public_id}`), so internal sequential IDs are never exposed. `status` ∈ `{active, inactive}`; an inactive card's public page refuses new submissions. `last_negative_alert_at` — the negative-feedback alert cooldown timestamp. This column can **only** be changed by `claim_negative_alert_send()` — a trigger (`private.prevent_direct_cooldown_update`, installed by migration 13, deliberately separate from the migration that introduces the RPC — see "Rollout ordering" above) rejects any other `UPDATE` to it, from any role, including the admin client itself.

### `private.alert_email_log`

Added in migration 12 (round 2, R2-08; **revised in round 3** for R3-06). Each row is a *reservation/attempt*, not an unconditional record of a send: `organization_id`, `nfc_card_id`, `status` (`reserved` → `delivered` or `failed`, set by `finalize_negative_alert_send()`), `reserved_at`, `delivered_at`, `failed_at`. Not exposed to PostgREST (lives in the non-exposed `private` schema, RLS enabled as of migration 15 though moot given no `anon`/`authenticated` grant exists either way); only `service_role` has `select`/`insert`/`update` on it (see § Row Level Security). Backs `claim_negative_alert_send()`'s organization-wide hourly budget — indexed on `(organization_id, reserved_at)` — counting `reserved`+`delivered` rows within the trailing hour but excluding `failed` ones, so a transient delivery failure doesn't permanently consume budget the org never actually used (see the migration's comment for the exact reasoning, including why a crashed/never-finalized reservation is an accepted, bounded worst case rather than something actively cleaned up).

### `private.notification_email_change_log` / `private.notification_email_change_config`

Added in migration 18 (round 5, R5-12; rewritten round 6, R6-01/R6-04). `notification_email_change_log` mirrors `private.alert_email_log`'s reservation/attempt shape (`organization_id`, `status` `reserved`→`delivered`/`failed`, `reserved_at`/`delivered_at`/`failed_at`) for notification-email change requests; `select`/`update` granted to `service_role` only (read by `issue_notification_email_change_token()`/`finalize_notification_email_change_send()`, both `SECURITY INVOKER` — see below). `notification_email_change_config` holds the cooldown/hourly-budget values `request_notification_email_change()` enforces, keyed **per organization** rather than a single global row (round-6 R6-04's own comment explains why: a shared global would make any test tuning it race every other concurrently-running test exercising the same RPC under normal defaults) — no row means the function falls back to its built-in defaults (5 minutes / 5 per hour). `service_role` has `select`/`insert`/`update`/`delete` on it, used by tests to seed a per-organization override; nothing grants `authenticated` any access to either table, by design — the whole point of R6-04 was to stop the rate limit being tunable by the party it constrains.

### `feedback`

Belongs to one org/location/nfc_card (all three denormalized for RLS and query performance — see consistency triggers below), and **immutably** once inserted: `organization_id`/`location_id`/`nfc_card_id`/`rating`/`feedback_text`/`created_at` cannot be changed by any `UPDATE`, from any role including a future admin-client bug (`private.prevent_feedback_content_change`, migration 4). Only `status` and `internal_note` are editable after submission — RLS alone only enforces *row* ownership, not *column* restriction, so this trigger is what actually stops an org member from rewriting a customer's original rating or written feedback. `rating` constrained `1..5` at the database level. `feedback_text` nullable, ≤ 1000 chars (validated in the Server Action; DB constraint caps at 5000 as a hard backstop). `status` ∈ `{new, in_progress, resolved}`. `internal_note` — dashboard-only, never shown to the customer. `priority` — **generated column**, `high` (rating ≤ 2) / `medium` (rating = 3) / `normal` (rating ≥ 4), always derived from `rating` and never independently writable.

### `profiles`

One row per `auth.users` row, auto-created by the `on_auth_user_created` trigger. Currently holds only `full_name`; nothing in the app reads it yet (the dashboard header shows the org name, not the user's name). Added ahead of need because retrofitting after real users exist is more disruptive than creating it empty.

### `organization_billing`

Added in migration 18. One row per organization (`organization_id` is both the PK and the FK), auto-created by `private.provision_organization_trial()` (an `after insert on organizations` trigger) the instant an organization is created — every organization, no exceptions, starts on a 14-day no-card trial. `stripe_customer_id`/`stripe_subscription_id` — nullable, populated on first checkout. `status` — mirrors Stripe's own `Subscription.status` enum exactly (`trialing`, `active`, `past_due`, `canceled`, `incomplete`, `incomplete_expired`, `unpaid`, `paused`), defaulting to `trialing`; kept exhaustive on purpose so the webhook handler's `UPDATE` can never fail on a status Stripe itself considers valid (see `app/api/webhooks/stripe/route.ts`'s `toBillingStatus`, which maps anything Stripe adds later to `incomplete` rather than crashing). `trial_ends_at` — only meaningful while `stripe_subscription_id` is still null (this app's own pre-signup trial); once a subscription exists, Stripe's `status` is authoritative and this column is ignored (`features/billing/status.ts`'s `isBillingActive`). `current_period_end`/`cancel_at_period_end` — kept in sync from the Stripe subscription object on every webhook event, shown on the billing page. Only `service_role` (the webhook handler and the checkout/portal Server Actions, both via the admin client) ever writes to this table — see § Row Level Security.

### `stripe_webhook_events`

Added in migration 18. `id` (the Stripe event id, e.g. `evt_...`) as the primary key, `created_at`. Purely an idempotency ledger: the webhook handler inserts the incoming event's id before doing anything else; a unique-violation on that insert means a duplicate delivery (Stripe explicitly documents at-least-once, possibly-repeated delivery) and the handler stops there instead of reapplying the event. No RLS policies at all, not even `select` — nothing but `service_role` (which bypasses RLS) ever needs to touch it.

## Indexes

Every FK column used in an RLS predicate is indexed (`organization_id` on memberships/locations/nfc_cards/feedback; `location_id`/`nfc_card_id` where used as join keys). `feedback (organization_id, created_at desc, id desc)` backs the newest-first inbox and its compound cursor pagination (migration 7 — `id` is a required tiebreaker, since `created_at` alone can tie between rows and a page boundary landing inside a tied group would otherwise silently skip whichever of them wasn't on the earlier page); `feedback (organization_id, status)` backs unresolved filtering; `feedback (organization_id, priority)` backs "unresolved high-priority first" queries.

## Data-integrity triggers (defense beyond RLS)

- `private.set_updated_at()` — generic `updated_at` bump, on every tenant-owned table.
- `private.prevent_organization_id_change()` — blocks `UPDATE`s that move a row from one org to another (relevant for a user who belongs to more than one org: without this, an `UPDATE ... WITH CHECK` policy alone could allow moving a row between two orgs the same user belongs to).
- `private.validate_nfc_card_organization()` — on `nfc_cards` insert/update, checks `organization_id` actually matches the referenced `location_id`'s organization. Without this, a member could construct an `nfc_card` whose `organization_id` passes RLS but whose `location_id` points at a different org's location.
- `private.validate_feedback_consistency()` — same idea for `feedback`: `organization_id`/`location_id` must match the referenced `nfc_card`'s own org/location.
- `private.prevent_feedback_content_change()` (migration 4) — blocks `UPDATE`s to `feedback`'s customer-authored/origin columns; only `status`/`internal_note` may change. RLS's row-level `feedback_update` policy alone permits rewriting any column, so this is the actual column-level restriction, not the RLS policy.
- `private.prevent_nfc_card_location_change()` (migration 5) — blocks any `UPDATE` that changes an `nfc_card`'s `location_id`.
- `private.prevent_direct_cooldown_update()` (migration 13) — blocks any `UPDATE` that changes `nfc_cards.last_negative_alert_at` unless a transaction-local flag (`app.allow_cooldown_update`) is set, which only `claim_negative_alert_send()` ever sets. Same pattern as the two triggers above (a column RLS's row-level policies cannot restrict), applied to a column no legitimate dashboard action ever needs to touch directly, rather than one legitimate actions need to touch selectively.
- `private.prevent_direct_notification_email_change()` (migration 17, round 3 R3-03) — blocks any `UPDATE` that changes `organizations.notification_email`/`notification_email_pending`/`notification_email_pending_token_hash`/`notification_email_pending_expires_at` unless a transaction-local flag (`app.allow_notification_email_change`) is set, which only `request_notification_email_change()`/`clear_notification_email()`/`confirm_notification_email_change()` ever set. Without this, a member could set the pending token hash to one they chose themselves and "confirm" an address without ever proving inbox possession — defeating the entire point of the confirmation flow.
- `private.provision_organization_trial()` (migration 18) — not a *restriction* trigger like the others above, but the same "must happen no matter which code path inserts the parent row" reasoning: `after insert on organizations`, creates that organization's `organization_billing` row with a 14-day trial. Runs under whatever privilege inserted the `organizations` row in the first place (`create_organization_atomic`'s `SECURITY DEFINER` context, or the admin client's `service_role`) — there is no path that creates an organization without also, atomically, provisioning its trial.

These exist because `organization_id`/`location_id` are denormalized (duplicated) rather than purely derived through joins; the triggers are what keeps the duplication from silently drifting and corrupting the tenant boundary — plus, for the last two, enforcing invariants RLS structurally cannot express (RLS is row-scoped, not column-scoped, and has no notion of "immutable after insert").

## Row Level Security

RLS is enabled on every table in `public`. Policy shape, uniformly: `to authenticated using (private.is_org_member(organization_id))`, with a matching `with check` on `insert`/`update` policies. `private.is_org_member()` is `SECURITY DEFINER` (needed to read `organization_memberships` without recursively triggering that table's own RLS) but is narrowly scoped: `stable`, `set search_path = ''`, takes one argument, checks `auth.uid()` internally, lives in the non-exposed `private` schema, and its `EXECUTE` grant is revoked from `public` and re-granted only to `authenticated`.

No table has an `anon`/`authenticated` **insert** policy for `organizations`, `organization_memberships`, or `feedback`. Those writes happen through two different, deliberate bypass mechanisms — see `SECURITY.md` § "The deliberate RLS bypasses" for the full accounting and the security reasoning behind each: the secret-key admin client (server-only, used by public feedback submission, public card lookup, and negative-feedback alerts), and the `SECURITY DEFINER`/`SECURITY INVOKER` database functions below that replace what used to be plain multi-step admin-client inserts with a single atomic, validated operation.

`profiles` follows the standard "own row only" pattern: `select`/`update` `using (auth.uid()) = id)`, no policy lets a user read another user's profile.

`private.alert_email_log` (migration 12, RLS enabled by migration 15 — round 3 R3-07) has no policies for `anon`/`authenticated` at all — the schema itself isn't exposed to PostgREST, and only `service_role` (via explicit `grant usage on schema private to service_role; grant select, insert, update on private.alert_email_log to service_role;`) can read or write it. `service_role`'s `bypassrls` does not substitute for these grants — RLS bypass and schema/table `GRANT`s are separate privilege types, confirmed the hard way when the migration was first applied without them and `claim_negative_alert_send` failed with "permission denied for schema private" even though its caller was `service_role`.

`organization_billing` (migration 18) has a `select` policy for members (`private.is_org_member(organization_id)`, so the billing page can render it) but **no `insert`/`update`/`delete` policy for `authenticated` at all** — deliberately: an owner must never be able to grant their own organization an active subscription by writing to this table directly, only Stripe's webhook (via signature-verified events) and this app's own admin-client code (creating the Stripe customer, linking `stripe_customer_id`) can. `stripe_webhook_events` (migration 18) has RLS enabled with zero policies of any kind, for any role — not even `authenticated` `select` — since nothing but `service_role` ever needs to touch it.

## Database functions callable as RPCs

Beyond `private.is_org_member` (used only from within RLS policy evaluation, never called directly), eleven functions in `public` are meant to be invoked as PostgREST RPCs. This was twelve through round 6 — the round-3 `request_notification_email_change(bigint, text, int)` was kept defined but ungrantable to any client-reachable role (round 6, R6-01/R6-03) — until round 7 (R7-03) dropped it outright after discovering that keeping it defined at all created a `PGRST203` overload-resolution ambiguity against the 2-argument replacement for any 2-named-argument call, independent of grants (see "Rollout ordering" above). `e2e/rpc-privilege-matrix.spec.ts`'s completeness test (round-5 R5-10) queries `pg_proc`/`pg_namespace` directly and fails if this count or list ever drifts from the real catalog — treat that test, not this document, as the authoritative count when the two disagree.

- **`submit_feedback_atomic(p_public_id, p_rating, p_feedback_text)`** (migration 6, relocked in migration 11) — `SECURITY INVOKER`. Locks **both** the target card and location rows (`for update of c, l`), atomically re-checks card/location active status and a per-card submission-rate limit (20 per 5 minutes), then inserts the feedback row. Migration 6 closed the check-then-insert race the old two-round-trip flow had for the card; round 2 (R2-05) found the location row was never locked — a location deactivated mid-transaction could still receive an insert — and migration 11 extended the same `SELECT ... FOR UPDATE` to cover it. `EXECUTE` is restricted to `service_role` only (see the role-allowlist table below); `SECURITY INVOKER` (not `DEFINER`) because its only caller, the admin client, already bypasses RLS at the connection-role level, so there's no privilege this function needs beyond what its caller already has.
- **`create_organization_atomic(p_name)`** (migration 8) — `SECURITY DEFINER`, unlike most other functions in this schema, because it must be callable directly by an authenticated user's own session to bootstrap their first organization, and there is deliberately no `INSERT` policy on `organizations`/`organization_memberships` for `authenticated` to invoke through otherwise. Idempotent (returns the caller's existing organization if they already have one) and serialized per user via `pg_advisory_xact_lock`. Mitigations for the `DEFINER` privilege: an explicit `auth.uid()` check as the first statement, `set search_path = ''`, and an explicit role allowlist (below).
- **`get_feedback_overview_snapshot(p_organization_id)`** (migration 9, round 2 R2-02/R2-03/R2-04) / **`get_feedback_period_analytics(p_organization_id, p_days)`** (migration 9, revised by migration 14 for R3-04 — signature changed, `p_since` removed) — both `SECURITY INVOKER`, `stable`. Called through the dashboard's own RLS-bound client (not the admin client), so RLS applies to every table they touch exactly as it would to a hand-written query. Each computes its entire result — totals, rating distribution, daily series, per-location/per-card breakdowns — as `jsonb` inside one statement built on a single shared `base` CTE, so every number in one call reflects one consistent MVCC snapshot; see `SECURITY.md` § "Analytics correctness" for the full consistency semantics. `get_feedback_period_analytics` additionally validates `p_days` against an explicit allowlist (7/30/90 — the only values the UI ever sends) before doing anything else, raising immediately rather than passing a caller-controlled value into `generate_series` (round-3 R3-04: an arbitrary `p_days` — huge, negative, zero — forced an unbounded or malformed series); `p_since` is derived internally from the now-validated `p_days` rather than trusted as a redundant caller-supplied value.
- **`claim_negative_alert_send(p_nfc_card_id, p_cooldown_minutes default 5, p_org_hourly_budget default 30)`** (migration 12, revised by the same file in round 3 for R3-02/R3-06; revised again by migration 21 for round 7's R7-05) — `SECURITY INVOKER`, same reasoning as `submit_feedback_atomic` (only caller is the admin client). Serializes per organization via `pg_advisory_xact_lock(hashtext('claim_negative_alert_send:' || org_id))` before checking the organization's trailing-hour reservation count against `private.alert_email_log` (round-3 R3-02: without this lock, two concurrent claims for two *different* cards in the same org never contend on any shared row lock, so both could read the same "under budget" snapshot and both succeed, overshooting the budget), then atomically claims the per-card cooldown via a flagged `UPDATE` and inserts a `'reserved'` log row. Returns the new log row's `bigint` id (or `null` if nothing was claimed) — **not** a boolean, and **not** a record of a send (round-3 R3-06) — see `finalize_negative_alert_send` below. **Round 7 (R7-05)**: every freshness/window check in the function body (the budget cutoff, the cooldown comparison) and every timestamp it writes (`last_negative_alert_at`, `reserved_at`) now reuse one `clock_timestamp()` value captured immediately after the advisory lock is acquired, rather than `now()` (fixed at transaction start) — the same class of bug round 6 (R6-04) fixed in `request_notification_email_change`, found here by searching the rest of the schema for the same pattern after fixing it there.
- **`finalize_negative_alert_send(p_log_id, p_delivered)`** (migration 12, round 3 R3-06) — `SECURITY INVOKER`, same caller as `claim_negative_alert_send`. Reports the real outcome of a reservation: sets its `status` to `'delivered'` or `'failed'` with the matching timestamp. `where status = 'reserved'` in its `UPDATE` makes a duplicate/retried call a silent no-op rather than a real transition — called exactly once per successful claim, from a `finally` block in `features/notifications/negative-feedback-alert.ts`, so every reservation eventually resolves.
- **`request_notification_email_change(p_organization_id, p_email)`** (migration 16, round 3 R3-03; rewritten migration 18, round 6 R6-01/R6-04) — `SECURITY DEFINER`, same reasoning as `create_organization_atomic` (must run as the calling member's own session; explicit `auth.uid()` + membership check inside). Validates and rate-limits (cooldown/budget read from `private.notification_email_change_config`, keyed per organization — round-6 R6-04, since the round-5 version's `p_cooldown_minutes`/`p_org_hourly_budget` were plain caller-suppliable arguments an `authenticated` caller could simply override to disable its own rate limit), then reserves a `'reserved'` row and records the candidate address as pending. Returns only a `bigint` **log id** — round 6 (R6-01) removed the token entirely from this function's return value; see `issue_notification_email_change_token` below for why. Overwrites any existing pending request outright.
- **`issue_notification_email_change_token(p_log_id, p_expires_in_minutes default 1440)`** (migration 18, round 6 R6-01) — `SECURITY INVOKER`, `EXECUTE` granted to `service_role` **only** (never `authenticated`, never `anon`). The only function that ever generates or sees the plaintext confirmation token: validates the log row is a known, still-`'reserved'` request, mints a random 32-byte token (`pgcrypto`'s `gen_random_bytes`), stores only its SHA-256 hash plus an expiry against that reservation's organization, and returns the raw token once. Callable exclusively from trusted server code via the admin client (`features/organizations/settings-actions.ts`, immediately after `request_notification_email_change` succeeds) — no browser or ordinary authenticated Supabase client can reach it or obtain a token through it, closing the exact gap R6-01 found in every prior version of `request_notification_email_change` itself (both round 3's and round 5's — see `SECURITY.md` § "The token was never actually protected").
- **`finalize_notification_email_change_send(p_log_id, p_delivered)`** (migration 18, round 5 R5-12; rewritten round 6 R6-04) — `SECURITY INVOKER` (was `DEFINER` through round 5, when its caller was the authenticated user's own session; round 6 made it `service_role`-only, so the caller — the admin client — already has, via explicit grants, everything the `DEFINER` privilege used to provide, and the `auth.uid()`+membership ownership check that used to authorize an arbitrary authenticated caller is no longer meaningful or present). Reports whether a reserved notification-email-change request's send actually succeeded, the same `reserved`/`delivered`/`failed` pattern as `finalize_negative_alert_send`, so a failed send doesn't permanently consume budget it never used. Round 5 originally made this callable by `authenticated` with a caller-supplied `p_delivered` result; round-6 finding R6-04 closed that — a client can no longer mark its own reservation delivered or failed at all.
- **`clear_notification_email(p_organization_id)`** (migration 16, round 3 R3-03) — `SECURITY DEFINER`, same membership check. Needs no token/confirmation — removing a recipient can't be abused to send email anywhere, unlike adding one.
- **`confirm_notification_email_change(p_token)`** (migration 16, round 3 R3-03; TOCTOU fixed migration 19, round 6 R6-05) — `SECURITY INVOKER`, called via the admin client from the public `app/api/notification-email/confirm` route (no `auth.uid()` to check — whoever clicks the email link may not be signed in to this app at all, the same as `/auth/confirm`). A single atomic conditional `UPDATE` (its `WHERE` clause re-checks the token hash, expiry, and pending-address presence, using `RETURNING` to learn whether anything matched) promotes `notification_email_pending` to `notification_email` and clears the pending fields only when a token whose hash matches a still-pending, non-expired request is given. Returns the confirmed organization's `bigint` id, or `null` if the token is unknown, already used, or expired. Round 6 (R6-05) found the round-3 version SELECTed the matching organization, then separately UPDATEd it by `id` alone with no re-check of the token — a concurrent `request_notification_email_change()` call for the same org, landing between those two statements, could replace the pending address/token before the UPDATE ran, which then blindly promoted the *new* address using the *old* token's authority. Collapsing both steps into one statement removes the window a concurrent write could land in.

The round-3 original 3-argument `request_notification_email_change(p_organization_id, p_email, p_expires_in_minutes default 1440)` (migration 16) is **no longer defined at all** as of migration 20 (round 7, R7-03) — dropped outright, not merely stripped of grants as migration 19 (round 6, R6-01) had left it. See "Rollout ordering" above for the `PGRST203` overload-ambiguity discovery that made an outright drop necessary, and for why production must have this PR's new application code deployed before this migration is applied.

### RPC role allowlists (round 2, R2-07; extended round 3, R3-07; extended round 5, R5-10/R5-12; extended round 6, R6-01/R6-04)

`revoke execute on function ... from public;` alone does **not** remove `anon`/`authenticated`'s ability to call a function on this project — this project's `ALTER DEFAULT PRIVILEGES` configuration grants `EXECUTE` on every new `public`-schema function directly to `anon`/`authenticated`/`service_role` as independent ACL entries, unaffected by a `PUBLIC`-only revoke. Round 3 (R3-07) found this had also been missed for `get_feedback_overview_snapshot` specifically (it retained an unintended `service_role` grant despite being documented as `authenticated`-only) — every RPC's role allowlist is now explicit and verified directly, not just declared:

|---|---|---|

| `create_organization_atomic` | `public`, `anon`, `service_role` | `authenticated` |
| `get_feedback_overview_snapshot` | `public`, `anon`, `service_role` | `authenticated` |
| `get_feedback_period_analytics` | `public`, `anon`, `service_role` | `authenticated` |
| `claim_negative_alert_send` | `public`, `anon`, `authenticated` | `service_role` |
| `finalize_negative_alert_send` | `public`, `anon`, `authenticated` | `service_role` |
| `request_notification_email_change(bigint, text)` | `public`, `anon`, `service_role` | `authenticated` |
| `issue_notification_email_change_token` (round 6, R6-01) | `public`, `anon`, `authenticated` | `service_role` |

Round 7 (R7-03) dropped that function outright (migration 20) after its grant-revocation-only state (migration 19, round 6 R6-01) turned out to still leave a `PGRST203` overload-ambiguity hazard against the 2-argument replacement — see "Rollout ordering" above — so it no longer needs a row here at all: eleven functions, eleven rows, verified equal by the completeness test.

Verified with `has_function_privilege()` for every role/function pair (`e2e/rpc-privilege-matrix.spec.ts`, round-3 R3-07 — committed as an automated test, not just checked by hand during development), plus a direct scan of `pg_proc.proacl` for a lingering `PUBLIC` grant, and with real calls as `anon`/`authenticated`/`service_role` elsewhere in the suite — not the grant-inspection check alone.

## Types

`lib/supabase/database.types.ts` is hand-written (no local Docker environment for `supabase gen types`) and updated by hand alongside every migration. `feedback.priority` is typed on `Row` only, not `Insert`/`Update`, since Postgres computes it and the app must never attempt to set it directly. `get_feedback_overview_snapshot`/`get_feedback_period_analytics` are typed with `Returns: Json` (they return `jsonb`) — `features/analytics/parse-snapshots.ts` is the one place that parses that `Json` into the app's actual typed shapes, discriminating an error/null result into `{ unavailable: true }` rather than trusting the shape blindly. `claim_negative_alert_send` is typed `Returns: number | null` (round-3 R3-06 — a reservation id, not a boolean); `finalize_negative_alert_send` is `Returns: undefined`. `clear_notification_email`/`confirm_notification_email_change` (round-3 R3-03) are typed `Returns: undefined` and `number | null` respectively. `request_notification_email_change` is now `Returns: number` (a log id, not the token — round-6 R6-01), `issue_notification_email_change_token` (new, round-6 R6-01) is `Returns: string`, and `finalize_notification_email_change_send` is `Returns: undefined` (unchanged type, though its grant moved to `service_role` — round-6 R6-04). The round-3 3-argument `request_notification_email_change` overload has no corresponding type entry and, as of round 7 (R7-03), no longer exists in the database either — dropped outright (migration 20), not merely unreachable.
