3. **`setOnboardingTourStatusAction` treated every zero-affected-row UPDATE result as success**, on the assumption that the WHERE clause's own "already completed" guard was the only way to get zero rows. It isn't: a membership revoked between the organization lookup and the UPDATE (RLS no longer permitting the write) produces the same zero-row result, and is a real failure, not a no-op — previously reported as success regardless, so the client would close the tour having persisted nothing. Fixed: a zero-row result now triggers a follow-up read of the row through the same RLS-bound client; only a confirmed `"completed"` value is treated as success, everything else (unreadable, gone, or readable-but-not-completed) returns the normal error.
