23. `20260906130000_add_onboarding_tour_status.sql` (**rewritten in place — never applied to production, so safe, the same reasoning as migration 18**; found during an independent review) — `organizations.onboarding_tour_status` (`not_started` | `completed` | `skipped`, CHECK-constrained): server-side persisted state for the first-time dashboard tour (`features/onboarding-tour/`). The original version added the column with `default 'not_started'` and then ran a separate `update ... set onboarding_tour_status = 'completed'` over every existing row — a real DML statement that bumped `updated_at` (via the `organizations_set_updated_at` trigger, migration 1) on every pre-existing organization for a reason unrelated to anything the organization itself changed. Fixed with the standard two-statement pattern instead: add the column with `default 'completed'` first (Postgres 11+ applies a constant `NOT NULL` default as a fast, metadata-only catalog change, not a per-row rewrite — no `UPDATE` ever runs against existing rows, so `updated_at` is never touched for them), then `alter column ... set default 'not_started'` in a second statement in the same migration — a column-default change affects only *future* inserts, never rows that already have a stored value. Net effect verified directly against the isolated project (see § "Onboarding tour state" below): every pre-existing organization reads `'completed'` with `updated_at` unchanged; every organization `create_organization_atomic()` creates after this migration gets `'not_started'` from the column's own default. **Not a safe same-signature drop-in like migrations 19/21/22** — the new dashboard code reads this column on every request, so unlike those, this one must be classified `--expand` (applied *before* the new application code deploys, not after) — see "Rollout ordering" below.

30. `20260907210000_fix_checkout_attempt_race_and_reconciliation_lease.sql` — fourth independent review, Findings 1/3/4/7/9. Migration 29 has already been applied to the isolated test project (unlike migrations 18/23, which were rewritten in place specifically because they never had been — see those entries above), so this is a genuine forward-fixing migration, not an in-place rewrite: it `alter table ... drop column`s `billing_sync_seq` and `drop function`s `claim_billing_sync(bigint)` outright, and `create or replace`s `claim_checkout_attempt()` (same name/signature, so every existing caller keeps working unchanged) rather than superseding it under a new name.
    - **Finding 1 (the `claim_checkout_attempt` bug):** the migration-29 version's "mint a fresh attempt" branch updated `checkout_attempt_interval`/`checkout_attempt_price_id`/`checkout_attempt_mode` to the new request's values but left `pending_checkout_session_id` untouched — so a fresh attempt's row could end up pairing new plan metadata with a session id that actually belonged to the *previous*, superseded attempt, and a subsequent reader trusting that pairing could hand back the wrong plan's Checkout URL. Fixed by clearing `pending_checkout_session_id = null` in the same `UPDATE` that mints the fresh attempt, so the row can never again pair stale-session/fresh-metadata. `features/billing/actions.ts` also independently verifies a reused session's own actual Stripe-side price via its line items before ever reusing it, as defense in depth on top of this fix, not a replacement for it.
    - **Finding 3 (replaces `billing_sync_seq` entirely):** an independent adversarial review demonstrated the prior fencing-token design was invalid in principle, not merely improvable — a request that claims an earlier sequence number can still execute, and observe genuinely fresher Stripe state, *after* a request that claimed a later sequence number has already written, and claim-order fencing discards that fresher read purely because of claim order, with nothing left to ever correct it. Replaced with an exclusive, expiring, durable **reconciliation lease** on `organization_billing`: four new columns, `reconciliation_lease_owner` (text), `reconciliation_lease_expires_at` (timestamptz), `needs_reconciliation` (boolean, default `false`), `reconciliation_dirty_since` (timestamptz), plus a partial index (`organization_billing_needs_reconciliation_idx ... where needs_reconciliation`) backing the scheduled sweep's own scan. `claim_reconciliation_lease()` row-locks the organization (`for update`) and either mints a fresh opaque owner token (`encode(extensions.gen_random_bytes(16),'hex')`) with an expiry, or — if a live lease is already held by someone else — durably marks `needs_reconciliation = true` and returns `null`. Only one reconciler can ever hold an organization's lease at a time, claimed *before* any Stripe network call, so there is no window where two readers observe Stripe state concurrently and race to write at all — mutual exclusion, not fencing after the fact.
    - **Finding 4 (`private.billing_anomalies`):** a new table (`id` bigint identity PK, `organization_id` references `organizations(id) on delete cascade`, `kind` text, `detail` jsonb default `'{}'`, `detected_at` timestamptz default `clock_timestamp()`) giving `features/billing/reconcile.ts`'s duplicate-active-subscription and unapproved-subscription-price detection somewhere durable to record what it found, rather than only a `console.error` line nothing keeps. RLS enabled, no `anon`/`authenticated` grant of any kind — same pattern as `private.alert_email_log`/`private.notification_email_change_log` below. Diagnostic/observability data — recording an anomaly is never itself part of the entitlement decision.
    - **Finding 7 (compare-and-swap results checked rigorously):** `write_reconciliation_result()`, `write_activation()`, and `renew_checkout_attempt()`/`renew_reconciliation_lease()` all condition their write on the caller still owning a live lease/attempt (the same CAS pattern `record_checkout_session`/`release_checkout_attempt` already used) and return a boolean the caller must check — `write_reconciliation_result`/`write_activation` additionally re-mark `needs_reconciliation = true` (with `reconciliation_dirty_since` set if not already) **in the same statement** on a lost-ownership failure, so a reconciliation that fails to land is never silently dropped; `release_reconciliation_lease()` always marks the organization dirty regardless of whether the release itself matched a row, since a release is called when a caller is giving up without having written a result, so the organization's state can never be assumed current. `features/billing/actions.ts`'s own callers of the checkout-attempt functions were found, separately, to not be checking these results rigorously either (the release path ignored a false/null result, and a reclaim never verified the ownership proof it was supposedly checking) — fixed the same round, in application code, not schema; see `DECISIONS.md`.
    - **Finding 9 (lease renewal at a checkpoint, not just a longer static duration):** `renew_checkout_attempt()`/`renew_reconciliation_lease()` let a caller prove continued ownership and extend its own claim right before its slowest remaining step (Checkout Session creation; a slow `stripe.subscriptions.list()`), so correctness stops depending on any single static claim/lease duration being provably longer than every possible Stripe round trip combined — the same idea, applied to both of this schema's lease-shaped mechanisms.

32. `20260907230000_fix_reconciliation_lease_crash_gap.sql` — found by this round's own three-independent-reviewer adversarial audit of migrations 30/31 (not one of the original 14 findings). Migration 30 has already been applied to the isolated test project, so this is a forward fix, not a rewrite. **`claim_reconciliation_lease()`'s SUCCESS path never touched `needs_reconciliation` at all** — only its failure branch (another reconciler already holds a live lease) did. A caller that successfully claims the lease and then suffers a genuine PROCESS-LEVEL kill (a Vercel function timeout, an OOM, a container cutover — not a catchable JS exception, which `features/billing/reconcile.ts`'s own `try`/`catch` already handled) before ever calling `write_reconciliation_result`/`write_activation`/`release_reconciliation_lease` left the organization's row holding a soon-to-expire lease with `needs_reconciliation` still `false` — invisible to the scheduled sweep (which scans strictly `where needs_reconciliation = true`) until some unrelated trigger happened to reconcile the organization again. This directly contradicted migration 30's own header comment and `DECISIONS.md`'s "guaranteed convergence" claim for exactly this one abandonment path. `create or replace`s `claim_reconciliation_lease()` (same name/signature) so its successful-claim branch now ALSO sets `needs_reconciliation = true`/`reconciliation_dirty_since` in the same `UPDATE` that mints the owner token — flipping the invariant from "dirty only once something has gone wrong" to "dirty from the moment reconciliation is attempted, clean only once it has PROVABLY completed" (`write_reconciliation_result`/`write_activation`'s own success paths are what clear it back to `false`).
33. `20260907240000_clear_reconciliation_dirty_rpc.sql` — found by the same adversarial audit. `release_reconciliation_lease()` is the ERROR/ABANDONMENT cleanup path (its own header comment: "a reconciliation attempt that claimed the lease but then hit an unexpected error before writing") and unconditionally re-marks the organization dirty in the same statement, regardless of why it's called — but `reconcileOrganizationBilling`'s `no_subscriptions` outcome (Stripe genuinely reports nothing to reconcile, or reports only unapproved-price subscriptions with nothing previously tracked to revoke — see `features/billing/reconcile.ts`) was calling it anyway, since there was no way to express "I definitively checked, there is genuinely nothing to reconcile" without ALSO leaving the organization permanently flagged dirty and re-polled by the scheduled sweep every 15 minutes forever. `clear_reconciliation_dirty(p_organization_id, p_owner)`: releases the lease and clears `needs_reconciliation`/`reconciliation_dirty_since`, CAS'd on the caller still owning the lease (the same discipline as `release_reconciliation_lease`) — but, unlike that function, does **not** unconditionally re-mark dirty afterward. Used only for a confirmed-clean outcome; `release_reconciliation_lease` keeps its own always-assume-dirty behavior for every genuine error/abandonment path, unchanged.

34. `20260908100000_checkout_request_identity.sql` — fifth review round, integrating an independent parallel implementation's checkout-identity model onto this schema's own attempt/lease design. Migrations 30–33 have already been applied to the isolated test project, so this is a forward migration; it `drop function`s the four checkout RPCs and re-creates them with new signatures (only `service_role` can execute any of them, and `features/billing/actions.ts` — their sole caller — changes in the same commit). Adds `organization_billing.checkout_request` (jsonb), `checkout_created_at` (timestamptz) and `checkout_owner_token` (text). Three distinct gaps, all about an interrupted Checkout operation:
    - **Attempt identity was destroyed by lease expiry.** `checkout_attempt_expires_at` alone meant both "this request owns the slot" and "this attempt exists," so a request that died after calling Stripe but before recording its Session lost the attempt id — and the next request minted a fresh one, hence a fresh `checkout:attempt-<id>` idempotency key, and Stripe (never having seen that key) created a genuine SECOND Checkout Session. Split into a durable ATTEMPT (`checkout_attempt_id`, survives expiry) and a short-lived OPERATION lease over it (`checkout_owner_token` + `checkout_attempt_expires_at`). A takeover reuses the attempt id and therefore replays the same key.
    - **A replayed idempotency key requires byte-identical parameters.** Stripe rejects — rather than deduplicates — a retry whose parameters differ from the original call under that key, so rebuilding the request per attempt made correctness depend on `NEXT_PUBLIC_SITE_URL`, the price env vars and the organization's own row never changing in between. `checkout_request` is the immutable snapshot of exactly what was first sent, written once at attempt creation and cleared only when the attempt is released. `claim_checkout_attempt` validates it against the row (mode, customer, `line_items[0].price`, `client_reference_id`) and raises `VT302` otherwise, so a stored snapshot can only ever be a faithful description of its own claim.
    - **An idempotency key is only useful while Stripe remembers it** (documented as roughly 24 hours, not a permanent guarantee). `checkout_created_at` backs the claim's `retry_safe` result — "still inside a conservative 23-hour window" — and outside it the caller starts a genuinely new attempt instead of replaying.
    Also new: `finish_checkout_operation()` releases only the LEASE (the customer may still be on Stripe's hosted page, so the attempt and its recorded Session must outlive the request), while `release_checkout_attempt()` — the only thing that discards the identity — is called exclusively once a terminal Stripe state has actually been confirmed. `record_checkout_session()` is now called BEFORE the returned Session is validated at all: a Session that exists at Stripe but was never written down here is invisible to every later attempt, which is precisely how a customer ends up with two.
35. `20260908110000_billing_reconciliation_generations.sql` — the same round, part two. Adds `billing_sync_requested`/`billing_sync_completed` (bigint, default 0), `billing_sync_last_attempt_at`, `billing_sync_last_error`, and an index (`organization_billing_sync_candidates_idx`) backing the new candidate scan. Drops and re-creates `claim_reconciliation_lease` (its return type changes) and `write_reconciliation_result`/`write_activation`/`clear_reconciliation_dirty` (each gains `p_requested_generation`); adds `request_billing_reconciliation()`, `fail_billing_reconciliation()` and `get_billing_reconciliation_candidates()`.
    - **An event arriving DURING a reconciliation was silently lost.** The lease gave real mutual exclusion, and migration 32 made an ABANDONED reconciliation always recoverable — but a COMPLETED one cleared `needs_reconciliation` unconditionally, including the flag set moments earlier by a newer webhook that had failed to claim the lease. The row was then left holding state that predated that webhook, with nothing anywhere recording it had happened. Fixed with a monotonic generation pair: every entry point calls `request_billing_reconciliation` before any Stripe call, `claim_reconciliation_lease` returns the generation it observed, and a completing write clears the dirty flag only if `billing_sync_requested` has not advanced past that observation. A write now answers "was every request I knew about satisfied," not merely "did I finish."
    - **Recovery depended entirely on the dirty flag ever being set** — and every path that sets it runs inside this application, so an event never received at all (a misconfigured endpoint, a delivery dropped after Stripe exhausted its finite retries, a change made by hand in the Stripe Dashboard) left nothing dirty and was invisible to the sweep forever. `get_billing_reconciliation_candidates(p_limit, p_stale_seconds)` adds a second, independent trigger: an organization whose state simply has not been checked for a while is a candidate regardless of any flag. Convergence now rests on elapsed time, which this app can always observe, rather than on having successfully received a notification. Only organizations with a `stripe_customer_id` are ever candidates (there is nothing at Stripe to reconcile otherwise, and a pre-signup trial must not cost an API call every sweep), rows under a live lease are skipped, and `billing_sync_last_attempt_at` gives a one-minute per-organization back-off so a persistently failing organization cannot monopolize a run.
    - **Lock-then-check.** Every lease-timed write here (`write_reconciliation_result`, `write_activation`, `clear_reconciliation_dirty`, `fail_billing_reconciliation`, `renew_reconciliation_lease`, and migration 34's `record_checkout_session`/`renew_checkout_attempt`) now takes an explicit `select ... for update` before its `UPDATE`. Without it, Postgres evaluates the `expires_at > clock_timestamp()` qual during the scan — *before* waiting behind another transaction's row lock — and then applies the update once the wait ends, by which point the lease may have lapsed. (An `UPDATE` re-checks its qual after a wait only when the blocking transaction actually modified the row; a plain `SELECT ... FOR UPDATE` holder leaves the tuple unchanged, so nothing is re-evaluated.) This was a real defect in migration 30's `write_reconciliation_result`, not a hypothetical one: `scripts/verify-local-database.mjs` reproduces it by blocking a second connection behind a genuine lock and letting the lease lapse during the wait, and caught it in the first draft of these two migrations.
    `fail_billing_reconciliation(p_organization_id, p_owner, p_error)` records the last failure reason durably and frees the lease without advancing `billing_sync_completed` — a failure is unfinished work. `clear_reconciliation_dirty` additionally stamps `last_synced_at` now, so a confirmed-clean check is treated as a real check by the staleness scan rather than re-selecting the same organization on every run.
36. `20260908120000_stripe_customer_creation_identity.sql` — the same round, correcting a claim the integration itself made rather than a defect it introduced. Adds `organization_billing.customer_creation_id`/`customer_creation_started_at` and three functions: `claim_stripe_customer_creation()`, `record_stripe_customer()`, `rotate_stripe_customer_creation()`.
    - **What was wrong.** `getOrCreateStripeCustomerId` used Stripe's Customer Search as its recovery mechanism before creating, and treated a *failed* search identically to an empty one ("proceeding to create"). Stripe documents that search is not read-after-write consistent ("propagation of new or updated data can be up to an hour behind during outages") and that idempotency keys are pruned after ~24 hours ("we generate a new request if a key is reused after the original is pruned"). So: a `create()` that succeeded at Stripe but whose response or database write was lost, retried a day later while search was failing or lagging, produced a genuine SECOND Customer. Reconciliation only ever lists subscriptions for the customer persisted locally, so a customer who then paid on the other one would be charged and stay locked out of the dashboard.
    - **The fix.** A durable record of *when* a creation was attempted, which is what makes the two mechanisms usable as complements: the frozen key is authoritative from 0 to ~24 hours (where search may lag), search is authoritative from ~1 hour onward (where the key may be pruned). Inside the retry-safe window (23 hours, conservative against Stripe's "at least 24" floor) the caller replays the frozen key and does not search at all — removing the read-after-write use of search rather than merely making it more careful. Outside it, the search must SUCCEED; a failure now fails the checkout closed instead of creating. An empty result is trusted only because the recorded attempt is by then older than both the key lifetime and Stripe's documented worst-case propagation delay, with roughly 22 hours of margin, and the dead key is retired via `rotate_stripe_customer_creation` before a fresh Customer is created.
    - The backfill stamps `customer_creation_started_at` from `coalesce(checkout_created_at, created_at)` rather than `now()`, so a genuinely old interrupted creation is not reported as freshly retry-safe just because the migration ran.
    - **A later correction to how the application uses these columns** (no schema change): the first version still authorized creating a Customer on a cleanly-empty search once the attempt was old enough. That rested on Stripe's "up to an hour behind during outages" as though it were an upper bound, which it is not. Creation is now authorized only by a COMPLETED enumeration of the canonical `customers.list` endpoint over the bounded window the attempt could have created in; search is used only for positive identification, where its staleness cannot mislead. `rotate_stripe_customer_creation` is therefore called only after that enumeration returns a sound negative, and an ambiguous outcome leaves the attempt pending. See `DECISIONS.md`.
37. `20260909100000_separate_activation_generations.sql` — round-9 review, R9-02 (P1). Adds `activation_requested`/`activation_completed`, `request_billing_activation()`, and re-creates the lease claim and the three write functions to carry both generations. One generation pair counted REQUESTS rather than KINDS OF WORK, so a subscription refresh and an invoice activation could each mark the other's pending requests complete — reproduced both ways against real PostgreSQL. Each writer now advances only its own counter, and the dirty flag is the disjunction. **Its second half was wrong and is reversed by migration 40:** it also had `write_reconciliation_result` set `activated_at` when writing an `active` status, on the reasoning that an active subscription IS evidence of payment. It is not — see migration 40.
38. `20260909110000_fix_remaining_time_before_lock.sql` — round-9 review, R9-05 (P2). `confirm_notification_email_change` compared expiry against transaction-start `now()`, and accepted a token that expired while the call waited for the row lock; `claim_negative_alert_send` read `clock_timestamp()` after its advisory lock but before the card ROW lock its UPDATE takes, backdating the cooldown. Both now take every lock the decision depends on, then read the clock, then decide. Fifth instance of this class in this project — see the migration header for why each previous class-wide search missed the next one.
39. `20260909120000_customer_creation_lease_and_legacy_key.sql` — round-9 review, R9-03 and R9-04 (both P2). Adds a creation operation lease (`customer_creation_lease_owner`/`_expires_at`) so a second caller stands down instead of racing an in-flight create, and so rotation — the step that declares the frozen key dead — is refused unless the caller holds that lease. Also re-does 20260908120000's backfill: every unresolved row now carries the sentinel `legacy-org-<id>`, which the application maps back to the previous version's deterministic `customer-create:org-<id>` key, dated from the organization's own `created_at`. The first backfill invented a RANDOM key and called it retry-safe, so the "replay" would not have been a replay and Stripe would not have deduplicated it.

40. `20260910100000_activation_from_verified_payment.sql` — round-10 review, R10-01 (P1) and R10-03 (P2). Adds `organization_billing.activation_evidence`; replaces `request_billing_activation` with a two-argument form that requires verified `invoice.paid` evidence and latches `activated_at` **in the same statement**; drops `write_activation`; and re-creates `claim_reconciliation_lease`, `write_reconciliation_result` and `clear_reconciliation_dirty` without the activation generation they no longer need. Adds `customer_creation_key_state` (`unused`/`sent`/`unverified_legacy`) and `mark_stripe_customer_key_sent()`; re-creates `claim_stripe_customer_creation` (now also returning `needs_recovery`) and `rotate_stripe_customer_creation`. Replaying an idempotency key is a real replay only if that key was actually sent, which migrations 36 and 39 both inferred from the identity's AGE instead — 36 by inventing a random key, 39 by overwriting valid modern identities with a legacy sentinel. The state makes it a recorded fact, so no migration can manufacture a false replay and no valid identity needs overwriting. Sixth instance of this class; the migration header records the documented lock order (`nfc_cards → locations → organizations`) that keeps making these locks explicit from introducing deadlocks.

### Rollout ordering for migrations 12→13 and 16→17

Both pairs follow the same expand/deploy/enforce sequence (round-3 finding R3-05): applying the "enforce" migration (13 or 17) to production at the same time as its "expand" migration (12 or 16) would break the *currently deployed* application code, which still performs a direct `UPDATE` to the column(s) the trigger would then reject — creating a real outage window (every negative-feedback alert, or every settings save touching the notification email, failing) between the migration landing and the new application code deploying. Apply 12/16 first, deploy this PR's application code (which uses the RPCs instead of a direct `UPDATE`), let old instances drain, then apply 13/17. See `DEPLOYMENT.md` § 7 for the concrete, current production rollout command.

**Migration 18's new function is named `reserve_notification_email_change`, not `request_notification_email_change` — a correction, not the original design.** An earlier version of this migration named the new 2-argument function `request_notification_email_change`, reasoning (per the R6-03 principle) that it would "coexist... as a distinct overload" alongside the round-3 3-argument function of the same name. **A third independent review found that reasoning wrong**: PostgREST resolves an RPC call to a specific `pg_proc` overload purely by matching the callable parameter shape, independent of which migration added which function or when. A call naming exactly `(p_organization_id, p_email)` — the only way this app has ever invoked this RPC, old code and new code alike — matches BOTH a 2-argument function of this name AND the 3-argument one (via its own `default 1440`) the instant both are defined, regardless of grants or deploy order. Since `DEPLOYMENT.md`'s documented rollout applies the 2-argument function during `prepare` (before merge) and only drops the 3-argument one during `finalize` (after deploy and drain), the ORIGINAL design guaranteed a `PGRST203` outage for every caller across that entire window — not a bounded, carefully-timed risk, an unconditional one. Renaming the new function removes the category of bug entirely: two different names can never collide as PostgREST overloads, at any point in any rollout. See `DECISIONS.md` for the full incident and `e2e/rollout-compatibility-notification-email-rpc.spec.ts` for an executable proof against the real isolated project. Every object migration 18 introduces remains purely additive (new tables, new functions under a name nothing else uses) — safe to apply before this PR's application code deploys, exactly like any other expand migration; that part of the original reasoning was correct.

**Migrations 19 and 20 are where round 7 corrected a real mistake in round 6's own rollout plan, not an intentional exception.** Round 6's original handoff (quoted in `REVIEW_REQUEST_ROUND8.md`, superseded) claimed migration 19 "needs no expand/enforce staged mechanism... no existing trigger or column is being newly protected against currently-deployed code," reasoning that revoking `authenticated`'s grant on the round-3 3-argument function was acceptable to apply immediately because that function's behavior was itself the vulnerability being closed. **That framing missed the actual hazard**: production's *currently-deployed application code* — this PR has not merged yet — still calls the round-3 3-argument signature to change the notification-email recipient, the same as it did the day PR #2 shipped. Revoking that function's grant (migration 19) before the new application code (which calls the 2-argument signature instead) is live would make every "change notification email" settings save on the live site fail immediately with `"permission denied for function"` — a real, self-inflicted production outage for a feature that currently works, not a bounded window where a bypass gets a clean error instead of leaking a token (that framing was correct for the vulnerability itself, but conflated "this behavior should stop being reachable" with "it is therefore safe to make unreachable before anything else changes"). Migration 20 (R7-03's drop) has the identical hazard, one step worse: a live caller of the dropped function gets `PGRST202` ("could not find the function") instead of merely a permission error.

**Corrected rollout order, following the same expand → deploy → enforce sequence as migrations 12→13 and 16→17 above:**
1. Apply migration 18 (now genuinely purely additive, once renamed — see above) and migration 21 (a same-signature `create or replace` bug fix — see below) — both safe before the application code deploys.
2. Merge and deploy this PR's application code, which calls `reserve_notification_email_change` and never the legacy 3-argument `request_notification_email_change`.
3. Let old serverless instances drain (the same reasoning as every other enforce migration in this document).
4. Apply migration 19 (revoke the 3-argument function's grant + the unrelated `confirm_notification_email_change` TOCTOU fix bundled into the same file) and migration 20 (drop the 3-argument function outright) — safe now that nothing still calls it, and — unlike the pre-rename design — never ambiguous at any earlier point either.

**Migration 21 is a safe drop-in, not part of the enforce step**, despite being new this round: `claim_negative_alert_send()`'s signature is unchanged (`create or replace function` only), so — like migration 19's TOCTOU-fix half — it can be applied at any point without a compatibility window; it is grouped with the expand step above only because doing so early is simplest, not because it must wait.

**Migrations 23 through 33 (`onboarding_tour_status`; `organization_billing`/`stripe_webhook_events` and their grandfathering/event-ordering/rename/`activated_at`/checkout-attempt/reconciliation-lease columns and RPCs; `private.billing_anomalies` and its RPC) are all `--expand`, but for the opposite reason migrations 19/20 are `--enforce`.** Migrations 19/20 protect *old* code's dependency on something being removed (apply only after new code no longer needs it). Migrations 23-33 are the mirror case: *new* code depends on something being added — the dashboard layout queries `organizations.onboarding_tour_status` on every request to decide whether to show the tour (23); `app/dashboard/layout.tsx`'s paywall queries `organization_billing`, including `grandfathered_at` (24, 25) and `activated_at` (27), on every non-billing dashboard request; `features/billing/reconcile.ts` — the one shared reconciliation service the webhook route, the billing page's checkout-success handler, the admin resync action, and the scheduled sweep endpoint all call — claims/renews/writes/releases the `claim_reconciliation_lease`/`renew_reconciliation_lease`/`write_reconciliation_result`/`write_activation`/`release_reconciliation_lease`/`clear_reconciliation_dirty` RPCs (30, 32, 33) and calls `record_billing_anomaly` (31) on essentially every reconciliation attempt; and `createCheckoutSessionAction` calls `claim_checkout_attempt`/`record_checkout_session`/`release_checkout_attempt`/`renew_checkout_attempt` (29, 30) on every checkout attempt. Deploying this PR's application code before any of these eleven applies would make the corresponding request fail with a missing-relation, missing-column, or missing-function error — not a graceful fallback, since the object doesn't exist for the query to even run. So all eleven must land in the expand phase, before the code deploy, exactly like migrations 18/21/22. Most of these eleven migrations are purely additive in the straightforward sense (new tables, new columns, new functions); migration 26's column **rename** is additive here only because the column it renames was itself never live in production (created earlier in this same still-pending set) — see that migration's own entry and `DEPLOYMENT.md` § 7 for why a rename is not generically safe the way an added column is. Migration 30's `drop column billing_sync_seq`/`drop function claim_billing_sync` are likewise additive-in-effect here for the identical reason: nothing outside this still-entirely-pending migration set has ever read or called either, so there is no currently-deployed code path a drop could break — unlike migrations 19/20, this is not a case of old code needing time to stop depending on something before it goes away. Migrations 32/33 are `create or replace`/new-function-only additions with the same reasoning. See `DEPLOYMENT.md` § 7 for where this fits in the corrected `scripts/rollout.mjs` invocation.

See `DEPLOYMENT.md` § 7 for the corrected `scripts/rollout.mjs` invocation reflecting this order, and `SECURITY.md` § "The isolated test project's own migration history had drifted" (R7-03) for how recreating the 3-argument function to match production is what surfaced the `PGRST203` ambiguity that made migration 20 necessary in the first place.

Never hand-edit the production schema outside a migration file (see `supabase` skill's Database Change Workflow). To change the schema: inspect current state → write a migration → preserve existing data → define FKs/constraints/RLS/indexes → update `database.types.ts` → update application code → verify authorized, unauthorized, and cross-tenant access.

#### Onboarding tour state (migration 23)

`onboarding_tour_status` gates whether `features/onboarding-tour/`'s welcome dialog + step-by-step tour auto-opens on dashboard load. Scoped to the **organization**, not the member who happens to trigger it — deliberately: the tour is about whether *this business* has been introduced to the product (and nudges toward "create your first location"), not about one person's individual familiarity with it. If a future invite flow ships (no membership other than `owner` can exist yet — see `DECISIONS.md`), a newly-invited teammate joining an already-configured organization must not be told to create a first location that already exists; per-user scoping would get this wrong.

No new RPC: this column isn't one of the ones `private.prevent_direct_notification_email_change` protects, so the existing `organizations_update` RLS policy (any member of the org, `private.is_org_member(id)`) already covers writing it — `features/onboarding-tour/actions.ts`'s `setOnboardingTourStatusAction` is a plain `.update()` through the ordinary RLS-bound client, the same pattern `settings-actions.ts` already uses for `name`/`logo_url`. The CHECK constraint is what actually enforces the three-value state model, not application code.

**Existing organizations are protected from seeing the tour unexpectedly, without a bulk `UPDATE`**: migration 23 adds the column with `default 'completed'` first (every row that already exists reads `'completed'` immediately, for free, as the column's own default — no separate write touches them, so `updated_at` is never bumped for a reason unrelated to anything the organization changed), then a second `alter column ... set default 'not_started'` changes only what a *future* insert receives. Verified directly against the isolated project after this migration was rewritten: `information_schema.columns` shows the live default is `'not_started'::text`, the CHECK constraint is unchanged, and a pre-existing sample organization already reads `'completed'`.

### `nfc_cards`

Belongs to one location (and, denormalized, one organization) — **immutably**: `location_id` cannot be changed after creation (`private.prevent_nfc_card_location_change`, migration 5). A business that physically moves a card should deactivate it and issue a new one at the new location, not relocate the existing one; see that migration's comment for why (one card mapping to two locations over its lifetime breaks per-card analytics and the product's own card model). This is also enforced in the dashboard UI, not just the database (round 2, R2-09): the edit form shows an existing card's location as read-only text and `updateNfcCardAction`'s schema has no `location_id` field at all — the create form's editable dropdown remains for new cards. `public_id` is a random UUID, not the internal `id` — this is what appears in the public URL (`/r/{public_id}`), so internal sequential IDs are never exposed. `status` ∈ `{active, inactive}`; an inactive card's public page refuses new submissions. `last_negative_alert_at` — the negative-feedback alert cooldown timestamp. This column can **only** be changed by `claim_negative_alert_send()` — a trigger (`private.prevent_direct_cooldown_update`, installed by migration 13, deliberately separate from the migration that introduces the RPC — see "Rollout ordering" above) rejects any other `UPDATE` to it, from any role, including the admin client itself.

### `private.alert_email_log`

Added in migration 12 (round 2, R2-08; **revised in round 3** for R3-06). Each row is a *reservation/attempt*, not an unconditional record of a send: `organization_id`, `nfc_card_id`, `status` (`reserved` → `delivered` or `failed`, set by `finalize_negative_alert_send()`), `reserved_at`, `delivered_at`, `failed_at`. Not exposed to PostgREST (lives in the non-exposed `private` schema, RLS enabled as of migration 15 though moot given no `anon`/`authenticated` grant exists either way); only `service_role` has `select`/`insert`/`update` on it (see § Row Level Security). Backs `claim_negative_alert_send()`'s organization-wide hourly budget — indexed on `(organization_id, reserved_at)` — counting `reserved`+`delivered` rows within the trailing hour but excluding `failed` ones, so a transient delivery failure doesn't permanently consume budget the org never actually used (see the migration's comment for the exact reasoning, including why a crashed/never-finalized reservation is an accepted, bounded worst case rather than something actively cleaned up).

### `private.notification_email_change_log` / `private.notification_email_change_config`

Added in migration 18 (round 5, R5-12; rewritten round 6, R6-01/R6-04). `notification_email_change_log` mirrors `private.alert_email_log`'s reservation/attempt shape (`organization_id`, `status` `reserved`→`delivered`/`failed`, `reserved_at`/`delivered_at`/`failed_at`) for notification-email change requests; `select`/`update` granted to `service_role` only (read by `issue_notification_email_change_token()`/`finalize_notification_email_change_send()`, both `SECURITY INVOKER` — see below). `notification_email_change_config` holds the cooldown/hourly-budget values `request_notification_email_change()` enforces, keyed **per organization** rather than a single global row (round-6 R6-04's own comment explains why: a shared global would make any test tuning it race every other concurrently-running test exercising the same RPC under normal defaults) — no row means the function falls back to its built-in defaults (5 minutes / 5 per hour). `service_role` has `select`/`insert`/`update`/`delete` on it, used by tests to seed a per-organization override; nothing grants `authenticated` any access to either table, by design — the whole point of R6-04 was to stop the rate limit being tunable by the party it constrains.

### `feedback`

Belongs to one org/location/nfc_card (all three denormalized for RLS and query performance — see consistency triggers below), and **immutably** once inserted: `organization_id`/`location_id`/`nfc_card_id`/`rating`/`feedback_text`/`created_at` cannot be changed by any `UPDATE`, from any role including a future admin-client bug (`private.prevent_feedback_content_change`, migration 4). Only `status` and `internal_note` are editable after submission — RLS alone only enforces *row* ownership, not *column* restriction, so this trigger is what actually stops an org member from rewriting a customer's original rating or written feedback. `rating` constrained `1..5` at the database level. `feedback_text` nullable, ≤ 1000 chars (validated in the Server Action; DB constraint caps at 5000 as a hard backstop). `status` ∈ `{new, in_progress, resolved}`. `internal_note` — dashboard-only, never shown to the customer. `priority` — **generated column**, `high` (rating ≤ 2) / `medium` (rating = 3) / `normal` (rating ≥ 4), always derived from `rating` and never independently writable.

### `profiles`

One row per `auth.users` row, auto-created by the `on_auth_user_created` trigger. Currently holds only `full_name`; nothing in the app reads it yet (the dashboard header shows the org name, not the user's name). Added ahead of need because retrofitting after real users exist is more disruptive than creating it empty.

### `organization_billing`

Added in migration 24 (`20260907150000_add_organization_billing.sql` — an earlier version of this line said migration 18, which is `20260905193325`'s notification-email-budget migration, not this table; corrected). One row per organization (`organization_id` is both the PK and the FK), auto-created by `private.provision_organization_trial()` (an `after insert on organizations` trigger) the instant an organization is created — every organization, no exceptions, starts on a 14-day no-card trial. `stripe_customer_id`/`stripe_subscription_id` — nullable, populated on first checkout. `status` — mirrors Stripe's own `Subscription.status` enum exactly (`trialing`, `active`, `past_due`, `canceled`, `incomplete`, `incomplete_expired`, `unpaid`, `paused`), defaulting to `trialing`; kept exhaustive on purpose so a reconciliation write can never fail on a status Stripe itself considers valid (see `features/billing/reconcile.ts`'s `toBillingStatus`, which maps anything Stripe adds later to `incomplete` rather than crashing). `trial_ends_at` — only meaningful while `stripe_subscription_id` is still null (this app's own pre-signup trial); once a subscription exists, Stripe's `status` is authoritative and this column is ignored (`features/billing/status.ts`'s `isBillingActive`). `current_period_end`/`cancel_at_period_end` — kept in sync from the Stripe subscription object on every successful reconciliation, shown on the billing page. `reconciliation_lease_owner`/`reconciliation_lease_expires_at`/`needs_reconciliation`/`reconciliation_dirty_since` (migration 30) — the exclusive reconciliation lease and its durable dirty-flag, superseding migration 29's `billing_sync_seq`; see that migration's entry above and `DECISIONS.md`'s "Stripe webhook reconciliation" entry for why. `billing_sync_requested`/`billing_sync_completed`/`billing_sync_last_attempt_at`/`billing_sync_last_error` (migration 35) — the generation pair that keeps an event arriving *during* a reconciliation from being discarded by that reconciliation's own completing write, plus the sweep's back-off and last-failure record. `checkout_request`/`checkout_created_at`/`checkout_owner_token` (migration 34) — the immutable Checkout request snapshot, when its idempotency key was minted, and the short-lived operation lease over an attempt whose identity now outlives it. Only `service_role` (the webhook handler, the checkout/portal Server Actions, and `features/billing/reconcile.ts`'s shared service, all via the admin client) ever writes to this table — see § Row Level Security.

### `stripe_webhook_events`

Added in migration 18. `id` (the Stripe event id, e.g. `evt_...`) as the primary key, `created_at`. Purely an idempotency ledger: the webhook handler inserts the incoming event's id before doing anything else; a unique-violation on that insert means a duplicate delivery (Stripe explicitly documents at-least-once, possibly-repeated delivery) and the handler stops there instead of reapplying the event. No RLS policies at all, not even `select` — nothing but `service_role` (which bypasses RLS) ever needs to touch it.

### `private.billing_anomalies`

Added in migration 30 (fourth independent review, Finding 4). `id` bigint identity PK, `organization_id` (references `organizations(id) on delete cascade`), `kind` text, `detail` jsonb default `'{}'`, `detected_at` timestamptz default `clock_timestamp()`, indexed on `(organization_id, detected_at desc)`. `features/billing/reconcile.ts` writes one row here whenever `pickCurrentSubscription` excludes a subscription whose price isn't in this app's own approved allowlist (`"unapproved_subscription"`), finds more than one simultaneously active/trialing subscription on the same Stripe Customer (`"duplicate_active_subscriptions"`), or the webhook/activation path finds a Stripe object's Customer doesn't match the organization's own already-persisted one (`"customer_mismatch"`) — diagnostic/observability data recording what a reconciliation found, never itself part of the entitlement decision (`pickCurrentSubscription`'s own return value is). RLS enabled, no `anon`/`authenticated` policy of any kind — not exposed to PostgREST at all (`private` schema, absent from `config.toml`'s `schemas` list), the same pattern as `private.alert_email_log`/`private.notification_email_change_log` above; reached exclusively via `record_billing_anomaly()` (migration 31), `service_role`-only, for the same reason those two tables each needed their own dedicated RPC. Only `select`/`insert` are granted to `service_role` — nothing ever needs to `update`/`delete` an anomaly record.

## Indexes

Every FK column used in an RLS predicate is indexed (`organization_id` on memberships/locations/nfc_cards/feedback; `location_id`/`nfc_card_id` where used as join keys). `feedback (organization_id, created_at desc, id desc)` backs the newest-first inbox and its compound cursor pagination (migration 7 — `id` is a required tiebreaker, since `created_at` alone can tie between rows and a page boundary landing inside a tied group would otherwise silently skip whichever of them wasn't on the earlier page); `feedback (organization_id, status)` backs unresolved filtering; `feedback (organization_id, priority)` backs "unresolved high-priority first" queries.

## Data-integrity triggers (defense beyond RLS)

- `private.set_updated_at()` — generic `updated_at` bump, on every tenant-owned table.
- `private.prevent_organization_id_change()` — blocks `UPDATE`s that move a row from one org to another (relevant for a user who belongs to more than one org: without this, an `UPDATE ... WITH CHECK` policy alone could allow moving a row between two orgs the same user belongs to).
- `private.validate_nfc_card_organization()` — on `nfc_cards` insert/update, checks `organization_id` actually matches the referenced `location_id`'s organization. Without this, a member could construct an `nfc_card` whose `organization_id` passes RLS but whose `location_id` points at a different org's location.
- `private.validate_feedback_consistency()` — same idea for `feedback`: `organization_id`/`location_id` must match the referenced `nfc_card`'s own org/location.
- `private.prevent_feedback_content_change()` (migration 4) — blocks `UPDATE`s to `feedback`'s customer-authored/origin columns; only `status`/`internal_note` may change. RLS's row-level `feedback_update` policy alone permits rewriting any column, so this is the actual column-level restriction, not the RLS policy.
- `private.prevent_nfc_card_location_change()` (migration 5) — blocks any `UPDATE` that changes an `nfc_card`'s `location_id`.
- `private.prevent_direct_cooldown_update()` (migration 13) — blocks any `UPDATE` that changes `nfc_cards.last_negative_alert_at` unless a transaction-local flag (`app.allow_cooldown_update`) is set, which only `claim_negative_alert_send()` ever sets. Same pattern as the two triggers above (a column RLS's row-level policies cannot restrict), applied to a column no legitimate dashboard action ever needs to touch directly, rather than one legitimate actions need to touch selectively.
- `private.prevent_direct_notification_email_change()` (migration 17, round 3 R3-03) — blocks any `UPDATE` that changes `organizations.notification_email`/`notification_email_pending`/`notification_email_pending_token_hash`/`notification_email_pending_expires_at` unless a transaction-local flag (`app.allow_notification_email_change`) is set, which only `request_notification_email_change()`/`clear_notification_email()`/`confirm_notification_email_change()` ever set. Without this, a member could set the pending token hash to one they chose themselves and "confirm" an address without ever proving inbox possession — defeating the entire point of the confirmation flow.
- `private.provision_organization_trial()` (migration 18) — not a *restriction* trigger like the others above, but the same "must happen no matter which code path inserts the parent row" reasoning: `after insert on organizations`, creates that organization's `organization_billing` row with a 14-day trial. Runs under whatever privilege inserted the `organizations` row in the first place (`create_organization_atomic`'s `SECURITY DEFINER` context, or the admin client's `service_role`) — there is no path that creates an organization without also, atomically, provisioning its trial.

These exist because `organization_id`/`location_id` are denormalized (duplicated) rather than purely derived through joins; the triggers are what keeps the duplication from silently drifting and corrupting the tenant boundary — plus, for the last two, enforcing invariants RLS structurally cannot express (RLS is row-scoped, not column-scoped, and has no notion of "immutable after insert").

## Row Level Security

RLS is enabled on every table in `public`. Policy shape, uniformly: `to authenticated using (private.is_org_member(organization_id))`, with a matching `with check` on `insert`/`update` policies. `private.is_org_member()` is `SECURITY DEFINER` (needed to read `organization_memberships` without recursively triggering that table's own RLS) but is narrowly scoped: `stable`, `set search_path = ''`, takes one argument, checks `auth.uid()` internally, lives in the non-exposed `private` schema, and its `EXECUTE` grant is revoked from `public` and re-granted only to `authenticated`.

No table has an `anon`/`authenticated` **insert** policy for `organizations`, `organization_memberships`, or `feedback`. Those writes happen through two different, deliberate bypass mechanisms — see `SECURITY.md` § "The deliberate RLS bypasses" for the full accounting and the security reasoning behind each: the secret-key admin client (server-only, used by public feedback submission, public card lookup, and negative-feedback alerts), and the `SECURITY DEFINER`/`SECURITY INVOKER` database functions below that replace what used to be plain multi-step admin-client inserts with a single atomic, validated operation.

`profiles` follows the standard "own row only" pattern: `select`/`update` `using (auth.uid()) = id)`, no policy lets a user read another user's profile.

`private.alert_email_log` (migration 12, RLS enabled by migration 15 — round 3 R3-07) has no policies for `anon`/`authenticated` at all — the schema itself isn't exposed to PostgREST, and only `service_role` (via explicit `grant usage on schema private to service_role; grant select, insert, update on private.alert_email_log to service_role;`) can read or write it. `service_role`'s `bypassrls` does not substitute for these grants — RLS bypass and schema/table `GRANT`s are separate privilege types, confirmed the hard way when the migration was first applied without them and `claim_negative_alert_send` failed with "permission denied for schema private" even though its caller was `service_role`.

`organization_billing` (migration 18) has a `select` policy for members (`private.is_org_member(organization_id)`, so the billing page can render it) but **no `insert`/`update`/`delete` policy for `authenticated` at all** — deliberately: an owner must never be able to grant their own organization an active subscription by writing to this table directly, only Stripe's webhook (via signature-verified events) and this app's own admin-client code (creating the Stripe customer, linking `stripe_customer_id`) can. `stripe_webhook_events` (migration 18) has RLS enabled with zero policies of any kind, for any role — not even `authenticated` `select` — since nothing but `service_role` ever needs to touch it.

## Database functions callable as RPCs

Beyond `private.is_org_member` (used only from within RLS policy evaluation, never called directly), twenty-two functions in `public` are meant to be invoked as PostgREST RPCs. This was eleven through round 7 — the round-3 `request_notification_email_change(bigint, text, int)` was kept defined but ungrantable to any client-reachable role (round 6, R6-01/R6-03) until round 7 (R7-03) dropped it outright after discovering that keeping it defined at all created a `PGRST203` overload-resolution ambiguity against the 2-argument replacement for any 2-named-argument call, independent of grants (see "Rollout ordering" above) — then fifteen after a third independent review's four checkout/reconciliation-fencing additions (migration 29), then twenty-one after a fourth independent review dropped `claim_billing_sync` (superseded, migration 30) and added seven more (`renew_checkout_attempt`, the five reconciliation-lease functions, and `record_billing_anomaly` — migrations 30/31), then twenty-two after that same round's own three-independent-reviewer adversarial audit added `clear_reconciliation_dirty` (migration 33 — see that entry above for the crash-recovery gap it closes). `e2e/rpc-privilege-matrix.spec.ts`'s completeness test (round-5 R5-10) queries `pg_proc`/`pg_namespace` directly and fails if this count or list ever drifts from the real catalog — treat that test, not this document, as the authoritative count when the two disagree.

- **`submit_feedback_atomic(p_public_id, p_rating, p_feedback_text)`** (migration 6, relocked in migration 11) — `SECURITY INVOKER`. Locks **both** the target card and location rows (`for update of c, l`), atomically re-checks card/location active status and a per-card submission-rate limit (20 per 5 minutes), then inserts the feedback row. Migration 6 closed the check-then-insert race the old two-round-trip flow had for the card; round 2 (R2-05) found the location row was never locked — a location deactivated mid-transaction could still receive an insert — and migration 11 extended the same `SELECT ... FOR UPDATE` to cover it. `EXECUTE` is restricted to `service_role` only (see the role-allowlist table below); `SECURITY INVOKER` (not `DEFINER`) because its only caller, the admin client, already bypasses RLS at the connection-role level, so there's no privilege this function needs beyond what its caller already has.
- **`create_organization_atomic(p_name)`** (migration 8) — `SECURITY DEFINER`, unlike most other functions in this schema, because it must be callable directly by an authenticated user's own session to bootstrap their first organization, and there is deliberately no `INSERT` policy on `organizations`/`organization_memberships` for `authenticated` to invoke through otherwise. Idempotent (returns the caller's existing organization if they already have one) and serialized per user via `pg_advisory_xact_lock`. Mitigations for the `DEFINER` privilege: an explicit `auth.uid()` check as the first statement, `set search_path = ''`, and an explicit role allowlist (below).
- **`get_feedback_overview_snapshot(p_organization_id)`** (migration 9, round 2 R2-02/R2-03/R2-04) / **`get_feedback_period_analytics(p_organization_id, p_days)`** (migration 9, revised by migration 14 for R3-04 — signature changed, `p_since` removed) — both `SECURITY INVOKER`, `stable`. Called through the dashboard's own RLS-bound client (not the admin client), so RLS applies to every table they touch exactly as it would to a hand-written query. Each computes its entire result — totals, rating distribution, daily series, per-location/per-card breakdowns — as `jsonb` inside one statement built on a single shared `base` CTE, so every number in one call reflects one consistent MVCC snapshot; see `SECURITY.md` § "Analytics correctness" for the full consistency semantics. `get_feedback_period_analytics` additionally validates `p_days` against an explicit allowlist (7/30/90 — the only values the UI ever sends) before doing anything else, raising immediately rather than passing a caller-controlled value into `generate_series` (round-3 R3-04: an arbitrary `p_days` — huge, negative, zero — forced an unbounded or malformed series); `p_since` is derived internally from the now-validated `p_days` rather than trusted as a redundant caller-supplied value.
- **`claim_negative_alert_send(p_nfc_card_id, p_cooldown_minutes default 5, p_org_hourly_budget default 30)`** (migration 12, revised by the same file in round 3 for R3-02/R3-06; revised again by migration 21 for round 7's R7-05) — `SECURITY INVOKER`, same reasoning as `submit_feedback_atomic` (only caller is the admin client). Serializes per organization via `pg_advisory_xact_lock(hashtext('claim_negative_alert_send:' || org_id))` before checking the organization's trailing-hour reservation count against `private.alert_email_log` (round-3 R3-02: without this lock, two concurrent claims for two *different* cards in the same org never contend on any shared row lock, so both could read the same "under budget" snapshot and both succeed, overshooting the budget), then atomically claims the per-card cooldown via a flagged `UPDATE` and inserts a `'reserved'` log row. Returns the new log row's `bigint` id (or `null` if nothing was claimed) — **not** a boolean, and **not** a record of a send (round-3 R3-06) — see `finalize_negative_alert_send` below. **Round 7 (R7-05)**: every freshness/window check in the function body (the budget cutoff, the cooldown comparison) and every timestamp it writes (`last_negative_alert_at`, `reserved_at`) now reuse one `clock_timestamp()` value captured immediately after the advisory lock is acquired, rather than `now()` (fixed at transaction start) — the same class of bug round 6 (R6-04) fixed in `request_notification_email_change`, found here by searching the rest of the schema for the same pattern after fixing it there.
- **`finalize_negative_alert_send(p_log_id, p_delivered)`** (migration 12, round 3 R3-06) — `SECURITY INVOKER`, same caller as `claim_negative_alert_send`. Reports the real outcome of a reservation: sets its `status` to `'delivered'` or `'failed'` with the matching timestamp. `where status = 'reserved'` in its `UPDATE` makes a duplicate/retried call a silent no-op rather than a real transition — called exactly once per successful claim, from a `finally` block in `features/notifications/negative-feedback-alert.ts`, so every reservation eventually resolves.
- **`reserve_notification_email_change(p_organization_id, p_email)`** (migration 16 named this `request_notification_email_change`, round 3 R3-03; rewritten and renamed migration 18, round 6 R6-01/R6-04, third independent review Finding 1) — `SECURITY DEFINER`, same reasoning as `create_organization_atomic` (must run as the calling member's own session; explicit `auth.uid()` + membership check inside). Validates and rate-limits (cooldown/budget read from `private.notification_email_change_config`, keyed per organization — round-6 R6-04, since the round-5 version's `p_cooldown_minutes`/`p_org_hourly_budget` were plain caller-suppliable arguments an `authenticated` caller could simply override to disable its own rate limit), then reserves a `'reserved'` row and records the candidate address as pending. Returns only a `bigint` **log id** — round 6 (R6-01) removed the token entirely from this function's return value; see `issue_notification_email_change_token` below for why. Overwrites any existing pending request outright. **Renamed from `request_notification_email_change`** (a third independent review): that name collided with migration 16's own 3-argument function of the same name, and PostgREST cannot resolve a 2-named-argument call between them once both are defined — see "Rollout ordering" above for the full incident.
- **`issue_notification_email_change_token(p_log_id, p_expires_in_minutes default 1440)`** (migration 18, round 6 R6-01) — `SECURITY INVOKER`, `EXECUTE` granted to `service_role` **only** (never `authenticated`, never `anon`). The only function that ever generates or sees the plaintext confirmation token: validates the log row is a known, still-`'reserved'` request, mints a random 32-byte token (`pgcrypto`'s `gen_random_bytes`), stores only its SHA-256 hash plus an expiry against that reservation's organization, and returns the raw token once. Callable exclusively from trusted server code via the admin client (`features/organizations/settings-actions.ts`, immediately after `request_notification_email_change` succeeds) — no browser or ordinary authenticated Supabase client can reach it or obtain a token through it, closing the exact gap R6-01 found in every prior version of `request_notification_email_change` itself (both round 3's and round 5's — see `SECURITY.md` § "The token was never actually protected").
- **`finalize_notification_email_change_send(p_log_id, p_delivered)`** (migration 18, round 5 R5-12; rewritten round 6 R6-04) — `SECURITY INVOKER` (was `DEFINER` through round 5, when its caller was the authenticated user's own session; round 6 made it `service_role`-only, so the caller — the admin client — already has, via explicit grants, everything the `DEFINER` privilege used to provide, and the `auth.uid()`+membership ownership check that used to authorize an arbitrary authenticated caller is no longer meaningful or present). Reports whether a reserved notification-email-change request's send actually succeeded, the same `reserved`/`delivered`/`failed` pattern as `finalize_negative_alert_send`, so a failed send doesn't permanently consume budget it never used. Round 5 originally made this callable by `authenticated` with a caller-supplied `p_delivered` result; round-6 finding R6-04 closed that — a client can no longer mark its own reservation delivered or failed at all.
- **`clear_notification_email(p_organization_id)`** (migration 16, round 3 R3-03) — `SECURITY DEFINER`, same membership check. Needs no token/confirmation — removing a recipient can't be abused to send email anywhere, unlike adding one.
- **`confirm_notification_email_change(p_token)`** (migration 16, round 3 R3-03; TOCTOU fixed migration 19, round 6 R6-05) — `SECURITY INVOKER`, called via the admin client from the public `app/api/notification-email/confirm` route (no `auth.uid()` to check — whoever clicks the email link may not be signed in to this app at all, the same as `/auth/confirm`). A single atomic conditional `UPDATE` (its `WHERE` clause re-checks the token hash, expiry, and pending-address presence, using `RETURNING` to learn whether anything matched) promotes `notification_email_pending` to `notification_email` and clears the pending fields only when a token whose hash matches a still-pending, non-expired request is given. Returns the confirmed organization's `bigint` id, or `null` if the token is unknown, already used, or expired. Round 6 (R6-05) found the round-3 version SELECTed the matching organization, then separately UPDATEd it by `id` alone with no re-check of the token — a concurrent `request_notification_email_change()` call for the same org, landing between those two statements, could replace the pending address/token before the UPDATE ran, which then blindly promoted the *new* address using the *old* token's authority. Collapsing both steps into one statement removes the window a concurrent write could land in.

The round-3 original 3-argument `request_notification_email_change(p_organization_id, p_email, p_expires_in_minutes default 1440)` (migration 16) is **no longer defined at all** as of migration 20 (round 7, R7-03) — dropped outright, not merely stripped of grants as migration 19 (round 6, R6-01) had left it. See "Rollout ordering" above for the `PGRST203` overload-ambiguity discovery that made an outright drop necessary, and for why production must have this PR's new application code deployed before this migration is applied.

- **`claim_billing_sync(p_organization_id)`** (migration 29, third independent review Finding 4 — **dropped by migration 30, fourth independent review Finding 3; no longer exists**) — the per-organization fencing token `syncSubscription` used to claim before any Stripe network call, conditioning its own final write on still holding the exact value claimed. A fourth independent review's own adversarial self-review found this design invalid in principle: a request that claims an earlier sequence number can still execute — and observe genuinely fresher Stripe state — *after* a request that claimed a later sequence number has already written, and claim-order fencing discarded that fresher read purely because of claim order, with nothing left to ever correct it. See `claim_reconciliation_lease`/`write_reconciliation_result` below for the replacement, and `DECISIONS.md`'s "Stripe webhook reconciliation" entry for the full incident.
- **`claim_checkout_attempt(p_organization_id, p_interval, p_price_id, p_mode, p_claim_seconds default 150)`** (migration 29, third independent review Finding 2; `create or replace`d in place by migration 30, fourth independent review Finding 1 — same name/signature, so this is a bug fix, not a new function) — `SECURITY INVOKER`, `service_role`-only. Claims (or returns the still-live) checkout attempt for an organization, row-locked (`for update`) to serialize concurrent claims; returns an opaque attempt id plus whatever's already known about a previously-created (possibly now-superseded) Stripe session, so the caller can reconcile it against Stripe before ever creating a new one. **Fourth independent review, Finding 1**: the migration-29 body's "mint a fresh attempt" branch updated the interval/price/mode columns but left `pending_checkout_session_id` pointing at the *previous* attempt's session — migration 30 clears it in the same `UPDATE` that mints the fresh attempt, so a subsequent reader can no longer pair fresh plan metadata with a stale session id.
- **`record_checkout_session(p_organization_id, p_attempt_id, p_session_id, p_lease_seconds default 86400)`** (migration 29, third independent review Finding 2) — `SECURITY INVOKER`, `service_role`-only. Persists a created Stripe Checkout Session against the attempt that created it, compare-and-swapped on `p_attempt_id` — returns `null`/no row if a newer attempt has since superseded it. `features/billing/actions.ts` checks this `boolean` result rigorously as of a fourth independent review's Finding 7 — an earlier version of the calling code did not.
- **`release_checkout_attempt(p_organization_id, p_attempt_id)`** (migration 29, third independent review Finding 2) — `SECURITY INVOKER`, `service_role`-only. Clears a stale or plan-mismatched attempt, compare-and-swapped on `p_attempt_id` the same way, so a fresh claim can be taken immediately rather than waiting out the rest of its lease. **Fourth independent review, Finding 7**: `features/billing/actions.ts`'s release path used to ignore a `false`/`null` result from this RPC — now checked, and a failed release is treated as a real, handled outcome rather than assumed to have succeeded.
- **`renew_checkout_attempt(p_organization_id, p_attempt_id, p_claim_seconds default 150)`** (migration 30, fourth independent review Finding 9) — `SECURITY INVOKER`, `service_role`-only. Lets a caller prove it still owns its claimed checkout attempt and push the claim's expiry out further, compare-and-swapped on `p_attempt_id` still being live — called by `features/billing/actions.ts` at a natural checkpoint (after customer resolution, right before the Checkout Session creation call), so correctness stops depending on any single static claim duration provably exceeding every possible Stripe round trip.
- **`claim_reconciliation_lease(p_organization_id, p_lease_seconds default 45)`** (migration 30, fourth independent review Finding 3) — `SECURITY INVOKER`, `service_role`-only. Row-locks the organization (`for update`) and either mints a fresh opaque owner token if no live lease exists, or — if another reconciler already holds one — durably marks `needs_reconciliation = true` (with `reconciliation_dirty_since` set if not already) in the same statement and returns `null`. Only one reconciler may hold an organization's lease at a time; a failed claim is never treated as "safe to assume someone else's write covers it" by any caller, precisely because that assumption is what Finding 3 found unsafe about the design this replaces.
- **`renew_reconciliation_lease(p_organization_id, p_owner, p_lease_seconds default 45)`** (migration 30, Finding 9) — `SECURITY INVOKER`, `service_role`-only. The reconciliation-lease equivalent of `renew_checkout_attempt` — compare-and-swapped on `p_owner` still holding a live lease, called by `features/billing/reconcile.ts` before its own slowest remaining step (`stripe.subscriptions.list()`).
- **`write_reconciliation_result(p_organization_id, p_owner, p_stripe_customer_id, p_stripe_subscription_id, p_status, p_current_period_end, p_cancel_at_period_end)`** (migration 30, Finding 3) — `SECURITY INVOKER`, `service_role`-only. Writes the reconciled billing state, compare-and-swapped on `p_owner` still owning a live lease; on success also clears the lease and every `checkout_attempt_*`/`pending_checkout_session_id` column — mirroring what `syncSubscription` used to clear "unconditionally on every successful sync" per `DECISIONS.md`'s "Checkout concurrency" entry, now moved into this function. On a lost-ownership failure it does **not** throw — it durably re-marks `needs_reconciliation = true` (with `reconciliation_dirty_since` set if not already) and returns `false`, so a reconciliation that fails to land is never silently dropped; the scheduled sweep (`app/api/admin/reconcile-billing-sweep/route.ts`) is what eventually picks it back up.
- **`write_activation(p_organization_id, p_owner)`** (migration 30) — **dropped by migration 40.** It was the second half of a two-phase activation, and that gap between "a payment was verified" and "the payment was recorded" was interruptible: a worker that died in between left an obligation nothing could later discharge (R10-03). Activation is now a single statement, `request_billing_activation`, so there is no second write to lose.
- **`release_reconciliation_lease(p_organization_id, p_owner)`** (migration 30, Finding 3) — `SECURITY INVOKER`, `service_role`-only. Releases a held lease, compare-and-swapped on `p_owner`, and **always** marks the organization `needs_reconciliation = true` regardless of whether the release itself matched a row — a release is called when a caller is giving up without having written a result, so the organization's state can never be assumed current on release alone.
- **`record_billing_anomaly(p_organization_id, p_kind, p_detail default '{}')`** (migration 31, Finding 4) — `SECURITY INVOKER`, `service_role`-only. Inserts into `private.billing_anomalies` (above) — needed because `private`-schema tables aren't exposed to PostgREST at all, the same reasoning already documented for `private.alert_email_log`/`private.notification_email_change_log`.
- **`clear_reconciliation_dirty(p_organization_id, p_owner)`** (migration 33, found by this round's own adversarial audit) — `SECURITY INVOKER`, `service_role`-only. The confirmed-clean counterpart to `release_reconciliation_lease`: releases the lease and clears `needs_reconciliation`/`reconciliation_dirty_since`, CAS'd on the caller still owning it, but — unlike `release_reconciliation_lease` — does **not** unconditionally re-mark the organization dirty afterward. `reconcileOrganizationBilling`'s `no_subscriptions` outcome calls this, not `release_reconciliation_lease`, since Stripe genuinely reporting nothing to reconcile (or reporting only unapproved-price subscriptions with nothing previously tracked to revoke) is a definitively-checked-clean result, not an error or an abandoned attempt — using `release_reconciliation_lease` there left every organization that ever reached that branch permanently flagged dirty, re-polled by the scheduled sweep forever.

## Types

`lib/supabase/database.types.ts` is hand-written (no local Docker environment for `supabase gen types`) and updated by hand alongside every migration. `feedback.priority` is typed on `Row` only, not `Insert`/`Update`, since Postgres computes it and the app must never attempt to set it directly. `get_feedback_overview_snapshot`/`get_feedback_period_analytics` are typed with `Returns: Json` (they return `jsonb`) — `features/analytics/parse-snapshots.ts` is the one place that parses that `Json` into the app's actual typed shapes, discriminating an error/null result into `{ unavailable: true }` rather than trusting the shape blindly. `claim_negative_alert_send` is typed `Returns: number | null` (round-3 R3-06 — a reservation id, not a boolean); `finalize_negative_alert_send` is `Returns: undefined`. `clear_notification_email`/`confirm_notification_email_change` (round-3 R3-03) are typed `Returns: undefined` and `number | null` respectively. `request_notification_email_change` is now `Returns: number` (a log id, not the token — round-6 R6-01), `issue_notification_email_change_token` (new, round-6 R6-01) is `Returns: string`, and `finalize_notification_email_change_send` is `Returns: undefined` (unchanged type, though its grant moved to `service_role` — round-6 R6-04). The round-3 3-argument `request_notification_email_change` overload has no corresponding type entry and, as of round 7 (R7-03), no longer exists in the database either — dropped outright (migration 20), not merely unreachable.
