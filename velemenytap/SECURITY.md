# Security

## Tenant isolation

This is a multi-tenant SaaS; cross-tenant data leakage is treated as critical severity. The tenant boundary is enforced at the database layer via Postgres RLS (`DATABASE_SCHEMA.md` § Row Level Security), not by application-level filtering — a query that "forgets" a `WHERE organization_id = ...` clause still cannot return another org's rows. Every RLS policy follows `private.is_org_member(organization_id)`, a single `SECURITY DEFINER` helper, so the tenant check is one auditable code path rather than duplicated per policy.

Denormalized `organization_id`/`location_id` columns (kept for RLS/query performance rather than requiring joins) are guarded against drift by trigger functions (`validate_nfc_card_organization`, `validate_feedback_consistency`) that re-derive the true value from the parent row and reject any insert/update where they disagree. `organization_id` itself is immutable post-creation (`prevent_organization_id_change`), closing the specific hole where a user belonging to two orgs could otherwise move a row between them via an `UPDATE`. `nfc_cards.location_id` is likewise immutable (`prevent_nfc_card_location_change`) — relocating a card to a different location isn't a tenant-isolation hole by itself, but it would let the same card span two locations' feedback history, breaking per-card analytics and the product's own card model.

RLS is a *row-level* boundary — it has no notion of restricting which *columns* an authorized `UPDATE` can touch. The `feedback_update` policy correctly restricts updates to rows the caller's org owns, but by itself would let any member rewrite a customer's original `rating`/`feedback_text` via a direct `UPDATE`, not just the `status`/`internal_note` fields the dashboard's own code ever sets. `private.prevent_feedback_content_change` closes that gap with a trigger that rejects changes to anything but `status`/`internal_note`, regardless of caller — including a hypothetical future bug in server-side admin code, since a trigger fires for every role, not just `authenticated`.

## Secrets

- `SUPABASE_SECRET_KEY` is read only in `lib/supabase/admin.ts`, which is guarded by `import "server-only"` — a build-time guarantee it can never enter a client bundle.
- No `NEXT_PUBLIC_*` variable holds a privileged credential; only the Supabase URL and publishable key are exposed to the browser.
- `.env.local` and `.env*.local` are gitignored; `.env.example` documents required variables without values.

## The deliberate RLS bypasses

An earlier version of this document claimed the admin (secret-key) client was used in exactly two places, then three. Both counts were wrong even at the time they were written — round 6 (R6-09) found a fourth, pre-existing consumer (the public notification-email confirmation route) this document had simply never listed, and this round's own R6-01 fix added a fifth. Both the count and the list below are current as of the migrations noted; re-verify with `grep -rln createAdminClient features app lib` (excluding `lib/supabase/admin.ts` itself) before trusting this list in the future, rather than assuming it stays accurate as the app grows.

### The admin (secret-key) client — bypasses RLS entirely, server-only

1. **Public card lookup** (`features/feedback/card-lookup.ts`) — renders the public NFC landing page (org/location name, Google Review URL, active status). Read-only. There is no authenticated user on this page, so `auth.uid()`-based RLS has nothing to check against; there is also deliberately no `anon` `select` policy on `nfc_cards`/`locations`/`organizations`.
2. **Public feedback submission** (`features/feedback/actions.ts`) — calls `submit_feedback_atomic` (below) via the admin client. The bypass is narrower than it looks: the RPC itself is `EXECUTE`-restricted to `service_role`, so even holding the admin client's credentials isn't sufficient on its own without also being that role — the two layers (client credential, function grant) are independent, not redundant.
3. **Negative-feedback alert email** (`features/notifications/negative-feedback-alert.ts`) — looks up an org's `notification_email` or its owner/admin/manager members' auth emails to send the alert, and performs the atomic alert-cooldown claim (`UPDATE nfc_cards ... WHERE last_negative_alert_at IS NULL OR < cutoff`). Read-only except for that one cooldown timestamp; never returns data to the client.
4. **Notification-email confirmation** (`app/api/notification-email/confirm/route.ts`, round 3 R3-03) — calls `confirm_notification_email_change` (below) from a public, unauthenticated route (whoever clicks the emailed link may not be signed in to this app at all). The token itself, not RLS or `auth.uid()`, is the actual credential checked.
5. **Notification-email token issuance and delivery reporting** (`features/organizations/settings-actions.ts`, round 6 R6-01) — calls `issue_notification_email_change_token`/`finalize_notification_email_change_send` (below) from the settings Server Action, after the user's own RLS-bound client has already validated and rate-limited the request via `request_notification_email_change`. Both are `service_role`-only precisely so no browser or authenticated Supabase client can reach them directly — see "Notification recipient verification" below for why that split exists.
6. **Billing** (`features/billing/actions.ts`, `app/api/webhooks/stripe/route.ts`, and — fourth independent review, Finding 5 — `features/billing/reconcile.ts`, `features/billing/admin-actions.ts`, `app/api/admin/reconcile-billing-sweep/route.ts`) — `organization_billing` deliberately has no `authenticated` write policy at all (`DATABASE_SCHEMA.md`), so creating/linking a Stripe customer (the checkout Server Action), recording subscription state changes (the webhook handler), and every other path that can affect entitlement all funnel through the one shared `reconcileOrganizationBilling`/`activateOrganizationBilling` service, itself admin-client-only. This is the narrowest possible bypass shape: an owner's own signed-in session, even with full knowledge of the schema, has no path to grant their own organization an active subscription directly — including through the new self-service resync action (`admin-actions.ts`'s `resyncOrganizationBillingAction`), which re-checks `canManageBilling(organization.role)` itself before ever calling the shared service, rather than relying on the admin client's own bypass as an authorization check.
7. **Scheduled reconciliation sweep** (`app/api/admin/reconcile-billing-sweep/route.ts`, fourth independent review, Finding 5) — a `POST` route, public in `proxy.ts`'s `PUBLIC_PATHS` because its actual caller (a scheduled GitHub Actions job, `.github/workflows/reconcile-billing-sweep.yml`, at the **repo root**, sibling to `velemenytap/`) has no user session at all. `RECONCILE_SWEEP_SECRET` — a bearer token compared against the `Authorization` header with `node:crypto`'s `timingSafeEqual` (fixed during this round's own adversarial audit, which found the original plain `!==` comparison timing-unsafe for a secret reachable from the public internet — length is checked first, since `timingSafeEqual` throws rather than returning `false` on a length mismatch, and a fixed-length check alone leaks nothing about the secret's actual content), never logged, read only server-side — is the actual security boundary here, the identical pattern the Stripe webhook route already uses (its own signature check, not `proxy.ts`'s auth gate). The route refuses to run at all (503) if the secret isn't configured server-side, rather than falling open to an unauthenticated sweep of every organization's billing state; see `DEPLOYMENT.md` for the two owner-side secrets (Vercel's `RECONCILE_SWEEP_SECRET`, the matching GitHub Actions repository secret) this depends on — both now configured; `PRODUCTION_RECONCILE_SWEEP_URL` remains unset, which is fine since the workflow's own fallback already matches the correct production URL.

Every dashboard read/write otherwise goes through the RLS-bound client (`lib/supabase/server.ts`), scoped to the signed-in user's own session. Organization creation does not use the admin client at all — it used to, until it was rewritten as a `SECURITY DEFINER` database function instead.

`service_role` (the admin client's Postgres role) also holds two narrowly-scoped grants outside `public` that exist only to support the negative-feedback alert cooldown below: `usage` on the `private` schema and `select, insert, update` on `private.alert_email_log` (the `update` grant is what lets `finalize_negative_alert_send` transition a reservation's `status` from `'reserved'` to `'delivered'`/`'failed'` — an earlier version of this document said only `select, insert`, which undercounted the grant actually needed for finalization to work at all). These were added deliberately, not defaulted — `bypassrls` (which `service_role` has) only bypasses *row-level security*; schema and table `GRANT`s are a completely separate privilege type that RLS bypass does not imply, so `claim_negative_alert_send`/`finalize_negative_alert_send` (below) needed them added explicitly even though their caller already bypasses RLS everywhere else.

### `SECURITY DEFINER`/`SECURITY INVOKER` database functions — the other bypass category

RLS can only be bypassed by a role with `bypassrls` (which the admin client's `service_role` has) or by a function whose privilege model routes around it. Eleven functions exist in `public` as of round 8; all are narrowly scoped and documented in full in `DATABASE_SCHEMA.md` § "Database functions callable as RPCs" (that document's own catalog, plus `e2e/rpc-privilege-matrix.spec.ts`'s completeness check — round-5 R5-10 — is the source of truth for the current count; this list is a summary of *why* each one's privilege mode is what it is, not a re-count kept independently in sync). **This count has been wrong twice before** (round 6 said eleven while a twelfth — the round-3 3-argument `request_notification_email_change`, kept defined but ungrantable — silently existed uncounted; round 7 caught that specific undercount but, before it could be corrected in this document, round-7 finding R7-03's own drift-repair work found the twelfth function didn't even exist in the isolated test project, and recreating it to match production immediately broke the whole notification-email-change feature with `PGRST203` — see `DATABASE_SCHEMA.md`'s "Rollout ordering" for the full discovery). The round-3 function is now **dropped outright** (migration `20260906100000`, not merely stripped of grants), so eleven is, as of this fix, both what the code says and what actually exists — re-verify with the completeness test rather than trusting this sentence to stay accurate on its own.

**`SECURITY DEFINER`** — three functions genuinely need it, all for the same underlying reason: each must run as the calling **authenticated user's own session** (not through the admin client) to do something plain RLS structurally can't authorize for that role, with an explicit `auth.uid()` check as the function's first statement (never trusts an implicit caller identity), `set search_path = ''`, and `EXECUTE` restricted to an explicit role allowlist (see "RPC permission enforcement" below) as the standard mitigations for a public-facing `DEFINER` function:
- **`create_organization_atomic`** — bootstraps a brand-new user's first organization; there is deliberately no `INSERT` policy on `organizations`/`organization_memberships` for `authenticated`.
- **`reserve_notification_email_change`** (named `request_notification_email_change` through round 7; renamed by a third independent review, Finding 1 — see `DECISIONS.md`) / **`clear_notification_email`** (round 3, R3-03; the former's signature narrowed in round 6, R6-01/R6-04 — see below) — write to `organizations`' notification-email columns, which the round-3 enforcement trigger blocks every other caller (including the admin client) from touching directly.

**`SECURITY INVOKER`** — the round-8 count (eight) is long stale now that billing has added its own INVOKER functions (below); none of the additions change the underlying reasoning — every one of them is not a privilege escalation in practice, since each function's only caller already has whatever privilege the function needs.
- **`submit_feedback_atomic`**, **`claim_negative_alert_send`**, **`finalize_negative_alert_send`**, **`issue_notification_email_change_token`**, **`finalize_notification_email_change_send`** — called only by the admin client, which already bypasses RLS; `INVOKER` here just means the function runs with privileges the caller already had, backed by the small explicit grants `service_role` needs beyond RLS bypass alone (schema/table `GRANT`s are a separate privilege type RLS bypass does not substitute for — see the `private.alert_email_log` note above, and `DATABASE_SCHEMA.md` for the equivalent grants on `private.notification_email_change_log`/`_config`). The last two are round 6's R6-01 fix (below): `EXECUTE` is granted to `service_role` **only** — never `authenticated`, never `anon` — so no browser or ordinary authenticated Supabase client can call either, or obtain a plaintext confirmation token, regardless of which organization it targets.
- **`get_feedback_overview_snapshot` / `get_feedback_period_analytics`** (round 2, R2-02/R2-03/R2-04) — called through the dashboard's own RLS-bound client, so RLS applies to every table they touch exactly as a hand-written query would — passing an `organization_id` the caller isn't a member of returns zero rows regardless of what the function's own `WHERE` clause says.
- **`confirm_notification_email_change`** (round 3, R3-03; TOCTOU fixed round 6, R6-05 — see below) — called via the admin client from the public, unauthenticated confirmation route; the token itself (not RLS or `auth.uid()`) is the actual credential checked.
- **`claim_checkout_attempt` / `record_checkout_session` / `finish_checkout_operation` / `release_checkout_attempt` / `renew_checkout_attempt` / `request_billing_reconciliation` / `claim_reconciliation_lease` / `renew_reconciliation_lease` / `write_reconciliation_result` / `write_activation` / `release_reconciliation_lease` / `clear_reconciliation_dirty` / `fail_billing_reconciliation` / `get_billing_reconciliation_candidates` / `record_billing_anomaly`** (third independent review Finding 2; fourth independent review Findings 3/4/9 — full detail in "Billing (Stripe subscriptions)" below and `DATABASE_SCHEMA.md`) — all `service_role`-only, called exclusively from `features/billing/actions.ts`/`reconcile.ts` via the admin client, the same reasoning as the first bullet above: `INVOKER` means each one runs with `service_role`'s own already-held privilege, not an escalation of it. None of them are reachable from `authenticated`/`anon` at all — see the grant table below.

### RPC permission enforcement (round 2, R2-07)

An independent review found that `revoke execute on function ... from public;` — the pattern used for both round-1 RPCs — does **not** actually remove `anon`/`authenticated`'s ability to call them on this project. Confirmed by direct inspection of `pg_proc.proacl` and `has_function_privilege()`: both `submit_feedback_atomic` and `create_organization_atomic` showed `EXECUTE` granted to `anon`, `authenticated`, **and** `service_role`, none of it routed through the `PUBLIC` pseudo-role at all. Root cause: this project has `ALTER DEFAULT PRIVILEGES` configured (visible in `pg_default_acl` for the `public` schema) that grants `EXECUTE` on every newly-created function in `public` directly to `anon`/`authenticated`/`service_role` as independent, explicit ACL entries — separate from, and unaffected by, a `REVOKE` that only targets `PUBLIC`.

This was **not** a demonstrated RLS bypass for either function at the time — calling `submit_feedback_atomic` as `anon` always failed with "card not found" (no `anon` `SELECT` policy on `nfc_cards`, so the lookup returns nothing regardless of the grant), and `create_organization_atomic` as `anon` always failed on its own `auth.uid() IS NULL` check before touching any table. Both are fixed anyway, because relying on those side effects happening to be safe is not the same as the grant itself being correct or robust to a future change in either function's body. Fix: every RPC now has its role allowlist enumerated explicitly rather than trusting a `PUBLIC`-only revoke —

## Deployment/version disclosure (round 4, R4-01)

`/api/health` is a new public, unauthenticated route reporting the deployed commit SHA, environment name, and expected-migration snapshot (`DEPLOYMENT.md` § 6, `ARCHITECTURE.md` § "Deployment verification"). Everything it returns is either already public by construction (Vercel's own System Environment Variables are visible to anyone with dashboard access, and a git commit SHA for an open-source-adjacent internal tool is not sensitive) or was already effectively public before this endpoint existed (the migration filenames are visible in the committed `supabase/migrations/` directory). It never touches a database connection, a secret key, or any customer data — this is deliberate: the whole point is to be safe to poll unauthenticated, repeatedly, from CI and from `scripts/rollout.mjs`, without adding a new credential or a new attack surface to protect.

**Round 6 (R6-06) found round 5's own fix to this endpoint rested on a false premise.** Round 5 (R5-05) computed "is this a genuinely deployed build" from `BUILD_VERCEL_ENV`, a build-time snapshot of `process.env.VERCEL_ENV`, reasoning that Vercel's build step always has `VERCEL_ENV` available regardless of the project's "Automatically expose System Environment Variables" toggle. Per Vercel's own current documentation, that's wrong: `VERCEL_ENV` is a System Environment Variable gated by that exact toggle at **both** build and runtime, with no build-time carve-out — a project with the toggle disabled would have had `BUILD_VERCEL_ENV` null too, and the old logic fell through to `environment: "development", ok: true`, silently hiding precisely the misconfiguration this endpoint exists to catch. See `DECISIONS.md` for the full correction and why the fix now uses `APP_ENV` (an ordinary, non-system environment variable the owner sets directly per Vercel environment) instead of any Vercel-managed variable for this decision.

**Round 7 (R7-07, LOW) found the "local development" half of that same fix was itself fail-open.** It decided "local dev" from `process.env.NODE_ENV !== "production"` — meaning *any* value other than exactly `"production"` (an unset `NODE_ENV`, a malformed one, or `"test"`, which is Vitest's own default) fell through to `environment: "development", ok: true` rather than to the strict `APP_ENV`/commit-SHA checks a genuine production-mode build requires. A build with `NODE_ENV` merely unset or mistyped would silently report healthy development instead of failing closed. Fixed by flipping the condition to fail-closed: only `NODE_ENV === "development"` (the one value `next dev` itself actually sets) is treated as local; every other value — missing, malformed, `"test"`, or anything else — is now a production-mode check requiring `APP_ENV` and a commit SHA, the same as a genuine deployment. `app/api/health/route.test.ts` tests development, production, `"test"`, a missing `NODE_ENV`, and a malformed value (`"developmnet"`) as distinct cases, each crossed with valid/missing `APP_ENV` and commit SHA.

## Public endpoint hardening

`submitFeedbackAction` (`features/feedback/actions.ts`):
- zod validation on `public_id` (UUID), `rating` (1–5 int), `feedback_text` (≤ 1000 chars).
- Card existence and active-status re-checked **atomically with the insert**, not just at page load or in a separate round trip beforehand — `submit_feedback_atomic` locks **both** the card and location rows it reads status from (`for update of c, l`) for the duration of the transaction, so either being deactivated concurrently either completes first (and this correctly sees "inactive") or waits until the insert has already committed. An earlier version of this endpoint did the status check and the insert as two separate requests with no lock at all — a real race, confirmed with a test that deactivates the card in the window between page load and submission (`e2e/public-submission-safety.spec.ts`). Round 2 (finding R2-05) found a second, narrower race in the fixed version: the lock covered only the card row, not the location row whose `status` the same function also reads — a location deactivated mid-transaction could still receive a feedback insert, since nothing held a lock on it. Reproduced with two real concurrent database connections (`e2e/location-deactivation-race.spec.ts`, requires direct Postgres access — skips gracefully if unavailable) and fixed by locking both rows in the same `SELECT`. This is the only code path that ever locks `nfc_cards` and `locations` together; see the migration's comment for the deadlock-ordering analysis (no other transaction ever acquires both locks, so no reverse-order contention is possible).
- Database-backed per-card rate limit: `submit_feedback_atomic` rejects a submission once a card has received 20 or more within the trailing 5 minutes. Deliberately generous — sized to never trip on a real, if unusually busy, physical location — while cutting off a script that would otherwise submit as fast as the network allows.
- Alert-email cooldown and organization-wide budget — see "Negative-feedback alert abuse controls" below.
- Cookie-based duplicate-submission guard (below) — no personal data, opaque marker, card-scoped.

## Negative-feedback alert abuse controls (round 2, R2-08)

The round-1 alert cooldown was a plain column (`nfc_cards.last_negative_alert_at`) updated via a raw admin-client `UPDATE`, guarded only by RLS's row-level `nfc_cards_update` policy — RLS is row-level, not column-level (the same class of gap findings #3/#4 already fixed for other columns on `feedback`/`nfc_cards`), and this was confirmed empirically: a real authenticated org member's own session could reset `last_negative_alert_at` to `NULL` via a direct `UPDATE`. Combined with an unverified `notification_email` and a per-card limit that does nothing to bound total volume across an org's cards, this was a real spam-relay vector: a malicious tenant could point `notification_email` at an arbitrary third party, reset the cooldown at will, and fan qualifying submissions out across as many cards as they create to drive real emails through this app's verified sending domain at volume.

Fixed with two independent, atomic, server-owned controls, both in `claim_negative_alert_send()` (`DATABASE_SCHEMA.md` § "Database functions callable as RPCs"):

1. **`last_negative_alert_at` is now genuinely server-owned.** A trigger (`private.prevent_direct_cooldown_update`, installed by a separate later migration — see "Rollout ordering" below) rejects any change to that column unless a transaction-local flag (`app.allow_cooldown_update`) is set — which only `claim_negative_alert_send()` itself ever sets. This blocks a direct `UPDATE` from **any** caller, including the admin client — there is now exactly one code path that can change this column, not "the admin client happens to be the only thing that currently does."
2. **An organization-wide hourly budget** (`private.alert_email_log`), independent of which card(s) the qualifying submissions came from — a business creating more cards does not create unlimited email capacity.

**Round 3 found and fixed two further gaps in the budget itself, not just around it:**

- **R3-02 (raceable budget):** the original budget check counted rows and compared to the limit, then locked and updated only the *one* card row this call concerned — never anything organization-scoped. Two concurrent claims for two *different* cards in the same org never contended on any shared lock, so both could read the same "under budget" snapshot and both succeed, overshooting the budget by as many concurrent callers as there were distinct cards. Confirmed empirically (budget of 1, zero prior sends, two concurrent claims for two different cards both returned a claim) and fixed with a `pg_advisory_xact_lock` keyed on the organization id, taken before the count-check — a second concurrent call for the same org now blocks until the first's transaction resolves. Verified with a **real concurrent test**, not a sequential loop: `e2e/negative-feedback-alert-abuse.spec.ts`'s R3-02 test fires five simultaneous claims (`Promise.all`, genuinely concurrent HTTP requests — PostgREST opens an independent connection/transaction per request) against a budget of one and asserts exactly one claim, and exactly one reservation, results.
- **R3-06 (attempts logged as sends):** `claim_negative_alert_send` used to insert its log row as an unconditional record of an alert "actually sent" the moment the cooldown/budget checks passed — before the caller had even looked up a recipient, let alone called Resend. A missing `notification_email`/no owner-admin-manager members, or a genuine Resend API failure, all consumed a slot in the budget for an email that was never sent. Rows are now attempts/reservations with an explicit `status` (`'reserved'` → `'delivered'`/`'failed'`, set by the new `finalize_negative_alert_send()`, called from a `finally` block in `features/notifications/negative-feedback-alert.ts` so every claimed reservation eventually resolves). The budget counts `'reserved'`+`'delivered'` rows in the trailing hour but excludes `'failed'` ones once known — an in-flight attempt must still count while unresolved (or two closely-spaced attempts could both slip past a budget check that only counted confirmed deliveries), but a transient delivery failure must not permanently consume real capacity the org never actually used. Tested directly (`e2e/negative-feedback-alert-finalize.spec.ts`): a failed reservation stops counting; a delivered one keeps counting; an unresolved (never-finalized) one still counts while pending; and finalize is idempotent against a duplicate call.

**This round's own independent adversarial self-review (not one of the 8 originally-named findings) then found a THIRD instance, inside the very function R6-04 had already partially fixed.** `request_notification_email_change()` correctly captures `clock_timestamp()` for its cooldown check and budget count, but the row it inserts right after (`insert into private.notification_email_change_log (organization_id, status) values (...)`) never set `reserved_at` explicitly, so it fell back to the column's `default now()` -- frozen at the same stale, pre-lock-wait instant this whole class of bug is about. Fixed the same way (migration `20260906120000`): captures one `clock_timestamp()` value immediately after the advisory lock and reuses it for both freshness checks and the reservation's `reserved_at`. Verified with a real two-connection concurrency test (`e2e/notification-email-verification.spec.ts`, "R7-05-class"): a second raw connection holds the identical advisory lock key for a fixed 1.5s window, forcing the RPC call to genuinely queue behind it, and the resulting `reserved_at` is asserted (using only server-side `clock_timestamp()` readings on both sides of the comparison, never the test runner's own wall clock, which turned out to disagree with the remote database server's clock by tens of seconds during this round's own testing) to land at or after the lock was actually released. **Confirmed as a genuine regression test, not just a plausible-looking assertion**: reverted to the pre-fix function body directly against the isolated test project, re-ran the test, watched it fail for exactly the predicted reason, then restored the fix and watched it pass — the same discipline this project applies to every other fix in this document.

**Round 7 (R7-05, MEDIUM) found `claim_negative_alert_send` had the same `now()`-under-concurrency bug round 6 (R6-04) had already found and fixed in `request_notification_email_change`.** Its cooldown check, its trailing-hour budget cutoff, and the `last_negative_alert_at` timestamp it writes all used `now()` — fixed at this transaction's own *start*, not at the moment it actually runs — evaluated *after* acquiring the per-organization advisory lock. Under genuine concurrency, a transaction queued behind another can resume with real wall-clock time well past its own frozen `now()`, so a claim serialized behind another could spuriously see the card as still "on cooldown" purely from timing, not because the cooldown was actually in effect. This is not a hypothetical extrapolation from the earlier fix — it is the identical bug shape in a second function this codebase happens to have written the same way. Fixed the same way (migration `20260906110000`): captures one `clock_timestamp()` value immediately after acquiring the lock, and reuses that single value for the budget cutoff, the cooldown comparison, the `last_negative_alert_at` write, and the reservation's `reserved_at` timestamp — never a fresh `now()`/`clock_timestamp()` call anywhere else in the function body. Verified with the same test shape as the earlier fix: 5 concurrent claims for the *same* card with `p_cooldown_minutes: 0` (no cooldown restriction at all) must all succeed — before the fix, a queued claim could be spuriously rejected purely from a frozen, stale `now()`. **This class of bug was then searched for across every other migration and function in the schema** (every use of `now()`/`current_timestamp` after a lock acquisition or as part of a freshness/window decision) — this round's own search found this instance and the one R6-04 already fixed, but **missed a third**, inside `request_notification_email_change` itself: a lock-scoped read that used `clock_timestamp()` correctly, sitting right next to a write (`insert ... reserved_at`) that still relied on the column's `now()` default. That third instance was caught only by this round's own independent adversarial self-review, not by the original class-wide search — see below. Every other timestamp read in this codebase (audit columns, `created_at`/`updated_at` defaults, expiry checks that don't follow a lock) has been checked and does not have the same hazard, since none of them both acquire a lock and then make a decision using a timestamp captured before that lock was held — but given two search passes each missed at least one real instance, treat that as a claim to re-verify independently rather than fully settled.

Verified without sending a single real email (`e2e/negative-feedback-alert-abuse.spec.ts`/`e2e/negative-feedback-alert-finalize.spec.ts`; this test project deliberately has no `RESEND_API_KEY`): a tenant's own authenticated session cannot reset the cooldown via a direct `UPDATE`; neither `anon` nor `authenticated` can call `claim_negative_alert_send`/`finalize_negative_alert_send` directly (see the RPC permission table above); the per-card cooldown still lets exactly one claim through per window; an org-wide budget caps total claims — now proven under real concurrency, not just a sequential approximation of it; and (R7-05) a zero-minute cooldown never spuriously rejects a concurrent claim for the same card.

### Rollout ordering (round 3, R3-05)

The alert-cooldown trigger and the notification-email-change trigger (below) are each installed by a migration deliberately separate from the one that introduces the RPCs they protect. Applying both together to production in one step would break the *currently deployed* application code, which still performs a direct `UPDATE` to the column(s) the trigger would then reject — a real outage window (every negative-feedback alert, or every settings save touching the notification email, failing) between the migration landing and new application code deploying. See `DATABASE_SCHEMA.md` § "Rollout ordering" and `DEPLOYMENT.md` § 7 for the concrete, current expand → deploy → enforce sequence.

### Rollout target trust (round 6, R6-07)

`scripts/rollout.mjs` authorizes real production database writes based on `--db-url` and, until round 6, two other caller-supplied arguments: `--allowed-origin`/`--health-url`, checked only against **each other**. Agreement between two arguments the same caller supplies proves nothing about whether either actually corresponds to the database named by `--db-url` — a misconfigured or compromised invocation could point `--db-url` at one Supabase project while `--allowed-origin`/`--health-url` named a completely different (if legitimate-looking) application, and the script would authorize the rollout anyway.

Fixed with a committed, reviewed manifest (`scripts/rollout-environments.json`) binding a `--target` name to its Supabase project ref, exact application origin, health URL, and expected `environment` value together — `--allowed-origin`/`--health-url` are no longer accepted as arguments at all, and `--db-url`'s own project ref (parsed the same way `e2e/support/db-connection.ts` already does, for the same reason: never trust the path/query/password/fragment, only the hostname or username component the server actually authenticates against) is checked against the manifest's ref before phase 0 runs. A `--db-url`/`--target` mismatch is now rejected immediately, not silently trusted on the strength of two caller-supplied values agreeing with each other.

### Rollout script hardening (round 6, R6-10/R6-11)

Two further, lower-severity gaps in the same script: `e2e/support/db-connection.ts`'s `decodeURIComponent()` call (used to extract a pooler connection's project ref from its percent-encoded username) ran unguarded — a malformed percent-encoding sequence (`%ZZ`, a lone `%`) threw an uncaught `URIError` instead of the clean "doesn't match" every other invalid input returns, crashing whichever check called it (R6-10). And `--expected-sha` accepted 7–40 hex characters, but `/api/health`'s own `commitSha` is always the full 40-character SHA and the comparison is exact string equality — a short SHA could never match, but that failure was only discovered after the expand migrations had already been applied and a multi-minute timeout had elapsed (R6-11). Both fixed: the decode is now inside its own `try`/`catch`, and `--expected-sha` requires the full 40 characters before phase 0 runs at all.

### Subprocess failures used to disclose the production database password (round 7, R7-02, HIGH)

`scripts/rollout.mjs`'s `sh()` wrapper redacted the connection string in its own happy-path log line, but called Node's `execFileSync()` directly for the actual `supabase` CLI invocations — and `execFileSync` embeds the **full command line, arguments included**, in `Error.message` on any non-zero exit, plus separately on `.stdout`/`.stderr`/`.output`. A failing `supabase migration list`/`supabase db push` (a wrong password, a network blip, the CLI itself erroring) would throw an error whose `.message` contained the raw `--db-url` value, username and password included, straight into whatever caught it — the console, a CI log, Sentry, if this script's own errors were ever piped there. Reproduced directly: a deliberately-failing `execFileSync` call with a canary password embedded in a connection string, confirming the canary appeared in the thrown error's `.message` even though the wrapper's own logging never printed it. Fixed with `sanitizeSubprocessError()`, wrapping every `execFileSync` call: catches the raw error, builds a new one whose `.message`/`.stdout`/`.stderr` all have every Postgres connection string's credentials redacted (`redactConnectionStrings()`, a regex over `postgres(ql)?://<user>@` — not just the specific `--db-url` value, so a credential embedded in a *different* connection string elsewhere in the command/output is also caught) plus any value passed via a flag the caller marks as a credential (`credentialSecretsFromArgs()`), before it ever leaves the wrapper. Tested with distinct canaries in both the username and password positions, across failure paths for both `supabase migration list` and `supabase db push`.

**This round's own independent adversarial self-review found one more path that bypassed the wrapper entirely.** `getPendingMigrations()` calls `sh()` and, on a *successful* (zero-exit) call whose stdout doesn't contain a `{`, throws its own error embedding that raw stdout directly — `sanitizeSubprocessError` never runs here, since nothing actually failed at the subprocess level. No current version of the `supabase` CLI mixes a credential into a successful exit's stdout, so this wasn't a live leak, but a future CLI version echoing a warning/banner line containing `--db-url` into stdout would leak it through this one specific path with none of the protections above in the way. Fixed by redacting `raw` the same way a subprocess failure would be before embedding it in the thrown error; regression-tested by mocking `execFileSync` to return non-JSON text containing a canary connection string and asserting it never appears in the resulting error's message.

### `allowedOrigin`/`healthUrl` were recorded but never actually checked against each other (round 7, R7-04, MEDIUM)

Round 6 (R6-07) bound `--target`'s manifest entry together — origin, health URL, expected environment, project ref — specifically so agreement between two caller-supplied values could no longer stand in for real verification. But the manifest's own `allowedOrigin` and `healthUrl` fields were themselves never cross-checked against each other, and `pollHealth`'s `fetch()` call used the platform default of following redirects. A `healthUrl` that was compromised, misconfigured, or simply pointed at a different host than `allowedOrigin` named could redirect the health check anywhere — including to a server that returns a syntactically-valid, correctly-shaped, spoofed "healthy, matches your commit SHA" response, which is exactly the signal the whole rollout script gates production writes on. Fixed: `loadEnvironments()` now strictly parses every manifest entry and requires HTTPS for any non-local target, requires `new URL(healthUrl).origin === new URL(allowedOrigin).origin` exactly (not a prefix or substring check), and rejects a `healthUrl` carrying credentials, a fragment, or an unexpected query string. `pollHealth` calls `fetch(healthUrl, { redirect: "error" })` (Node's built-in `fetch` throws on any redirect response with this option, confirmed directly against a real local server before relying on it) instead of silently following one. Tested against real local `node:http` servers, not mocked `fetch`: same-origin success, an off-origin redirect, a same-origin redirect, a redirect loop, an HTTP-downgrade redirect, and a spoofed response carrying the correct commit SHA from the wrong origin — all rejected. `parseArgs()` also now rejects the removed `--allowed-origin`/`--health-url` flags explicitly (with a hint pointing at `--target`) and any other unrecognized flag or bare positional argument, rather than silently ignoring them as the pre-round-6 parser did.

### Rate limiting: database-backed, not Redis

An earlier version of this document said rate limiting was deliberately not implemented for MVP, reasoning that Vercel's serverless functions don't share memory across instances so an in-process limiter would be unreliable without adding real infrastructure. That reasoning about in-process limiters was correct, but it's not actually a reason to have no rate limiting at all: Postgres is already the shared state every request goes through regardless of which serverless instance handles it, so a count-over-a-trailing-window check inside the same atomic function that does the insert (above) needed no new infrastructure — no Redis, no Upstash, nothing beyond the existing database. The cookie-based duplicate guard remains, layered underneath, for the common case (an accidental double-tap) that doesn't need a database round trip to catch.

## Auth

- Supabase Auth, email/password. Server-side identity via `getClaims()` (not `getUser()`/`getSession()`), per current Supabase guidance.
- `proxy.ts` is protect-by-default: every route not in `PUBLIC_PATHS` (`/`, `/login`, `/signup`, `/auth`, `/r`, `/api/e2e-config-check`, `/api/notification-email/confirm`, `/api/webhooks/stripe`) requires a session. The last of those is Stripe's own server calling in — its signature check, not this gate, is the real security boundary (see "Billing" below).
- No `user_metadata`/`raw_user_meta_data` is used in any authorization decision (it's user-editable and would be a privilege-escalation hole); the one place it's read (`profiles.full_name` at signup) is display-only, never a security decision.
- Passwords: Supabase's own hashing/storage; the app never sees or logs a plaintext password beyond the single request that submits it.

## Data minimization

The public feedback flow collects no personal data — no email, no name, no device fingerprinting. The duplicate-submission cookie carries no identifying value, just presence. Feedback is private to authenticated members of the owning organization; there is no public read path for feedback content.

## Error handling / logging

Customer-facing errors on the public page are simple and non-technical ("Could not send your feedback. Please try again."). Server-side errors (failed inserts, failed email sends) are still logged via `console.error`/`console.warn` (not deliberately redacted — Vercel's own log retention is short-lived and access is already restricted to the project's team).

**Sentry** (`@sentry/nextjs`) captures errors across client, server, and edge runtimes (`instrumentation.ts`, `instrumentation-client.ts`, `sentry.server.config.ts`, `sentry.edge.config.ts`), plus root-layout rendering errors via `app/global-error.tsx`. Every event passes through `lib/sentry-redact.ts`'s `beforeSend` hook first, per the product skill's "avoid logging raw sensitive feedback unnecessarily":
- `event.request.data` is **dropped entirely**, not redacted in place — its shape is `unknown` and unpredictable (it could be a raw string, an array, or an object using field names this app has never heard of), so the only actually-safe handling is not attempting to selectively keep parts of it.
- `extra`/`contexts`/breadcrumb `data` are redacted key-by-key (`feedback_text`/`internal_note`, camelCase included) via a cycle-safe recursive walk (a path-scoped `Set`, not a whole-tree one, so sibling branches sharing a common object don't leak into each other or falsely flag as circular) that also recognizes a sensitive field hidden inside a `JSON.stringify`'d string, not just a plain object key.
- An earlier version of this redaction had four confirmed bugs — trusted the original object shape too much (`request.data` redacted in place, not dropped, so any field it didn't recognize passed through untouched), missed JSON-stringified content, and a circular reference returned the *original*, unredacted object through the back-reference rather than a placeholder (the previous test suite asserted this as correct behavior). Fixed and covered by canary-based unit tests in `lib/sentry-redact.test.ts` that assert against the fully serialized event output, not just specific object keys — including the circular-reference case, corrected to assert the back-reference is `"[circular]"`, never the original object.
- Round-5 finding R5-11 extended this to `event.request.url` and breadcrumb `url`/`to`/`from` fields — this app hands out real, live, single-use credentials as URL query parameters by design (`/api/notification-email/confirm?token=...`, Supabase's own `/auth/confirm?token_hash=...`), and nothing before R5-11 sanitized a query string embedded in a URL, only key-named object fields.
- **Round 6 (R6-02) found `beforeSend` alone does not cover everything Sentry can send.** Three further gaps, all fixed: (1) `event.request.query_string` is a *separate* field from `event.request.url` — Sentry's own type allows it to be a string, an object, or an array of `[key, value]` pairs, and R5-11's fix never touched it, so a canary placed there survived redaction outright; now sanitized in all three shapes. (2) `beforeSend` never sees **transaction events** at all — Sentry's tracing pipeline (enabled here via `tracesSampleRate`) is a separate pipeline with its own `beforeSendTransaction` hook, now wired to the same `redactSensitiveData` function in every config (client/server/edge), since a `TransactionEvent` carries the same `request`/`breadcrumbs`/`contexts`/`extra` shape. (3) Neither hook sees **individual spans** within a transaction — the HTTP instrumentation attaches the full request URL, query string included, to span `data`, reachable only through the separate `beforeSendSpan` hook, now wired to a new `redactSpan` function. `sendDefaultPii` was also set explicitly `false` in every config at the time (already the SDK default, made explicit rather than implicit-by-omission).
- **Round 7 (R7-01, HIGH) found round 6's `redactSpan` fix was itself incomplete, and that `sendDefaultPii: false` was never actually equivalent to disabling URL/query collection in the first place.** `redactSpan` sanitized `url.full`/`http.url`/`url.query` but not `http.target` — a real attribute name the installed Sentry SDK (10.73.0) attaches to incoming/outgoing HTTP spans under OpenTelemetry semantic conventions, carrying the raw pathname *and* query string. A canary placed there (reproduced directly against the SDK's own span shape before writing the fix) survived every existing redaction path. Separately, `sendDefaultPii: false` only ever meant "don't attach IP addresses/cookies by default" — it was never a documented switch for URL query collection specifically, so treating it as one was itself a latent gap even where `redactSpan` did apply. Fixed two ways: `SPAN_URL_ATTRIBUTE_KEYS` (`lib/sentry-redact.ts`) now also covers `http.target` and `url.original`, and a new `SPAN_QUERY_ATTRIBUTE_KEYS` (`url.query`, `http.query`) is sanitized as a query string specifically rather than a full URL; and every config (`sentry.server.config.ts`, `sentry.edge.config.ts`, `instrumentation-client.ts`) replaces `sendDefaultPii: false` with an explicit `dataCollection` block (`urlQueryParams: false`, `cookies: false`, `httpHeaders: { request: false, response: false }`, `httpBodies: []`, `databaseQueryData: false`) — the SDK's own current mechanism for this, verified against the installed version's own type definitions rather than assumed from an older API shape. **A specific gotcha documented in the config files themselves**: setting `dataCollection` at all switches the SDK's *other* internal defaults away from whatever `sendDefaultPii` used to imply, back to fully-permissive — every sub-field has to be restated explicitly, not just the one this finding was about, or fixing this exact gap would silently reopen a different one. `lib/sentry-redact.test.ts` covers `http.target` directly (the finding's own reproduction), `url.original`, `http.query`, span-description redaction, and one comprehensive "realistic incoming HTTP server span" test asserting every field at once against the fully serialized span output — not just the previously-covered fields in isolation.
- **This document's own defense-in-depth framing needs a correction**: the redaction layer (`redactSpan`/`redactSensitiveData`) is the actual, load-bearing control — the SDK-level `dataCollection` settings are a second, coarser layer underneath it, not a substitute for it. R7-01 is the second time a Sentry SDK-level toggle believed to cover a whole class of leakage (`sendDefaultPii`, then implicitly the assumption that R6-02's `beforeSendSpan` wiring was complete) turned out not to, once checked against the SDK's actual current behavior instead of its name.
- **This round's own independent adversarial self-review found a further, structural gap `redactSensitiveData` had never covered: `event.exception` — the actual captured error message text.** No current code path in this app embeds a token or URL in a thrown `Error`'s message (checked directly against every route/action that handles a live token), so this was never an active leak, but it's exactly the kind of hole this file exists to close before something depends on it being safe: a future `throw new Error(\`failed for ${url}\`)` anywhere in the app would otherwise reach Sentry through `event.exception.values[].value` with no redaction pass in its way at all, bypassing every protection described above. Fixed by running each exception value's message through `sanitizeUrl` (catches a token embedded in a URL) and the same JSON-string sensitive-key check `extra`/`contexts` already get (catches one embedded in a serialized object), inside `redactSensitiveData` itself rather than a separate hook. `Sentry.captureException` is called from exactly one place in this app (`app/global-error.tsx`), which goes through the normal client-SDK `beforeSend` pipeline — confirmed there's no other call site (`captureMessage`/`addBreadcrumb`/`setContext`/`setTag`) that could construct an event bypassing these hooks.

The Sentry DSN (`NEXT_PUBLIC_SENTRY_DSN`) is intentionally public — a DSN only lets a client *report* events, not read them, which is why Sentry's own docs embed it directly in client-side code.

## Redirect safety

`signInAction` (`features/auth/actions.ts`) and `app/auth/confirm/route.ts` both accept a `next` query/form parameter naming where to send the user after signing in — an open-redirect surface if not validated, since an attacker can craft a link through this app's own trusted domain that ends somewhere else entirely (a convincing phishing vector: the URL bar shows this app's real domain up until the redirect fires). A naive check (`next.startsWith("/") && !next.startsWith("//")`) is not sufficient: WHATWG URL parsing (what a real browser uses to resolve a redirect) treats a backslash the same as a forward slash for `http`/`https`, so `/\evil.example.com` passes that check yet a browser resolves it identically to `//evil.example.com` — an external, protocol-relative URL. Both call sites use one shared helper (`lib/safe-redirect.ts`) that parses the candidate against the app's own trusted origin and requires the *parsed* result's origin to match exactly, rather than pattern-matching the raw string.

**Round 2 (finding R2-01)** found that origin-matching the parsed candidate is necessary but not sufficient on its own: `/a/..//evil.example/path` resolves same-origin (the `..` pops back to root before the parser considers a new authority), yet its resulting *pathname* is `//evil.example/path` — itself a protocol-relative URL. Any consumer that later resolves the value this function returns (a browser following a `Location` header, or this same logic invoked again downstream) reads that leading `//` as "same scheme, new host" and leaves the site anyway. The same shape also arises non-recursively, with no `..` at all, from a same-origin *absolute* URL whose pathname itself starts with `//` (e.g. `https://trusted.example//evil.example/path`). The fix re-parses the exact string the function is about to return — not just the original candidate — against the trusted origin, and rejects it too if that round-trip doesn't stay same-origin; this is not a second pattern-match but literally simulating what a real downstream consumer does with the returned value. 34 unit tests (`lib/safe-redirect.test.ts`, up from 29) plus an extended Playwright suite (`e2e/redirect-safety.spec.ts`, 7 tests) drive the real login and email-confirmation flows against both the round-1 backslash bypass and both round-2 payloads, and confirm a legitimate path containing `//` later in it (not at the start) still passes through unaffected.

## Analytics correctness (round 2, R2-02/R2-03/R2-04)

Round 1's analytics fix (page-by-page fetching past PostgREST's 1000-row cap, `MAX_ROWS = 5000`) turned out to have two further problems, both confirmed against real data before being fixed:

- **R2-02**: 5000 was itself still a silent correctness ceiling — an organization with more than 5000 feedback rows hit the exact same silent truncation the original finding was about, just at a higher threshold.
- **R2-03**: `OFFSET`-based pagination is not consistent under concurrent writes. A row inserted between fetching page 1 and page 2 shifts every subsequent row's effective offset, causing rows to be skipped or double-counted — deterministically, not as a rare race. Adding an `id` secondary sort key (which fixed the *inbox's* pagination, finding #9) does not fix this: ordering-among-ties and offset-stability-across-requests are different properties.

Fixed by moving every statistic into two tenant-scoped SQL functions (`get_feedback_overview_snapshot`, `get_feedback_period_analytics` — `DATABASE_SCHEMA.md` has the full signatures) computed inside a single statement per call, rather than paginating raw rows into Node at all. This closes R2-02 (a `COUNT`/`AVG`/`GROUP BY` over the full matching set has no row-count ceiling to hit) and R2-03 (there is no multi-request pagination left to be inconsistent — Postgres computes each call as one query against one consistent MVCC snapshot, however many times the query plan re-scans the underlying CTE). **Consistency semantics, stated explicitly**: every number returned by *one* call to either function reflects exactly one internally-consistent snapshot — the total, the daily series, and the per-location/per-card breakdowns within a single `get_feedback_period_analytics` call can never disagree with each other about which rows exist. What is *not* guaranteed: the overview snapshot and a separate, later call to the period-analytics function are not guaranteed to reflect the identical instant — an ordinary property of any two independent reads of a live database, not a bug, and categorically different from what R2-03 flagged (a single logical "give me all N rows" operation skipping or duplicating rows against its own total).

- **R2-04**: a failed analytics query used to risk surfacing as an apparently-valid, silently empty or partial stats page. `features/analytics/parse-snapshots.ts` now returns a discriminated `{ unavailable: true }` result on any RPC error or null data (logged via `console.error`, not swallowed), and both `app/dashboard/page.tsx` and `app/dashboard/analytics/page.tsx` render an explicit destructive `Alert` instead of falling through to the normal stats layout with empty-looking numbers. An empty-but-real organization (zero feedback rows, no error) is explicitly distinguished from an actual failure — both are tested (`features/analytics/parse-snapshots.test.ts`, `e2e/analytics-aggregation.spec.ts`).

Tested against real volume beyond both the original 1000-row cap and the retired 5000-row ceiling — `e2e/analytics-aggregation.spec.ts` seeds 5500 and 6000 mixed-rating/status rows respectively for the overview and period-analytics cases — and against concurrency: 100 base rows plus 100 concurrent inserts racing a read confirm the total returned is always internally consistent (`>=` the base count and `<=` the base-plus-concurrent count, never inconsistent with itself).

**Round 3 (R3-04)** found `get_feedback_period_analytics` trusted its caller-supplied `p_days` completely, passing it straight into `generate_series`. The dashboard UI only ever sends 7, 30, or 90, but the function is `EXECUTE`-granted to `authenticated` and callable directly with any value — a large, negative, or zero `p_days` forced an unbounded or malformed series and a correspondingly unbounded JSON response, at whatever cost building and returning that imposes, for the price of one HTTP request. Fixed by validating `p_days` against an explicit allowlist (7/30/90) as the very first thing the function does, raising before `generate_series` or any table scan runs; `p_since` was also removed from the signature entirely (it was redundant with `p_days` in every legitimate call) and is now derived internally from the validated value. Tested directly as the authenticated caller this finding is about — not through the UI, which never sends an invalid value in the first place — for both the three valid values and seven invalid ones (`e2e/analytics-period-validation.spec.ts`): zero, negative, an unsupported-but-plausible value, and very large values, all rejected with the specific validation error, none reaching `generate_series`.

## Test configuration safety (round 2, R2-06; revised round 3, R3-01)

`e2e/support/env.ts` fails closed rather than silently falling back to production credentials: it resolves `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and `SUPABASE_SECRET_KEY` from exactly **one** canonical source — a fully-populated `.env.test.local`, or a fully-populated process environment (CI's case) — and throws an explicit, actionable error naming exactly what's missing or mixed if neither is complete on its own; it never reads `.env.local` (the production project) as a fallback.

**Round 3 (R3-01) found the original single-source check was broken in exactly the case it was meant to protect**: the per-key presence check (`is this key in the file OR in process.env`) could pass while the function still returned only the file's (empty, in CI) contents — missing every required key anyway. This is precisely what broke Playwright's `globalSetup` in CI: it read `loadEnvVars().NEXT_PUBLIC_SUPABASE_URL`, got `undefined`, and failed the entire run before a single test executed. Separately, a developer with production values already exported in their shell alongside a complete `.env.test.local` could have the two sources silently blend, keyed on which value happened to already exist in `process.env`. Fixed by resolving from one complete source only (the file wins if complete; the process environment is used only when the file doesn't exist or isn't complete on its own) and returning every required key from whichever source won — never a partial mix of the two.

**Credential presence is also no longer treated as proof of safety.** The resolved `NEXT_PUBLIC_SUPABASE_URL` is validated against an explicit allowlisted project reference (extracted from the URL's subdomain) before anything else runs — a complete, well-formed, syntactically valid *production* credential set would otherwise pass every check above and this suite would happily run destructive tests against it. `RESEND_API_KEY` and `NEXT_PUBLIC_SENTRY_DSN` are force-cleared for the duration of the test run regardless of what's set anywhere, so a test run can never send a real email or report a real error to production Sentry as a side effect. Finally, the resolved values **overwrite** (not merely fill gaps in) `process.env` — so this process's own fixtures (`e2e/support/seed.ts`) and the spawned `next dev`/`next start` server (`playwright.config.ts`'s `webServer.env`, built from the same resolved object) are guaranteed to agree on every key, even if a stale, different value for one of them was already sitting in `process.env` for an unrelated reason.

A Playwright `globalSetup` (`e2e/support/verify-server-config.ts`) polls a small unauthenticated diagnostic route (`/api/e2e-config-check`) and compares the *actually running* server's configured Supabase URL against the one the test suite itself resolved, failing the whole run with a detailed error if they disagree — this is what makes `reuseExistingServer` safe: a stale or wrongly-configured already-running server is caught before any test executes against it, rather than trusted blindly. Every failure path — missing config, a mixed partial source, the wrong project, a stale mismatched server — is exercised directly (`e2e/support/env.test.ts`, 11 tests).

**Round 7 (R7-03, MEDIUM) found the isolated test project's own migration history had drifted from what it claimed to have applied.** `supabase_migrations.schema_migrations` recorded the round-3 3-argument `request_notification_email_change` as applied, but the function itself did not actually exist in the isolated project — traced to earlier verification work in this project's history that applied schema changes via a raw `pg` connection instead of `supabase db push`, which updates the schema without recording (or, here, apparently mis-recording) the bookkeeping table `supabase db push` itself relies on. `e2e/rpc-privilege-matrix.spec.ts` had been silently accommodating this with a `mayNotExistInThisEnvironment` flag on that one row and a corresponding conditional skip — a genuine security-relevant check quietly not running for the one function actually most relevant to R6-01's fix, and (per this task's own standing rule) a database missing the production object under test is not the same as having verified its security. Repaired by recreating the historically-accurate function directly (its exact committed SQL, not a guess) via a raw connection, verified present before any other change; `mayNotExistInThisEnvironment` and the conditional skip were then removed entirely from the test file. **Repairing the drift immediately surfaced a second, previously-undiscovered, more serious bug**: with the 3-argument function genuinely present again, every 2-named-argument call to `request_notification_email_change` became ambiguous between it and the 2-argument function (PostgREST's overload resolution can't disambiguate two candidates by name+arity alone once one has a `default` making it callable with fewer arguments), returning `PGRST203` for **every caller**, old and new application code alike — a bug round 6's own verification never caught only because the drift above happened to make the ambiguous overload invisible to it. Fixed by dropping the 3-argument function outright (migration `20260906100000`) rather than the grant-revocation-only approach round 6 had used — see `DATABASE_SCHEMA.md`'s "Rollout ordering" for the full sequence and why this changes the production rollout plan. **Prevention**: any future verification work that touches the isolated project's schema outside `supabase db push` should run `supabase migration repair` (as `DECISIONS.md`'s rollout-script entry already documents doing once for this same project) before trusting `supabase migration list`'s own account of what's applied.

**Round 4 (R4-04)** closed a related gap: `SUPABASE_DB_URL` (needed for `e2e/rpc-privilege-matrix.spec.ts` and `e2e/location-deactivation-race.spec.ts`, both security-relevant — a role/grant matrix and a concurrency-safety guarantee, respectively) was optional everywhere, including CI, and both spec files silently skipped every test inside them if it was missing or unreachable. A skipped security test reporting as part of a green CI run is false confidence, not "coverage that degrades gracefully" — no different in kind from finding #10/R3-07's own point about committing privilege checks as real tests rather than one-time manual verification. `e2e/support/db-connection.ts` now throws (fails the run) rather than returning `null` (skip) whenever `process.env.CI` is set and the connection is missing, unreachable, or doesn't resolve to the approved isolated project (the same project-ref allowlist as `env.ts`, reused rather than duplicated) — local runs without the variable still skip gracefully, since not every contributor has or needs a direct Postgres connection for the rest of the suite to be useful.

**Round 6 (R6-08) found the same class of gap one layer up, at the CI job level rather than the test level.** For a fork-originated pull request, GitHub Actions correctly never exposes repository secrets — `check-e2e-secrets` reports `configured: false`, and the `e2e` job's own `if:` condition then makes it **skip** entirely (not fail). Both are correct and intentional in isolation. The problem is what a skip means to GitHub's branch-protection model: a skipped job satisfies a required status check exactly the same as one that ran and passed. Once `e2e` is eventually configured as a required check (`DEPLOYMENT.md` § 5 — still an open owner action, R4-02), a fork PR could merge having never run the RPC privilege matrix, the RLS tests, or anything else database-dependent — silently defeating R4-04's whole guarantee for precisely the untrusted-contribution path it matters most for. Fixed with a new job, `e2e-gate`, that treats anything other than `e2e` having genuinely **succeeded** — including a skip — as a failure; it needs no secrets and checks out no untrusted code (no `pull_request_target`), so a fork PR gains nothing by triggering it, and it is `e2e-gate`, not `e2e`, that `DEPLOYMENT.md` § 5 now documents as the check to require in branch protection. See `DEPLOYMENT.md`'s "Fork contribution flow" for how a maintainer runs the real suite against a fork PR's code before merging it.

## Onboarding integrity

`createOrganizationAction` used to perform two separate admin-client inserts (organization, then membership) with no transaction across them — a failure between the two could leave an ownerless, permanently inaccessible organization behind, and nothing stopped a double-submit from creating two organizations for the same user. Rewritten as `create_organization_atomic` (`DATABASE_SCHEMA.md` § "Database functions callable as RPCs"): atomic (both inserts share the function's implicit transaction), idempotent (a user who already has an organization gets it back rather than a second one), and serialized per user via an advisory lock so two near-simultaneous calls can't both pass the "no existing org" check before either commits.

## Billing (Stripe subscriptions)

This app never handles card data itself — subscribing goes through Stripe Checkout, managing an existing subscription through the Stripe Billing Portal, both Stripe-hosted pages this app only ever redirects to (`features/billing/actions.ts`). The two things that matter most here:

**The webhook is public by necessity — its signature check is the actual security boundary.** `app/api/webhooks/stripe/route.ts` is in `proxy.ts`'s `PUBLIC_PATHS` (Stripe's servers call it with no session at all), so nothing about `proxy.ts`'s auth gate protects it. Every request is verified with `stripe.webhooks.constructEvent(body, signature, STRIPE_WEBHOOK_SECRET)` before any part of the payload is trusted; a missing or invalid signature returns 400 immediately, before touching the database. Without this check, a POST to this URL with a guessed or enumerated `organization_id` could grant that organization a free active subscription — there is no other authorization check anywhere in the handler.

**Idempotent by construction, not by convention.** Stripe explicitly documents at-least-once, possibly-duplicate webhook delivery (retries on anything but a 2xx response, and occasional redelivery even without one). Each event's `id` is inserted into `stripe_webhook_events` (a table with RLS enabled and zero policies — nothing but `service_role` ever touches it) before any state change; a duplicate delivery hits that table's primary key and returns `{ received: true, duplicate: true }` without reapplying the event. An insert failure for any *other* reason returns `500`, asking Stripe to retry rather than silently dropping the event.

**`organization_billing` has no `authenticated` write policy at all** (`DATABASE_SCHEMA.md`) — only the webhook handler and the checkout/portal Server Actions, both via the admin client, ever write to it. An owner's own signed-in session cannot grant their own organization an active subscription by writing to this table directly, no matter what the client sends.

**Status values are validated, not trusted blindly, even from Stripe itself.** Stripe's `Subscription.status` type is forward-compatible (Stripe can add new statuses at any time); the webhook handler maps anything outside the known, exhaustive set mirrored by `organization_billing`'s `CHECK` constraint to `'incomplete'` and logs it loudly, rather than letting an unrecognized status either crash the handler (a rejected `UPDATE`, since the constraint would reject it) or silently write a value the rest of the app has never accounted for.

**The paywall gates the dashboard only — never the public-facing product.** `isBillingActive()` (`features/billing/status.ts`) is checked in `app/dashboard/layout.tsx`, nowhere near `app/r/[publicId]` or `submitFeedbackAction`. A card already sold and sitting on a customer's counter keeps collecting real feedback regardless of its organization's billing status — this is a direct product requirement (`PRODUCT_SPEC.md`, `DECISIONS.md`), not an oversight, and `e2e/billing-paywall.spec.ts` tests it as an explicit regression, the same shape as the Google-Review non-gating test in `e2e/review-gating.spec.ts`.

**Concurrent reconciliation writers are mutually excluded by a real Postgres lease, not fenced by claim order (fourth independent review, Finding 3).** An independent adversarial review demonstrated that the third round's `billing_sync_seq` fencing token — a per-organization sequence number claimed before the write and checked at write time — was unsound in principle: a request that claims an earlier sequence number can still execute, and observe genuinely fresher Stripe state, *after* a request with a later sequence number has already written, and gets discarded purely because its claim came first, with nothing left to ever correct it. `claim_billing_sync`/`billing_sync_seq` are now dropped outright (migration `20260907210000`), replaced with `claim_reconciliation_lease`/`write_reconciliation_result`/`write_activation`/`release_reconciliation_lease`/`clear_reconciliation_dirty` — an exclusive, expiring lease that only one reconciler can hold per organization at a time, claimed before any Stripe network call. A contender that fails to claim it, or loses it before writing, never assumes someone else's write already covers it: `needs_reconciliation` is set durably, in the same statement, by the database function itself — including on a successful claim (migration `20260907230000`, closing a genuine process-crash gap this round's own three-independent-reviewer audit found in the first version of the lease), and cleared (not re-marked) only once a reconciliation attempt has definitively confirmed there's nothing left to do (`clear_reconciliation_dirty`, migration `20260907240000`). **Mutual exclusion alone still let one class of event be lost, and migration `20260908110000` closes it:** a reconciliation that COMPLETED cleared the dirty flag unconditionally, including the flag a newer webhook had set moments earlier after failing to claim the lease — so an event arriving mid-reconciliation left no trace anywhere. A monotonic generation pair (`billing_sync_requested`/`billing_sync_completed`, set by `request_billing_reconciliation` before any Stripe call and reported back by `claim_reconciliation_lease`) means a completing write may clear the flag only if nothing newer has been requested since. The same migration adds `get_billing_reconciliation_candidates`, whose staleness criterion is the only recovery trigger that does not depend on this application having been told anything at all — the case a never-delivered webhook produces. See `DECISIONS.md`'s "Stripe webhook reconciliation" entry for the full incident, including a corrected record of why the third round's own concurrency test for this never actually exercised the scenario it claimed to.

**A subscription/invoice's Stripe Customer must match the organization's own already-persisted one before it is ever applied (Finding 11).** `customerIdMatches()` (`features/billing/reconcile.ts`) is checked before both `syncSubscription` and `activateOnPayment` ever call the shared reconciliation service — a mismatch is quarantined (logged loudly, recorded to `private.billing_anomalies` via `record_billing_anomaly()` as a `"customer_mismatch"` anomaly, left for Stripe to retry) rather than treated as license to rebind the organization to a different Stripe Customer. `private.billing_anomalies` (migration `20260907210000`) is a new table following the same pattern already established for `private.alert_email_log`/`private.notification_email_change_log`: RLS enabled, no `anon`/`authenticated` policy of any kind, not exposed to PostgREST at all (the `private` schema is absent from `config.toml`'s exposed `schemas` list), reachable only via the dedicated `record_billing_anomaly` RPC (`service_role`-only, migration `20260907220000`) — diagnostic/observability data, never itself part of an entitlement decision.

**Only an approved Price governs entitlement at all (Finding 11).** `features/billing/reconcile.ts`'s `pickCurrentSubscription` excludes any subscription whose price isn't in `approvedPriceIds()` (this app's own configured monthly/yearly Price ids) from the pool entirely, not merely de-prioritized — a subscription attached to some other Stripe Product/Price on the same Customer (a data-integrity anomaly, or a forged/foreign attachment) can never establish entitlement, and is itself recorded as an `"unapproved_subscription"` anomaly.

**The environment/livemode check now fails closed, not open (Finding 6, HIGH).** `resolveExpectedLivemode()`'s prior design skipped `event.livemode`/Stripe-key-mode enforcement for anything other than exactly `APP_ENV === "production"`/`"preview"` — including an unset, empty, or misspelled `APP_ENV` in a genuinely deployed runtime, which is exactly the misconfiguration this check exists to catch. Fixed by inverting the condition: only `NODE_ENV === "development"` is exempt; every other runtime must resolve `APP_ENV` to exactly `"production"` or `"preview"` or the function throws, and both the webhook route and `assertStripeConfigurationValid()` treat that thrown error as a hard refusal to proceed, never an unhandled exception that would let processing continue past it.

**The scheduled reconciliation sweep's own bearer secret is the real boundary for a public route (Finding 5)** — see "The deliberate RLS bypasses" above (item 7) for the full mechanism; it is documented here too because it is the newest addition to `proxy.ts`'s `PUBLIC_PATHS` and belongs in the same review pass as the webhook route it mirrors.

## Tenant-isolation test coverage

Beyond RLS policies themselves, `e2e/tenant-isolation.spec.ts` runs against the isolated test project with two real organizations and two real signed-in users, and asserts — through each user's own RLS-bound client, not the admin client, which bypasses RLS and would prove nothing — that Org A cannot read Org B's organization/locations/nfc_cards/feedback/membership rows, cannot update Org B's feedback or nfc_cards (zero rows affected, not an error, and Org B's data is confirmed unchanged afterward), cannot insert directly into Org B's locations/nfc_cards, and never sees Org B's data rendered in its own dashboard. Combined with the per-file RLS coverage in `e2e/feedback-and-card-integrity.spec.ts` (column-level restrictions, finding #3/#4 above) and the Review-Gating Regression Test in `e2e/review-gating.spec.ts` (the Google Review CTA must be identical across all five ratings — the product's one non-negotiable rule), this is the automated form of the Security Checklist's "verify cross-tenant reads fail" / "verify cross-tenant mutations fail" steps, not just a one-time manual check.

## Notification recipient verification (round 3, R3-03)

Round 2 (R2-08) left `notification_email` accepting any syntactically-valid address with zero verification the organization actually controlled it — the org-wide budget above bounded the blast radius but a determined tenant could still direct real, budget-limited alert traffic at an arbitrary third party's inbox. Round 3 built the confirmation flow round 2 explicitly deferred (`DECISIONS.md` § "R2-08" has the full before/after reasoning):

- `reserve_notification_email_change()` (named `request_notification_email_change` through round 7 — renamed by a third independent review, see `DECISIONS.md`) validates the caller and stores a candidate address as **pending**. Round 6 (R6-01, below) changed what happens next: it no longer generates or returns a token at all.
- `confirm_notification_email_change()` — called from the public `app/api/notification-email/confirm` route via the admin client, since whoever clicks the link may not be signed in to this app at all — promotes the pending address to the active `notification_email` only when given a token whose hash matches a non-expired pending request, via a single atomic conditional `UPDATE` (round 6, R6-05 — see below).
- Until confirmed, `notification_email` is untouched, so `features/notifications/negative-feedback-alert.ts`'s existing fallback (email every owner/admin/manager member when it's null) is what actually delivers alerts — "alerts go only to verified organization-member addresses until confirmation" falls directly out of that pre-existing behavior, not new logic that could itself have a gap.
- Requesting a new address while one is already pending overwrites it outright — the old token's hash no longer matches anything, so it silently stops working. There's deliberately no history of abandoned requests to manage.
- `clear_notification_email()` needs no confirmation — removing a recipient can't be abused to send email anywhere, unlike adding one.

The same "RLS is row-level, not column-level" gap already closed for the alert cooldown applies here too, with the same fix: a trigger (`private.prevent_direct_notification_email_change`, installed by a later migration — see "Rollout ordering" above) rejects any direct write to the four notification-email columns from any caller but the functions in this section. Without it, an org member could set the pending token hash to a hash of a token *they* chose (trivial to compute client-side) and then visit the confirmation link with that same token, "confirming" an address without ever proving they control its inbox — defeating the entire point of this fix.

### The token was never actually protected by the confirmation flow (round 6, R6-01, HIGH)

Every version of `request_notification_email_change()` through round 5 — both the round-3 original and round 5's rate-limited revision — returned the raw confirmation token **directly to its `authenticated` caller**. Nothing about that RPC's own grant distinguishes "the settings Server Action calling it on the member's behalf" from "the member's own browser calling it directly with their own Supabase client" — both are the identical `authenticated` role with the identical JWT. A member could therefore call the RPC directly (skipping the settings form, the Server Action, and Resend entirely) with an arbitrary candidate address, read the live token straight out of the RPC's own response, and immediately visit the public confirmation link with it — confirming any address as the organization's notification recipient without the confirmation flow's one actual guarantee (that whoever confirms it received the token by having access to that address's inbox) ever holding. This is not a theoretical reading of the code: the pre-round-6 e2e suite's own "requesting a new address sets it as pending" test already called the RPC directly and read `data.token` from the response to build every other test on top of — the demonstration was sitting in the test suite the whole time.

Fixed by splitting the operation across the same client-boundary the rest of this document draws everywhere else: `reserve_notification_email_change()` (still `authenticated`, still `SECURITY DEFINER`) validates the caller, rate-limits, and reserves the request, returning only a `log_id` — never a secret. The actual token is minted by a new function, `issue_notification_email_change_token(p_log_id)`, `EXECUTE`-granted to `service_role` **only** (never `authenticated`, never `anon`) — reachable exclusively from trusted server code via the admin client (`features/organizations/settings-actions.ts`, § "The deliberate RLS bypasses" above), the same boundary that already keeps `SUPABASE_SECRET_KEY` itself out of any client bundle. A round-3-shaped attack against the *round-3* signature is also closed: migration `20260906090000` revokes `authenticated`'s grant on that original 3-argument function outright (see `DATABASE_SCHEMA.md`'s "Rollout ordering" for why this is a deliberate, documented exception to a strict compatibility window, not an oversight).

Verified directly (`e2e/notification-email-verification.spec.ts`): the response from `reserve_notification_email_change` contains nothing token-shaped; an authenticated client's own attempt to call `issue_notification_email_change_token` gets "permission denied for function"; the original round-3 3-argument signature is likewise no longer callable by `authenticated`.

### A confirmed token could promote a DIFFERENT, later address (round 6, R6-05, MEDIUM — TOCTOU)

`confirm_notification_email_change()` used to `SELECT` the organization matching the supplied token's hash, then separately `UPDATE` it by `id` alone, with no re-check of the token in the `UPDATE`'s own `WHERE` clause. A second `request_notification_email_change()` call for the *same* organization, landing between those two statements, replaces the pending address and token hash — and the pending `UPDATE`, keyed only on `id`, then blindly promotes that *new* address using the *old* token's authority, even though the old token was never issued for it and proves nothing about who controls it.

Fixed by collapsing both statements into one atomic `UPDATE` whose `WHERE` clause re-checks the token hash, the expiry, and that a pending address still exists, using `RETURNING` to learn whether anything matched — there is no window left for a concurrent write to land in, because there is no longer a separate read step. Verified directly: issue a token for address A, replace the pending request with address B before confirming, then confirm the *old* token for A and assert it promotes nothing (not B, not A) — `e2e/notification-email-verification.spec.ts`'s "a token cannot be used to confirm a DIFFERENT pending address requested after it was issued".

### Server-owned request budget (round 5, R5-12; parameters closed off entirely in round 6, R6-04)

Round 5 found that `request_notification_email_change` itself had no rate limit at all — unlike the negative-feedback alert path, an org member could call it in a tight loop, and since every call (at the time) sent a real confirmation email, this was a way to spam an arbitrary third-party inbox with confirmation links, budget-unbounded, the exact class of abuse round 2's `claim_negative_alert_send` cooldown/budget already exists to prevent for the *other* email-sending path.

Round 5's own fix turned out to have the same flaw R6-04 describes generally: the cooldown/budget were accepted as plain `p_cooldown_minutes`/`p_org_hourly_budget` RPC arguments with defaults — an authenticated caller could simply pass `p_cooldown_minutes: 0, p_org_hourly_budget: 999999` and disable its own rate limit outright, which is not a rate limit at all if the party being limited sets the limit. Fixed by removing both from the public signature entirely; the real values now live in `private.notification_email_change_config`, a table keyed **per organization** (not a single shared global row — see the migration's own comment for why: a shared global would make any test that tunes it race every other concurrently-running test exercising this same RPC under its normal defaults), readable only by the `SECURITY DEFINER` function itself and by `service_role` directly (for tests to seed a per-organization override). `finalize_notification_email_change_send` is `service_role`-only now too (previously `authenticated`, with a caller-supplied delivery result and an `auth.uid()`+membership check standing in for authorization) — a client can no longer report its own reservation delivered or failed at all, structurally, not just by convention.

The dual-control mechanics are otherwise unchanged: `private.notification_email_change_log` (migration `20260905193325`) tracks each request as `reserved`/`delivered`/`failed`, both checks are serialized via `pg_advisory_xact_lock` before a new `'reserved'` row is inserted, a cooldown violation raises `VT203`, a budget violation raises `VT204` (`features/organizations/settings-actions.ts` maps both to a Hungarian "too many requests" message). The budget counts `reserved` + `delivered` rows, excluding `failed` ones, so a request that never actually sent (e.g. Resend was down) doesn't permanently consume budget it never used.

**Round 7 (R7-06, LOW) found a reservation could strand as `'reserved'` indefinitely (within the trailing-hour window) if anything failed between creating it and finalizing it.** `features/organizations/settings-actions.ts` called `issue_notification_email_change_token()` and, on success, `sendNotificationEmailConfirmation()`, then called `finalize_notification_email_change_send()` — but a failure in token issuance returned early, before ever calling finalize, and even the finalize call's own error was previously ignored rather than logged. A `'reserved'` row that never resolves still counts against the hourly budget for the rest of its trailing-hour window, for a send that never happened — the same "attempts counted as sends" class of gap round 3 (R3-06) already fixed for the negative-feedback alert path, reappearing here in the newer code. Fixed with a `try`/`catch`/`finally` around the whole post-reservation block: `finalize_notification_email_change_send` is now called exactly once on every path after the reservation is created — a token-issuance failure, a Resend failure, or any unexpected thrown exception all fall through to the same `finally`, which reports `p_delivered: false` unless a send was actually confirmed — and a failure to even reach `finalize` itself (a network-level failure) is now logged via `console.error` rather than silently swallowed. **Deliberate, documented outcome**: if the email genuinely sent but the finalize call itself then failed, the user still sees success — the real-world thing they care about (an email went out) happened, and a finalize failure is purely an internal budget-accounting concern that shouldn't make a successful send look like a failure to the person who triggered it; the finalize failure is logged for operational visibility, not surfaced to the user. An unresolved reservation from a genuinely crashed process (not caught by any `try`/`catch`, since the process itself stopped running) remains the same accepted, bounded worst case `private.notification_email_change_log`'s own migration comment already documents — it ages out of the trailing-hour window on its own. Verified directly (`e2e/notification-email-verification.spec.ts`): repeated token-issuance failures against a small budget (`BUDGET = 2`) do not themselves consume all request capacity for the hour, because each failed reservation is finalized as failed rather than left `'reserved'`.

Verified end-to-end against the isolated test project (`e2e/notification-email-verification.spec.ts`): requesting sets pending, not active; confirming with the correct token promotes it; an unknown or already-used token confirms nothing; an expired token is rejected; a second request overwrites the first and invalidates its token; clearing needs no confirmation and works with a request outstanding; a member of a different organization cannot request a change for this one; `anon`/`authenticated` cannot call `confirm_notification_email_change` directly; a direct `UPDATE` attempt against the protected columns is rejected; through a real browser, the Settings page renders the pending notice and updates correctly after visiting the actual confirmation URL; a second request inside the cooldown window is rejected (`VT203`); five concurrent requests against a per-organization budget of one, proven under real concurrency (`Promise.all`), yield exactly one success and four `VT204` rejections; a failed send does not permanently consume the budget it never used; an authenticated client cannot call `issue_notification_email_change_token` or `finalize_notification_email_change_send` directly (both "permission denied for function"); an authenticated client cannot override the cooldown/budget (the parameters no longer exist on the signature at all); and the round-3 original 3-argument signature is no longer callable by `authenticated` either.

## Card-editor location lock (round 2, R2-09)

`nfc_cards.location_id` has been immutable at the database level since round 1 (`private.prevent_nfc_card_location_change`, `DATABASE_SCHEMA.md`), but the edit dialog rendered the same fully-editable location dropdown for an existing card as for a new one — picking a different location and saving produced a generic "couldn't save" error instead of ever explaining why, since the UI implied a change the database would always reject. Fixed at both layers: `updateNfcCardAction`'s validation schema has no `location_id` field at all (a crafted extra form field is silently ignored, never reaching the database trigger), and the edit form shows the current location as read-only text with an explanation of the deactivate-and-reissue workflow, while card creation keeps the full editable dropdown. Verified with a real browser against the isolated test project (`e2e/nfc-card-location-lock.spec.ts`): edit mode shows read-only text, renaming an existing card still works, a direct crafted `location_id` write is rejected by the database trigger regardless of which client attempts it, and creating a new card is unaffected.
